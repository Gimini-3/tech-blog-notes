# 계좌이체 한 건은 실제로 어떻게 완료될까?

- 읽은 날짜: 2026-09-23
- 회사/작성 주체: 직접 정리
- 노션 정리: [원본 페이지](https://app.notion.com/p/3e7a987f6c4080d4baafc5256e37d8ff)

---

모바일뱅킹에서 다른 은행 계좌로 10만 원을 송금해보자.

```text
A은행 김민수
잔액 500,000원

      │ 100,000원 송금
      ▼

B은행 이철수
잔액 +100,000원
```

송금 버튼을 누르면 몇 초도 지나지 않아 상대방 계좌에 돈이 들어온다.
그래서 우리는 자연스럽게
> A은행에서 B은행으로 실제 돈 10만 원이 즉시 이동했다.
고 생각하기 쉽다.
하지만 실제 금융기관 사이의 결제는 조금 다르게 동작한다.

```text
사용자 계좌 반영
      │
      │ 거의 실시간
      ▼
송금 완료 표시

======================

은행 사이 실제 자금 정산
      │
      │ 이후
      ▼
한국은행에서 최종결제
```

이 차이를 이해하려면 **지급 → 청산 → 결제**를 먼저 알아야 한다.

---

## 1. 지급, 청산, 결제

계좌이체 하나도 크게 세 단계로 나눌 수 있다.

```text
Payment
지급
  │
  ▼
Clearing
청산
  │
  ▼
Settlement
결제
```

#### 지급(Payment)

사용자가 실제로 돈을 보내겠다는 요청을 하는 단계다.

```text
김민수

"이철수에게 10만원 보내줘"
```

#### 청산(Clearing)

은행끼리 서로 얼마를 주고받아야 하는지 계산하는 단계다.

```text
A은행 → B은행 100만원

B은행 → A은행 70만원

       ↓

실제로는

A은행 → B은행 30만원
```

#### 결제(Settlement)

계산이 끝난 금액을 실제 중앙은행 계좌에서 이동시켜 **은행 간 채권·채무 관계를 끝내는 단계**다.
한국은행은 금융기관에 당좌예금계좌를 제공하고, 금융기관들은 이 계좌를 이용해 최종적으로 자금을 결제한다.

---

## 2. 먼저 A은행에서 송금을 요청한다

A은행 사용자 김민수가 B은행 이철수에게 10만 원을 보낸다고 해보자.

```text
김민수
  │
  │ 100,000원 송금
  ▼
A은행 모바일 앱
  │
  ▼
A은행 서버
```

은행에서는 먼저 여러 조건을 확인한다.

```text
계좌가 정상인가?

잔액이 충분한가?

이체 한도를 넘지 않았는가?

거래가 제한된 계좌는 아닌가?

인증이 정상인가?
```

문제가 없다면 지급인의 계좌에서 금액이 차감된다.

```text
A은행

김민수 계좌

500,000원
     │
     │ -100,000
     ▼
400,000원
```

여기까지는 A은행 내부에서 일어나는 일이다.

---

## 3. 상대방이 다른 은행이라면?

만약 수취인도 A은행 사용자라면 같은 은행 내부에서 계좌 간 원장을 변경하면 된다.

```text
A은행

김민수 계좌
     │
     │ 100,000
     ▼
이철수 계좌
```

하지만 이철수의 계좌가 **B은행**에 있다면 이야기가 달라진다.
A은행이 B은행 시스템을 직접 수정할 수는 없다.

```text
A은행

"이철수 계좌에
10만원 넣어주세요"

        │
        ▼

    ????

        │
        ▼

B은행
```

그래서 금융기관 사이에서 지급지시를 전달하는 공동 인프라가 필요하다.

---

## 4. 전자금융공동망

인터넷뱅킹이나 모바일뱅킹을 이용한 타행 계좌이체에는 금융결제원이 운영하는 **전자금융공동망**이 사용된다.

```text
               금융결제원
            전자금융공동망
                  │
        ┌─────────┼─────────┐
        ▼         ▼         ▼
      A은행      B은행      C은행
```

전자금융공동망은 은행 간 공동전산망을 통해 온라인 송금과 같은 서비스를 처리하는 금융결제원의 소액지급시스템 중 하나다.

---

## 5. 지급지시는 이렇게 이동한다

전체 흐름을 단순화하면 다음과 같다.

```text
김민수
  │
  ▼
A은행
  │
  │ "B은행 이철수에게
  │  10만원 입금"
  ▼
금융결제원
전자금융공동망
  │
  ▼
B은행
  │
  ▼
이철수 계좌
```

금융결제원은 은행 사이에서 지급지시를 확인하고 전달한다.
B은행이 정상적으로 요청을 처리하면 결과가 반대 방향으로 돌아간다.

```text
A은행
  │
  ▼
금융결제원
  │
  ▼
B은행
  │
  │ 입금 처리
  ▼
이철수 계좌

       │

처리 결과

       ▼

B은행
  │
  ▼
금융결제원
  │
  ▼
A은행
```

사용자는 이 과정을 몇 초 안에 경험한다.

---

## 6. B은행은 바로 10만 원을 넣어준다

B은행이 지급지시를 받으면 수취인 계좌에 금액을 반영한다.

```text
B은행

이철수 계좌

200,000원
     │
     │ +100,000
     ▼
300,000원
```

이 시점에서 이철수는 10만 원을 사용할 수 있다.
따라서 사용자 입장에서는 송금이 끝났다.

```text
김민수

"송금 완료"


이철수

"10만원 입금"
```

그런데 여기서 중요한 점이 있다.
**아직 A은행이 B은행에 실제 은행 간 자금 10만 원을 최종 지급한 것은 아니다.**
한국은행의 2025년도 연차보고서도 금융결제원 소액지급시스템에서는 수취인 계좌에 자금이 먼저 입금되고, 은행 간 결제는 다음 영업일에 이루어진다고 설명한다.

---

## 7. 왜 바로 은행끼리 10만 원을 보내지 않을까?

하루 동안 A은행과 B은행 사이에는 송금이 한 건만 발생하지 않는다.

```text
A은행 → B은행

10만원
30만원
20만원
50만원


B은행 → A은행

40만원
20만원
30만원
```

모든 거래를 하나씩 실제 결제한다면 엄청나게 많은 자금 이동이 필요하다.

```text
10만원 결제
30만원 결제
20만원 결제
40만원 반대 방향 결제
...
```

그래서 서로 주고받을 돈을 합산한다.

---

## 8. 이것이 청산이다

예를 들어 하루 동안 다음 거래가 발생했다고 해보자.

```text
A은행 → B은행

100만원


B은행 → A은행

70만원
```

각 거래를 모두 결제할 필요는 없다.

```text
A → B 100만원
B → A  70만원

       │
       ▼

100 - 70

       │
       ▼

A → B 30만원
```

최종적으로 A은행이 B은행에 30만 원만 지급하면 된다.
이를 **차액결제(Net Settlement)** 라고 한다.
금융결제원은 각 금융기관 사이에서 발생한 지급지시를 바탕으로 서로 주고받아야 할 금액을 정산한다.

---

## 9. 여러 은행이 있으면?

실제로는 은행이 두 개뿐이 아니다.

```text
A은행
B은행
C은행
D은행
...
```

수많은 거래가 발생한다.

```text
A → B   100억
A → C    50억

B → A    70억
B → C    20억

C → A    30억
C → B    10억
```

금융결제원은 이런 거래들을 모아서 각 은행의 **최종 순포지션**을 계산한다.

```text
A은행

받을 돈 - 줄 돈

        │
        ▼

최종적으로 얼마를
지급하거나 받아야 하는지 계산
```

그리고 이 결과가 한국은행으로 전달된다.

---

## 10. 이제 한국은행이 등장한다

여기서 최종결제를 담당하는 것이 **한은금융망(BOK-Wire+)**이다.

```text
금융결제원
   │
   │ 차액결제 정보
   ▼
한국은행
BOK-Wire+
   │
   ▼
은행별 한국은행 당좌예금
```

은행들은 한국은행에 계좌를 가지고 있다.

```text
한국은행

┌──────────────────┐
│ A은행 당좌예금   │
│ B은행 당좌예금   │
│ C은행 당좌예금   │
└──────────────────┘
```

금융기관 사이의 최종 자금결제는 이 계좌 사이에서 이루어진다.

---

## 11. 실제 은행 사이의 돈은 다음 영업일에 움직인다

전자금융공동망 같은 주요 소액지급시스템은 **이연차액결제 방식**으로 운영된다.
현재 한국은행 자료 기준으로

```text
오늘(T)

사용자 송금
   │
   ├─ A은행 계좌 출금
   │
   └─ B은행 계좌 입금

         ↓


다음 영업일(T+1)
오전 11시

금융기관 간 차액
최종결제
```

가 이루어진다.
즉,

```text
사용자가 돈을 받는 시점

       ≠

은행끼리 최종적으로
돈을 주고받는 시점
```

이다.
이게 계좌이체 구조에서 가장 중요한 부분이다.

---

## 12. 왜 이런 구조를 사용할까?

이 방식에는 큰 장점이 있다.

#### 사용자 입장

돈을 바로 받을 수 있다.

```text
송금
 │
 ▼
몇 초 후 입금
```

#### 은행 입장

수백만 건을 하나하나 결제하지 않아도 된다.

```text
수많은 거래

      │
      ▼
상계(Netting)

      │
      ▼
차액만 결제
```

따라서 실제 결제에 필요한 유동성을 크게 줄일 수 있다.

```text
총 1,000억을 주고받았지만

최종 차액이 50억이라면

실제 최종결제

50억
```

이것이 이연차액결제의 장점이다.

---

## 13. 그런데 위험하지 않을까?

문제가 하나 있다.
B은행은 이철수에게 이미 10만 원을 지급했다.

```text
B은행

이철수에게
10만원 먼저 지급

      │
      ▼

이철수 사용 가능
```

하지만 A은행으로부터 실제 결제자금을 받는 것은 다음 영업일이다.

```text
오늘

B은행 ──▶ 고객에게 10만원 지급


다음 영업일

A은행 ──▶ B은행 최종결제
```

그 사이 A은행이 결제를 못 하면 어떻게 될까?
B은행 입장에서는 이미 고객에게 돈을 지급했기 때문에 손실 위험이 생긴다.
이것이 **차액결제리스크**다.

```text
선지급

   │

   │   ← 위험 구간
   │

최종결제
```

한국은행도 이연차액결제에서는 수취은행이 최종결제 전까지 상대 금융기관의 결제불이행 위험에 노출된다고 설명한다.

---

## 14. 그래서 순이체한도와 담보가 있다

이 위험을 그냥 두는 것은 아니다.
한국은행은 차액결제리스크를 줄이기 위한 제도를 운영한다.
대표적으로

```text
순이체한도

+

담보

+

결제부족자금 지원
```

등이 있다.
은행이 무제한으로

```text
"나중에 줄게"
```

하면서 다른 은행 고객에게 돈을 선지급하게 만들 수 없도록 통제하는 것이다.
2025년에는 차액결제이행용 담보제공비율이 최종 목표인 \*\*100%\*\*까지 인상됐다.

---

## 15. RTGS와는 무엇이 다를까?

한은금융망 자체는 **RTGS(Real-Time Gross Settlement)** 기반 거액결제시스템이다.
RTGS는 거래가 발생할 때마다 총액을 즉시 결제하는 방식이다.

```text
A은행 → B은행 100억

즉시 결제


B은행 → A은행 70억

즉시 결제
```

반면 소액결제시스템은

```text
A → B 100억
B → A  70억

       │
       ▼
상계

       │
       ▼

A → B 30억
```

처럼 차액을 나중에 결제한다.

```text
RTGS

장점
→ 결제리스크 낮음

단점
→ 많은 유동성 필요


이연차액결제

장점
→ 적은 유동성으로 처리 가능

단점
→ 최종결제 전까지 리스크 존재
```

---

## 16. 송금 도중 장애가 나면?

백엔드 관점에서는 여기서도 중요한 문제가 생긴다.
예를 들어 A은행이 지급지시를 보냈다.

```text
A은행
  │
  │ 송금 요청
  ▼
금융결제원
  │
  ▼
B은행
  │
  ▼
입금 완료
```

그런데 입금 완료 응답이 돌아오는 중 네트워크 장애가 발생했다고 해보자.

```text
B은행

입금 성공

   │
   │ 응답
   X
   │
네트워크 장애

   │
   ▼

A은행

Timeout
```

A은행 입장에서는 애매하다.

```text
실패했나?

성공했나?

모름
```

여기서 똑같은 이체를 무작정 다시 실행하면 중복 지급 문제가 발생할 수 있다.

---

## 17. Timeout은 실패가 아니다

분산 결제시스템에서 중요한 원칙이다.

```text
Timeout

≠

Transaction Failed
```

Timeout은 단순히
> 결과를 확인하지 못했다.
라는 의미일 수 있다.
그래서 금융 시스템에서는 거래마다 식별 가능한 거래번호를 관리하고, 처리 결과를 확인할 수 있는 구조가 필요하다.

```text
이체 요청
   │
   ▼
거래번호 생성
   │
   ▼
외부 시스템 요청
   │
   ▼
Timeout
   │
   ▼
같은 거래를 바로 다시 실행 ❌
   │
   ▼
처리결과 확인
   │
   ├─ 성공 → SUCCESS
   │
   └─ 실패 → 재처리 판단
```

금융결제원이 제공하는 전자금융업무에도 송금거래의 처리 결과를 실시간으로 조회하는 **거래확인조회** 기능이 존재한다.

---

## 18. 전체 흐름 다시 보기

10만 원 송금을 처음부터 끝까지 보면 다음과 같다.

```text
김민수
```

## 19. 결국 사용자가 보는 '송금 완료'는 무엇일까?

사용자가 보는 송금 완료는

```text
A은행에서 고객 돈 차감

+

B은행에서 고객 돈 입금
```

이 정상적으로 처리됐다는 의미로 이해할 수 있다.
하지만 금융시스템 전체에서 보면 그 뒤에

```text
지급지시 중계
     │
     ▼
금융기관별 거래 집계
     │
     ▼
청산
     │
     ▼
차액 계산
     │
     ▼
한국은행 계좌에서 최종결제
```

라는 과정이 남아 있다.
따라서

```text
사용자 관점

송금 = 거의 실시간


은행 관점

최종결제 = 이연차액결제
```

라는 두 시점을 구분해서 이해하는 것이 중요하다.

## 정리

우리가 모바일뱅킹에서 보내는 타행 송금 한 건의 핵심 구조는 다음과 같다.

```text
사용자
  │
  ▼
송금은행
  │
  ▼
금융결제원
전자금융공동망
  │
  ▼
수취은행
  │
  ▼
수취인

──────── 사용자 거래 ────────


수많은 은행 간 거래
        │
        ▼
금융결제원
   Clearing
        │
        ▼
  차액 계산
        │
        ▼
한국은행
BOK-Wire+
        │
        ▼
 Settlement

────── 금융기관 최종결제 ──────
```

결국 계좌이체 시스템의 핵심은 **돈을 빠르게 보여주는 것과 돈을 최종적으로 결제하는 것을 분리한 구조**에 있다.
사용자에게는 즉시 돈을 지급하면서도, 금융기관들은 수많은 거래를 상계해 차액만 결제함으로써 필요한 유동성을 줄인다.
그리고 이 구조 때문에

```text
차액결제리스크
순이체한도
담보
결제유동성
거래결과 확인
```

같은 금융 시스템 특유의 개념들이 등장한다.
단순해 보이는 **10만 원 송금 한 건 뒤에도 실시간 분산 시스템과 금융기관 간 청산·결제 인프라가 함께 움직이고 있는 것**이다.
