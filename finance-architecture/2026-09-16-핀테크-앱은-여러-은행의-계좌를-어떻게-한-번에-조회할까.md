# 핀테크 앱은 여러 은행의 계좌를 어떻게 한 번에 조회할까?

- 읽은 날짜: 2026-09-16
- 회사/작성 주체: 직접 정리
- 노션 정리: [원본 페이지](https://app.notion.com/p/684a987f6c4082b5a24e81f109387f33)

---

은행 앱이나 핀테크 앱에서 '다른 은행 계좌 추가'를 누르고 몇 가지 인증을 거치면 이런 화면을 볼 수 있다.

```text
내 계좌

국민은행    3,200,000원
신한은행      820,000원
우리은행    1,550,000원
카카오뱅크    420,000원
```

은행은 모두 다른데 하나의 앱에서 몇 초 만에 잔액이 나타난다.
그러면 이 앱이 국민은행, 신한은행, 우리은행 서버에 각각 직접 접속하는 걸까?
실제로는 그 사이에 **오픈뱅킹**이라는 중요한 계층이 있다.
> 참고로 자산관리 앱의 '내 자산 모아보기'처럼 은행·카드·증권·보험을 한 화면에 모아 보여주는 기능은 2022년 이후 주로 **마이데이터**를 기반으로 동작한다. 이 글은 오픈뱅킹의 구조를 중심으로 설명하고, 마이데이터와의 차이는 16장에서 다룬다.

---

## 1. 은행마다 직접 연동하면 어떤 문제가 있을까?

오픈뱅킹이 없다고 생각해보자.
핀테크 회사가 여러 은행의 계좌를 조회하려면 각각 연동해야 한다.

```text
                 핀테크 서버
                     │
        ┌────────────┼────────────┐
        ▼            ▼            ▼
     국민은행        신한은행       우리은행
      API           API          API
```

은행마다 API 규격이 다르면

```text
국민은행

GET /account/balance


신한은행

POST /bank/account/inquiry


우리은행

POST /v1/deposit/query
```

처럼 모든 은행에 맞는 코드를 따로 만들어야 한다.
은행이 20개라면 은행마다 별도로 협약을 맺고, 인증 방식과 API 규격, 연동을 모두 따로 관리해야 한다.
그래서 중간에서 금융기관의 기능을 **표준화해서 제공하는 플랫폼**이 필요하다.

---

## 2. 오픈뱅킹

한국에서는 금융결제원이 **오픈뱅킹**을 운영한다.
오픈뱅킹은 참여기관 공동의 표준 API를 제공하고, 그 API를 통한 거래를 중계하는 **개방형 금융결제 플랫폼**이다.
구조를 단순화하면 다음과 같다.

```text
             핀테크 서비스
                  │
                  │ 표준 API
                  ▼
        ┌───────────────────┐
        │ 금융결제원        │
        │ 오픈뱅킹          │
        └─────────┬─────────┘
                  │
       ┌──────────┼──────────┐
       ▼          ▼          ▼
    국민은행    신한은행    우리은행
```

핀테크 회사 입장에서는 모든 은행의 서로 다른 시스템을 직접 이해하는 대신 **오픈뱅킹에서 제공하는 표준 API****를 사용할 수 있다.**
처음에는 은행 중심으로 시작했지만 참가기관은 계속 늘어났다.

```text
2019년 12월    은행 + 핀테크 기업 (전면 시행)
2020년 12월    상호금융, 우체국, 증권사
2021년         저축은행, 카드사
```

그래서 지금은 은행 계좌뿐 아니라 증권사나 상호금융 계좌도 같은 표준 API로 다룰 수 있다.
오픈뱅킹에서 제공하는 대표적인 계좌 관련 API는 다음과 같다.

```text
잔액조회 (개인, 법인)
거래내역조회 (개인, 법인)
계좌실명조회
송금인정보조회
수취조회
입금이체
출금이체
```

계좌 외에도 다음과 같은 API가 추가됐다.

```text
카드목록 · 카드청구정보 조회
선불목록 · 선불잔액 · 선불거래내역 조회
보험목록 · 보험납입정보 조회
대출·리스목록 · 대출·리스기본정보 조회
```

## 3. 그렇다고 아무 계좌나 조회할 수 있는 것은 아니다

당연히 핀테크 회사가

```text
계좌번호만 알면

→ 잔액 조회
```

할 수 있는 구조는 아니다.
먼저 사용자의 인증과 동의가 필요하다.
전체 흐름은 다음과 같다.

```text
사용자

"다른 은행 계좌 추가"
      │
      ▼
오픈뱅킹 연동 페이지로 이동
      │
      ▼
본인 인증
      │
      ▼
등록할 계좌 선택
      │
      ▼
조회 / 출금 동의
      │
      ▼
핀테크 앱 ↔ 계좌 연결
```

여기서 설명하는 것은 가장 일반적인 **결제원인증** 방식이다. 이 방식에서는 사용자가 핀테크 앱이 아니라 **오픈뱅킹이 제공하는 연동 페이지**에서 인증과 동의를 진행한다. 은행이나 대형사업자 같은 일부 자체인증 이용기관은 자체 인증 절차를 사용할 수 있다.
오픈뱅킹은 여러 권한을 한 번에 요청하는 **멀티 스코프**를 지원한다. 그래서 사용자 인증과 계좌등록이 한 번의 흐름에서 함께 처리된다.
그리고 이 동의는 영구적이지 않다. 금융정보조회 신청은 1년 단위로 다시 해야 한다.
따라서 서비스는

```text
동의 만료
    │
    ▼
재연결 안내
    │
    ▼
다시 인증 + 동의
```

같은 흐름도 함께 설계해야 한다.

## 4. OAuth를 사용하는 이유

사용자가 핀테크 앱에서 국민은행 계좌를 연결한다고 해보자.
좋지 않은 구조는 다음과 같다.

```text
핀테크 앱

국민은행 ID
국민은행 Password

      ↓

핀테크 서버 저장
```

핀테크 회사가 은행 로그인 정보를 직접 가지고 있어야 한다.
보안상 좋지 않다.
이건 가상의 예가 아니다. 과거 많은 자산관리 서비스는 실제로 사용자의 금융기관 로그인 정보를 받아 대신 로그인한 뒤, 화면의 데이터를 긁어오는 **스크래핑** 방식을 썼다. 마이데이터가 전면 시행되면서 마이데이터 사업자의 스크래핑은 금지됐다(16장).
OAuth에서는 구조가 다르다. 결제원인증 방식을 기준으로 보면 다음과 같다.

```text
핀테크 앱
    │
    │ 계좌 연결 요청
    ▼
오픈뱅킹 연동 페이지
    │
    │ 사용자 인증 + 동의
    ▼
오픈뱅킹
    │
    │ Authorization Code (Callback URL로 전달)
    ▼
핀테크 서버
    │
    │ Code 교환 (Client ID / Secret 함께 전송)
    ▼
Access Token
```

즉, 핀테크 서비스가 은행 비밀번호를 전달받아 저장하는 방식이 아니다. **사용자가 권한을 허용하고, 핀테크 서비스는 그 권한을 나타내는 Token을 이용한다.**

#### Token은 두 종류다

오픈뱅킹의 모든 API가 사용자 동의를 거친 Token을 쓰는 것은 아니다.

```text
사용자 Token (3-legged)

- 사용자 인증 + 동의를 거쳐 발급
- OAuth 2.0 Authorization Code Grant
- 잔액조회, 거래내역조회처럼
  "특정 사용자의 계좌"를 다루는 API에 사용


이용기관 Token (2-legged)

- 사용자 개입 없이 Client ID / Secret만으로 발급
- OAuth 2.0 Client Credentials Grant
- 계좌실명조회처럼
  이용기관이 알고 있는 계좌를 확인하는 API에 사용
```

## 5. 계좌번호도 그대로 사용하지 않는다

여기서 또 재미있는 부분이 있다.
결제원인증 방식에서 이용기관은 사용자의 은행명과 계좌번호를 직접 받아 등록할 수 없다. 반드시 오픈뱅킹의 계좌등록 페이지를 거쳐야 한다.
계좌등록이 완료되면 실제 계좌번호 대신 **핀테크이용번호**를 받는다.

```text
실제 계좌

국민은행
123-456-789012

       │
       ▼

오픈뱅킹

       │
       ▼

핀테크이용번호

123456789012345678901234
```

핀테크이용번호는 24자리 숫자로 된 일종의 가상 계좌번호다.

```text
- 등록한 계좌마다 따로 발급된다
- 발급받은 이용기관(클라이언트) 안에서만 유효하다
- 다른 이용기관에서는 쓸 수 없다
```

이후 잔액조회, 거래내역조회, 출금이체 등에서는 실제 계좌번호 대신 이 번호를 사용한다.
핀테크 서비스는 실계좌번호를 직접 들고 있지 않아도 되므로, 정보가 노출될 수 있는 범위가 줄어든다.

#### 다만 예외도 있다

```text
자체인증 이용기관 (은행, 대형사업자 등)
→ 핀테크이용번호 대신 실계좌번호로 받을 수 있음

계좌실명조회
→ 실계좌번호 + 이용기관 Token 사용

입금이체
→ 핀테크이용번호와 실계좌번호 모두 사용 가능
```

즉 "오픈뱅킹 API는 항상 핀테크이용번호를 쓴다"가 아니다. **사용자 계좌를 조회하는 API는 핀테크이용번호를 쓴다**가 정확하다.

## 6. 이제 잔액을 조회해보자

사용자가 앱에서

```text
새로고침
```

을 누른다고 해보자.
핀테크 서버에는 사용자가 연결해 놓은 계좌 정보가 있다.

```text
User 100

Account A
핀테크이용번호 = AAA

Account B
핀테크이용번호 = BBB

Account C
핀테크이용번호 = CCC
```

그러면 각 계좌에 대해 잔액조회 API를 호출할 수 있다.

```text
                  핀테크 서버

            ┌─────────┼─────────┐
            │         │         │
            ▼         ▼         ▼

         Account A Account B Account C

            │         │         │
            └─────────┼─────────┘
                      ▼
                  오픈뱅킹
                      │
          ┌───────────┼───────────┐
          ▼           ▼           ▼
       국민은행     신한은행     우리은행
```

잔액조회 요청에는 대표적으로 다음 값이 들어간다.

```text
GET /v2.0/account/balance/fin_num

Authorization: Bearer <사용자 Access Token>

bank_tran_id      요청마다 부여하는 거래고유번호
fintech_use_num   핀테크이용번호
tran_dtime        요청일시
```

## 7. 앱에서 '한 번에 조회'된다는 의미

여기서 중요한 점이 있다.
사용자가 버튼을 한 번 눌렀다고 해서 실제로

```text
SELECT *
FROM 모든은행계좌
WHERE user_id = 100;
```

같은 쿼리가 실행되는 것은 아니다.
각 금융기관은 서로 완전히 다른 시스템이다.
실제로는 여러 조회 결과를 **Aggregation**한다.

```text
국민은행 조회 ──────┐
                 │
신한은행 조회 ──────┼──▶ Aggregator ──▶ 앱
                 │
우리은행 조회 ──────┘
```

사용자 입장에서는

```text
"내 계좌 조회"
```

한 번이지만,
서버 내부에서는 여러 요청을 보내고 결과를 하나로 합치는 것이다.
> 여기서 말하는 구조는 오픈뱅킹의 **개별 잔액조회 API**를 쓰는 경우다. 잔액조회 API는 핀테크이용번호 하나로 계좌 하나를 조회한다. 그래서 여러 계좌를 보여주려면 계좌별로 호출한 뒤 결과를 합쳐야 한다.
	금융결제원에는 이와 별도로 **어카운트인포(계좌정보 통합관리 서비스)**의 계좌통합조회 API도 있다. 사용자 명의로 전 금융기관에 개설된 계좌를 한 번에 조회하는 API다. 다만 오픈뱅킹과는 별도 계약이 필요한 다른 서비스이고, 흩어진 계좌와 휴면계좌를 확인하는 '내 계좌 찾기'에 가까운 목적을 가진다.
	그리고 이 경우에도 Aggregation이 사라지는 것은 아니다. 여러 기관의 결과를 모으는 일을 핀테크 서버 대신 금융결제원이 할 뿐이다.

## 8. 순차적으로 요청하면 느리지 않을까?

계좌가 5개 있다고 해보자.
한 요청에 300ms가 걸린다면 순차 호출은

```text
국민은행     300ms
     ↓
신한은행     300ms
     ↓
우리은행     300ms
     ↓
하나은행     300ms
     ↓
카카오뱅크   300ms

총 약 1.5초
```

처럼 시간이 누적된다.
그래서 이런 Aggregation 서비스는 가능한 범위에서 독립적인 요청을 **병렬로 처리하는 구조**를 생각할 수 있다.

```text
                  조회 시작
                     │
        ┌────────────┼────────────┐
        ▼            ▼            ▼
     국민은행      신한은행      우리은행
      300ms         400ms         250ms
        │            │            │
        └────────────┼────────────┘
                     ▼
                결과 Aggregation
```

전체 응답 시간은 가장 느린 요청의 영향을 크게 받는다.
다만 무제한으로 동시에 호출하면 안 된다. 금융기관의 부하, 오픈뱅킹 이용 정책, 그리고 **조회 API에도 건별로 붙는 수수료**를 고려해 동시 호출량을 제어해야 한다.

## 9. 은행마다 응답 형식이 다르면?

오픈뱅킹의 중요한 역할 중 하나가 **표준화된 API 인터페이스를 제공****하는 것**이다.
그래서 국민은행이든 신한은행이든 증권사든, 잔액조회 응답은 같은 필드 구조로 온다.
하지만 핀테크 서비스 내부에서는 보통 자신들이 사용할 Domain Model로 한 번 더 변환한다.
예를 들어 외부에서

```text
은행명
계좌종류
상품명
잔액
출금가능금액
```

형태로 받은 데이터를 내부에서는

```text
BankAccount

bank
accountId
productName
balance
withdrawableAmount
updatedAt
```

처럼 사용한다.
전체 구조는

```text
각 금융기관 시스템
      │
      ▼
오픈뱅킹 표준 API
      │
      ▼
핀테크 Adapter
      │
      ▼
내부 Domain Model
      │
      ▼
모바일 앱
```

이 된다.
외부 시스템의 데이터 구조를 서비스 내부까지 그대로 끌고 들어오지 않는 것이다. 나중에 오픈뱅킹 외에 마이데이터 같은 다른 데이터 소스가 추가돼도 Adapter만 늘리면 된다.

---

## 10. 하나의 은행이 장애 나면?

여러 외부 시스템을 조회하는 서비스에서 중요한 문제가 있다.
예를 들어

```text
국민은행   성공

신한은행   성공

우리은행   Timeout

하나은행   성공
```

이라고 해보자.
우리은행 하나가 실패했다고 전체 요청을 실패시키면

```text
내 계좌 조회 실패

❌ 국민은행
❌ 신한은행
❌ 우리은행
❌ 하나은행
```

사용자 경험이 좋지 않다.
그래서 Aggregation 시스템에서는 **부분 실패를 허용하는 구조**가 중요하다.

```text
국민은행    3,200,000원

신한은행      820,000원

우리은행    조회 실패
           ↳ 다시 시도

하나은행    1,500,000원
```

즉,

```text
4개 중 3개 성공

       ↓

성공한 데이터는 반환

       +

실패한 기관만 별도 처리
```

하는 방식이다.

#### 그런데 '실패'를 판정하는 것부터 단순하지 않다

오픈뱅킹 응답에는 응답코드가 두 층으로 들어 있다.

```text
rsp_code         오픈뱅킹(API) 레벨 응답코드     정상: A0000

bank_rsp_code    참가기관(은행) 레벨 응답코드    정상: 000
```

HTTP 상태코드만 보고 성공으로 처리하면 안 된다. 두 코드를 모두 확인해야 한다.

```text
오픈뱅킹 단에서 실패했는가?
        또는
특정 금융기관 단에서 실패했는가?
```

그래야 어떤 기관을 "조회 실패"로 표시할지 정확히 구분할 수 있다.

## 11. Timeout도 중요하다

은행 API 하나가 응답을 계속 주지 않는다고 생각해보자.

```text
국민은행  200ms
신한은행  300ms
우리은행  30초...
```

전체 요청이 우리은행 때문에 30초 동안 기다리면 안 된다.
그래서 외부 금융기관 호출에는 일반적으로

```text
Connection Timeout

Read Timeout

Retry

Circuit Breaker
```

같은 실패 대응 전략을 함께 고려한다.
예를 들어

```text
우리은행 API
     │
     ▼
3초 동안 응답 없음
     │
     ▼
Timeout
     │
     ▼
전체 요청을 막지 않음
     │
     ▼
우리은행만 조회 실패 처리
```

하는 방식이다.
다만 여기까지는 **조회** 이야기다. 이체에서는 Timeout의 의미가 완전히 달라진다(12장).

---

## 12. 무조건 Retry하면 되는 것도 아니다

외부 API가 실패했다고 무조건 계속 재시도하면 더 큰 문제가 생길 수 있다.

```text
은행 장애
   │
   ▼
요청 실패
   │
   ▼
Retry
Retry
Retry
Retry
Retry
   │
   ▼
은행 서버 부하 증가
```

장애 중인 시스템에 모든 핀테크 서버가 재시도를 쏟으면 **Retry Storm**이 발생할 수 있다.
그래서 보통

```text
Retry

     +

Exponential Backoff

     +

Jitter

     +

Circuit Breaker
```

같은 전략을 조합한다.

#### 조회와 이체는 다르다

금융 도메인에서는 Retry Storm보다 더 조심해야 할 문제가 있다.

```text
잔액조회 Timeout

→ 조회 요청 자체는 계좌 상태를 바꾸지 않는다
→ 그래서 다시 조회해도 부작용이 없다
→ 단, 재조회 시점에 따라 잔액은 달라질 수 있다
  (그 사이 입출금이 일어날 수 있으므로)
→ 호출마다 조회 수수료는 발생한다


출금이체 Timeout

→ 은행에서는 이미 출금이 처리됐을 수 있다
→ 그대로 다시 요청하면 이중 출금 위험
→ 먼저 이체결과를 확인해야 한다
```

재시도가 안전한지를 가르는 기준은 **"결과 값이 같은가"가 아니라 "****요청이 서버 상태를 바꾸는가****"**다. 같은 잔액조회를 두 번 해서 다른 값이 나와도 계좌에는 아무 일도 일어나지 않았다. 반면 출금이체는 한 번 더 보내는 것만으로 계좌 상태가 한 번 더 바뀔 수 있다.
그리고 이체에서 **응답을 받지 못했다는 것은 실패했다는 뜻이 아니다.** 결과를 모르는 상태일 뿐이다.
금융결제원 문서도 이체 요청에서 응답을 받지 못한 경우에는 API 명세서의 처리 절차를 따르도록 안내한다.
그래서 이체에서는

```text
이체 요청
   │
   ▼
Timeout (결과 모름)
   │
   ▼
이체결과조회 API로 실제 처리 여부 확인
   │
   ├── 처리됨    → 성공으로 기록
   │
   └── 처리 안 됨 → 새 요청으로 재시도
```

처럼 **먼저 결과를 확인한 뒤 판단**해야 한다.
이를 위해 요청마다 부여하는 거래고유번호(bank_tran_id)를 반드시 기록해 둔다.

## 13. 거래내역은 어떻게 가져올까?

잔액뿐 아니라 거래내역도 조회할 수 있다.

```text
Account
   │
   ▼
거래내역조회 API
   │
   ▼
2026-09-20 스타벅스    -5,500
2026-09-20 편의점      -3,000
2026-09-21 급여     +3,000,000
```

거래내역조회 API는 기간을 지정해서 조회한다.

```text
GET /v2.0/account/transaction_list/fin_num

inquiry_type     A(전체) / I(입금) / O(출금)
inquiry_base     D(일자 기준) / T(시간 기준)
from_date ~ to_date
from_time ~ to_time   (시간 기준일 때)
sort_order       D(내림차순) / A(오름차순)
```

그리고 한 페이지에 최대 25건씩, 페이지 단위로 가져온다.
따라서 거래가 많으면

```text
Page 1 (최대 25건)
  │
  │ next_page_yn = Y
  │ befor_inquiry_trace_info 를 다음 요청에 전달
  ▼
Page 2
  │
  ▼
Page 3
  │
  ▼
...
  │
  │ next_page_yn = N
  ▼
끝
```

처럼 여러 번 요청해야 한다.

## 14. 매번 모든 거래를 다시 가져올 필요는 없다

이미 가져온 거래내역을 매번 처음부터 다시 수집하는 것은 비효율적이다. 그래서 마지막 동기화 시점을 관리하는 방법을 생각할 수 있다.
그런데 여기서 주의할 점이 두 가지 있다.

```text
1. 이 API는 "마지막 조회 이후 바뀐 것만" 주는
   변경분(delta) 조회를 제공하지 않는다.
   → 기간을 지정해서 그 기간의 거래를 다시 받는 방식이다.

2. 응답의 개별 거래에는 고유 ID가 없다.
   → 거래일자, 거래시간, 입출금구분, 거래구분,
     통장인자내용, 거래금액, 거래후잔액 등만 온다.
```

그래서 서비스에서는 다음과 같은 방식을 고려할 수 있다. 아래는 금융결제원이 정한 방식이 아니라 **애플리케이션 설계 예시**다.

```text
마지막 동기화

2026-09-20 18:00

       │
       ▼

조금 겹치게 다시 조회
(예: 2026-09-20 17:00 ~ 현재)

       │
       ▼

응답 필드를 조합한 자체 거래 fingerprint로 중복 제거
(예: 거래일자 + 거래시간 + 입출금구분
     + 거래금액 + 거래후잔액)

       │
       ▼

새로운 거래만 저장

       │
       ▼

마지막 동기화 시점 갱신
```

겹치게 조회하는 이유는 경계 시점에 걸친 거래를 놓치지 않기 위해서다.
fingerprint에 **거래후잔액**을 넣으면 같은 시각에 같은 금액의 거래가 두 건 있어도 구분할 수 있다. 다만 오픈뱅킹이 거래별 고유 ID를 제공하는 것은 아니므로, 이 fingerprint를 완전한 식별자로 간주해서는 안 된다.
그리고 내부 DB에서

```text
사용자

     │

     ├─ 국민은행 거래
     ├─ 신한은행 거래
     └─ 우리은행 거래
```

를 통합한다.
이렇게 만들어진 데이터를 이용하면

```text
이번 달 식비

이번 달 소비

총 자산

카테고리별 지출
```

같은 기능도 만들 수 있다.

## 15. 캐시도 사용할 수 있다

계좌조회 화면에 들어올 때마다 모든 금융기관 API를 호출하면 두 가지 문제가 생긴다.

```text
1. 외부 API 의존성이 지나치게 커진다
2. 조회 API 호출마다 수수료가 발생한다
```

그래서 서비스 요구사항에 따라

```text
Client
   │
   ▼
Fintech Server
   │
   ├── 최근 데이터 존재
   │       │
   │       └──▶ Cache 반환
   │
   └── 최신 조회 필요
           │
           ▼
       Open Banking
```

같은 구조를 사용할 수도 있다.
즉 캐시는 성능 문제이면서 동시에 **비용 문제**다.
다만 금융정보는 **최신성이 중요하므로 데이터 종류마다 캐시 정책을 다르게 가져가는 것**이 중요하다.
예를 들어 잔액과 오래된 거래내역은 같은 캐시 정책을 사용할 이유가 없다.

```text
잔액              짧은 TTL 또는 사용자 새로고침 시 갱신
최근 거래내역     동기화 주기에 맞춰 갱신
오래된 거래내역   이미 확정된 데이터 → 내부 DB에서 제공
```

## 16. 오픈뱅킹과 마이데이터는 같은 걸까?

여기서 자주 헷갈리는 개념이 있다.

```text
Open Banking

vs

MyData
```

둘 다 여러 금융기관의 정보를 한 앱에서 보여줄 수 있다. 하지만 **제도의 성격**이 다르다.

#### 오픈뱅킹

금융결제원이 운영하며, 참여기관 공동의 **표준 API를 제공하고 그 API를 통한 거래를 중계****하는 ****개방형 금융결제 플랫폼**이다.
은행에서 시작해 상호금융, 우체국, 증권사, 저축은행, 카드사까지 참가기관이 넓어졌다.

```text
잔액조회, 거래내역조회

계좌실명조회

입금이체, 출금이체

카드 · 선불 · 보험 · 대출/리스 정보 조회
```

등을 제공한다.
핵심은 조회뿐 아니라 **돈을 실제로 옮기는 이체와 거래중계까지 처리한다**는 점이다.

---

#### 금융 마이데이터

마이데이터는 신용정보법에 따른 **본인신용정보관리업**이다.
사용자가 자신의 정보를 특정 사업자에게 보내달라고 요구하면(전송요구권), 정보를 가진 기관이 표준 API로 해당 정보를 전송한다.

```text
은행 ──────┐
           │
카드 ──────┤
           │
증권 ──────┤
           │
보험 ──────┼──▶ MyData 사업자
           │
저축은행 ──┤
           │
전자금융 ──┤
           │
통신 ──────┘
```

한국의 금융 마이데이터는 기존의 화면 스크래핑 방식에서 표준 API 방식으로 전환됐다. 2022년 1월 5일부터 API 방식이 전면 시행됐고, 이때부터 마이데이터 사업자의 스크래핑은 금지됐다.
**마이데이터 API 자체에는 이체 기능이 없다.** 다만 마이데이터 사업자가 오픈뱅킹을 별도로 연동해 같은 앱에서 이체를 제공할 수는 있다.

---

#### 정리하면

|  | 오픈뱅킹 | 금융 마이데이터 |
| --- | --- | --- |
| 성격 | 표준 API 기반 개방형 금융결제 플랫폼 | 본인 신용정보 전송·관리 제도 |
| 근거 | 금융결제원 오픈뱅킹공동업무 | 신용정보법 (본인신용정보관리업) |
| 핵심 기능 | 조회 + 이체 + 거래중계 | 본인 금융정보 전송·통합 |
| 이체 | 지원 | 마이데이터 API 자체에는 없음 |
| 대표 활용 | 타행 계좌 조회·송금 | 통합 자산관리 |

따라서 앱에서

```text
은행 계좌
+
카드
+
주식
+
보험
+
대출
```

까지 한 번에 보여준다면, 그 화면은 대부분 마이데이터로 동작한다.
반대로 그 화면에서 바로 **다른 은행 계좌의 돈을 출금하거나 송금**한다면 오픈뱅킹이 쓰이는 것이다.
그리고 이 글에서 다룬 Aggregation, 부분 실패, Timeout, Adapter 구조는 마이데이터 기반 서비스에서도 그대로 적용된다.

## 18. 전체 흐름 정리

처음 사용자가 계좌를 연결할 때는 (결제원인증 방식 기준)

```text
계좌 연결 요청
   │
   ▼
오픈뱅킹 연동 페이지
   │
   ▼
본인 인증 + 계좌 선택 + 조회/출금 동의
   │
   ▼
Authorization Code (Callback)
   │
   ▼
Code → Access Token 교환 (서버에서)
   │
   ▼
핀테크이용번호 수신 · 저장
   │
   ▼
동의 만료 시점 관리 (1년 단위 갱신)
```

이후 계좌를 조회할 때는

```text
사용자 조회 요청
       │
       ▼
연결된 계좌 확인 (핀테크이용번호)
       │
       ▼
캐시 확인 (데이터 종류별 정책)
       │
       ▼
필요한 계좌만 병렬 조회
(동시성 제한 + Timeout)
       │
       ▼
오픈뱅킹
       │
       ▼
각 금융기관
       │
       ▼
응답코드 판정 (두 층 모두)
       │
       ▼
Domain Model 변환 + Aggregation
       │
       ▼
부분 실패 처리
       │
       ▼
사용자에게 반환
```

이라는 구조가 된다.

---

## 19. 이 구조에서 중요한 점

사용자에게는

```text
"내 계좌 한 번에 조회"
```

라는 단순한 기능처럼 보인다.
하지만 백엔드 관점에서는 사실 **분산된 여러 금융 시스템의 데이터를 모으는 Aggregation 문제**다.

```text
여러 금융기관
     │
     ▼
표준 API
     │
     ▼
병렬 요청
     │
     ▼
Timeout / Retry
     │
     ▼
응답코드 판정 + 부분 실패
     │
     ▼
데이터 표준화
     │
     ▼
Aggregation
```

따라서 이 기능의 핵심은 단순히 API 하나를 호출하는 것이 아니다.
**서로 다른 금융기관을 하나의 서비스처럼 보이게 만드는 것**에 있다.

```text
사용자 입장

       하나의 금융 서비스


실제 내부

국민은행 ─┐
신한은행 ─┼──▶ 표준화 ──▶ 핀테크 서비스
우리은행 ─┤
하나은행 ─┘
```

그리고 그 사이에서 **오픈뱅킹이 금융기관과 핀테크 서비스를 연결하는 표준화된 통로 역할**을 한다.
마지막으로 하나 더 기억할 점이 있다. 조회는 서버 상태를 바꾸지 않기 때문에 부분 실패와 재시도로 풀 수 있다. 하지만 이체까지 다루는 순간, 시스템은 **"결과를 모르는 상태"를 안전하게 처리하는 문제**를 함께 풀어야 한다.
