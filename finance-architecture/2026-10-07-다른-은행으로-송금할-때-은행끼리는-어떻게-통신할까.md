# 다른 은행으로 송금할 때 은행끼리는 어떻게 통신할까?

- 읽은 날짜: 2026-10-07
- 회사/작성 주체: 직접 정리
- 노션 정리: [원본 페이지](https://app.notion.com/p/b1ca987f6c408302954d017de1239070)

---

앱에서 다른 은행으로 10만 원을 송금하면 사용자 입장에서는 단순하다.

```text
A은행 내 계좌
100,000원 감소

        ↓

B은행 상대 계좌
100,000원 증가
```

하지만 내부에서는 단순히 A은행이 B은행에 돈을 보내는 것으로 끝나지 않는다.
한국의 타행송금을 이해하려면 크게 세 주체를 보면 된다.

```text
A은행 / B은행
→ 고객 계좌와 원장 관리

금융결제원
→ 은행 간 소액 지급지시 중계 + 청산

한국은행
→ 은행 간 최종 자금결제
```

전체 흐름은 다음과 같다.

```text
                 [실시간 송금]

고객
 │
 ▼
A은행
 │
 ▼
금융결제원
 │
 ▼
B은행
 │
 ▼
수취인


                 [사후 청산·결제]

여러 은행의 거래
      │
      ▼
 금융결제원
      │
      │ 은행별 차액 계산
      ▼
   한국은행
      │
      ▼
  BOK-Wire+
      │
      ▼
은행들의 한국은행 당좌예금계좌
```

즉 **고객에게 보이는 송금과 은행 사이의 최종 결제는 서로 다른 단계**다.

---

## 1. 왜 은행끼리 직접 연결하지 않을까?

은행이 여러 개 있을 때 모든 은행이 서로 직접 연결한다면 구조가 복잡해진다.

```text
A ↔ B
A ↔ C
A ↔ D

B ↔ C
B ↔ D
...
```

은행 수가 증가할수록 연결 수도 크게 증가한다.
그래서 중간에 공통 금융 인프라를 둔다.

```text
        A은행
          │
        B은행
          │
     금융결제원
          │
        C은행
          │
        D은행
```

금융결제원이 은행 사이의 공통 소액지급 인프라 역할을 한다.

---

## 2. 금융결제원은 무엇을 할까?

타행송금을 단순화하면 금융결제원은 다음 역할을 한다.

```text
A은행

"이 계좌에서
 B은행 계좌로
 10만원을 보내주세요."

       │
       ▼

금융결제원

- 지급지시 확인
- 수취은행 식별
- 메시지 중계

       │
       ▼

B은행
```

금융결제원은 고객의 실제 계좌 잔액을 관리하는 기관은 아니다.

```text
A은행 고객 원장
→ A은행 관리

B은행 고객 원장
→ B은행 관리

은행 간 연결
→ 금융결제원
```

금융결제원은 전자금융공동망, 오픈뱅킹공동망 등 금융기관 간 지급결제 인프라를 제공한다.

---

## 3. 전체 실시간 송금 구조

서비스 관점에서 보면 다음과 비슷하다.

```text
┌──────────────┐
│    고객 앱    │
└──────┬───────┘
       ▼
┌──────────────┐
│  A은행 채널계 │
└──────┬───────┘
       ▼
┌──────────────┐
│ 인증/한도/FDS │
└──────┬───────┘
       ▼
┌──────────────┐
│ A은행 이체시스템│
└──────┬───────┘
       ▼
┌──────────────┐
│  A은행 대외계 │
└──────┬───────┘
       ▼
┌──────────────┐
│   금융결제원  │
└──────┬───────┘
       ▼
┌──────────────┐
│  B은행 대외계 │
└──────┬───────┘
       ▼
┌──────────────┐
│  B은행 계좌원장│
└──────┬───────┘
       ▼
     수취인
```

---

## 4. 1단계: A은행이 송금 요청을 받는다

사용자가

```text
A은행 계좌

→ B은행 계좌

100,000원
```

을 송금한다고 하자.
A은행은 먼저

```text
로그인 / 본인 인증

계좌 상태

출금 가능 잔액

1회 / 1일 이체한도

FDS

추가 인증
```

등을 확인한다.
여기서 실패하면 금융결제원이나 B은행까지 요청을 보낼 필요가 없다.

---

## 5. 2단계: 거래번호를 만든다

검증에 성공하면 송금 거래를 식별할 수 있는 번호를 만든다.

```text
TX_ID = ABC123
```

그리고 보통 다음과 같은 정보를 관리한다.

```text
TX_ID
금액
수취은행
수취계좌
거래시각
거래상태
```

이 번호는 나중에 **중복 전송과 재처리를 구분하는 핵심 값**이 된다.

---

## 6. 3단계: A은행 고객 원장에 출금한다

개념적으로는

```text
A은행 고객 계좌

500,000원
    │
    │ -100,000원
    ▼
400,000원
```

처럼 반영된다.
다만 실제 은행 시스템에서는 바로 확정하거나, 환원 가능한 중간 상태를 두는 등 구현 방식이 달라질 수 있다.
중요한 것은 이 처리가 **A은행 내부 원장 트랜잭션**이라는 점이다.

---

## 7. 대외계는 왜 필요할까?

은행 내부 Core System을 외부 기관과 직접 연결하지 않고 보통 **대외계**라는 경계 시스템을 둔다.

```text
A은행 Core
    │
    ▼
A은행 대외계
    │
    ▼
금융결제원
```

대외계에서는

```text
내부 데이터
      │
      ▼
외부 전문 포맷으로 변환
      │
      ▼
송수신
```

같은 역할을 수행한다.
또 Timeout, 응답 전문, 거래 추적 등 외부 기관 통신을 관리한다.

---

## 8. 은행끼리는 무엇을 주고받을까?

개념적으로는 금융 전문 메시지를 주고받는다.

```text
[HEADER]
[
송신기관
수신기관
거래구분
거래번호
전송시각


[BODY]

계좌
금액
적요
거래정보


[검증정보]

무결성 검증
인증 정보
```

즉 내부 서비스에서 사용하는 임의의 JSON을 그대로 보내는 것이 아니라 기관 간 합의된 전문 규격을 사용한다고 이해하면 된다.

---

## 9. 4단계: 금융결제원이 B은행으로 중계한다

```text
A은행
   │
   │ 지급지시
   ▼
금융결제원
   │
   │ 확인 / 중계
   ▼
B은행
```

금융결제원을 쉽게 표현하면
> **은행들이 서로 송금할 수 있도록 공통 소액결제 네트워크를 제공하는 곳**
이라고 볼 수 있다.

---

## 10. 5단계: B은행이 실제 입금한다

B은행은 지급지시를 받으면

```text
계좌가 존재하는가?

입금 가능한 상태인가?

거래 제한은 없는가?
```

등을 확인한다.
정상이면 B은행 자신의 원장을 변경한다.

```text
B은행 고객계좌

200,000원
    │
    │ +100,000원
    ▼
300,000원
```

그리고 처리 결과를 돌려보낸다.

```text
B은행
 ↓
금융결제원
 ↓
A은행
 ↓
고객
```

---

## 11. 실시간 송금 전체 흐름

```text
고객        A은행       금융결제원       B은행
 │            │             │             │
 │ 송금요청    │              │             │
 │───────────>│             │             │
 │            │ 인증/잔액확인  │             │
 │            │ 출금         │             │
 │            │────────────>│             │
 │            │             │ 지급지시     │
 │            │             │────────────>│
 │            │             │             │ 계좌검증
 │            │             │             │ 입금
 │            │             │<────────────│
 │            │<────────────│ 성공         │
 │<───────────│             │             │
 │ 송금 완료   │             │             │
```

사용자 입장에서는 여기에서 송금이 끝난 것처럼 보인다.

---

## 12. 그런데 은행끼리의 돈 문제는 아직 안 끝났다

사용자 원장은 이미 바뀌었다.

```text
A은행 고객

-100,000원


B은행 고객

+100,000원
```

그런데 B은행 입장에서는

```text
"A은행 고객 대신
 우리 고객에게 10만원을 반영했다."

        ↓

"A은행에서 받을 돈이 있다."
```

라는 은행 간 채권관계가 생긴다.
즉

```text
고객 송금 완료

≠

은행 간 최종 결제 완료
```

다.

---

## 13. Payment → Clearing → Settlement

타행송금은 이 세 단어로 이해하면 가장 쉽다.

```text
PAYMENT

고객의 송금
A은행 → 금융결제원 → B은행


        ↓


CLEARING

은행끼리
얼마를 받을지 / 줄지 계산


        ↓


SETTLEMENT

실제로 은행 사이의 돈을 이동해
채무를 최종적으로 끝냄
```

---

## 14. Clearing은 금융결제원이 담당한다

하루 동안 다음 거래가 발생했다고 해보자.

```text
A → B : 100억

B → A : 70억
```

모든 거래를 따로 정산할 필요 없이

```text
100억 - 70억

       ↓

A → B

30억
```

만 결제하면 결과가 같다.
이렇게 여러 거래를 상계해 은행별 순채권·순채무를 계산하는 것이 **청산(Clearing)** 이다.

---

## 15. 이제 한국은행이 등장한다

금융결제원이

```text
"A은행이 B은행에
30억원을 지급해야 합니다."
```

까지 계산했다면, 이제 실제 자금을 이동해야 한다.
이 **최종결제(Settlement)** 단계에서 한국은행이 핵심 역할을 한다.
은행들은 한국은행에 당좌예금계좌를 가지고 있다.

```text
                한국은행

      ┌────────────────────┐
      │ A은행 당좌예금        │
      │                    │
      │ B은행 당좌예금        │
      │                    │
      │ C은행 당좌예금        │
      └─────────┬──────────┘
                ▼
            BOK-Wire+
```

---

## 16. 왜 한국은행 계좌를 사용할까?

은행끼리 자신들의 DB에

```text
A은행 DB

"B은행에게 30억 지급"


B은행 DB

"A은행에서 30억 수취"
```

라고 기록하는 것만으로는 최종 결제가 아니다.
은행들이 모두 신뢰할 수 있는 **중앙은행 돈(Central Bank Money)** 을 이용한다.

```text
A은행 한은계좌

100억
 │
 │ -30억
 ▼
70억


B은행 한은계좌

200억
 │
 │ +30억
 ▼
230억
```

이 단계까지 가면 은행 사이의 채무가 최종적으로 끝난다.

---

## 17. BOK-Wire+는 무엇일까?

BOK-Wire+는 **한은금융망**, 한국은행이 운영하는 금융기관 간 결제 인프라다.

```text
은행 ───-─┐
증권사 ──-─┤
기타기관 --─┼──▶ BOK-Wire+
          │
          ▼
    한국은행 당좌예금
```

여기서 중요한 구분은

```text
개인의 타행송금 전문

→ 금융결제원이 중계
```

하고

```text
그 결과 발생한
은행 간 최종 자금결제

→ 한국은행 BOK-Wire+
```

에서 처리된다는 점이다.

---

## 18. 왜 고객은 바로 입금된 돈을 볼 수 있을까?

모든 10만 원 송금마다

```text
A은행 고객 출금

       ↓

한국은행 최종결제

       ↓

B은행 고객 입금
```

순서로 끝까지 기다리는 방식으로만 처리되는 것은 아니다.
논리적으로는

```text
고객 지급 처리
     │
     ▼
빠르게 반영


은행 간 결제
     │
     ▼
별도 단계에서 최종 처리
```

되는 구조가 존재한다.
그래서 고객은 타행송금 결과를 빠르게 확인할 수 있다.

---

## 19. 송금 도중 장애가 나면?

타행송금은 여러 시스템이 연결된 전형적인 분산 시스템이다.

```text
A은행

금융결제원

B은행
```

가장 까다로운 상황은 이런 경우다.

```text
B은행

입금 완료
   │
   ▼
성공 응답
   │
   X
네트워크 장애


A은행

응답 못 받음
```

A은행은

```text
실패했나?

성공했는데
응답만 없어졌나?
```

를 알 수 없다.

---

## 20. Timeout은 실패가 아니다

금융 시스템에서는 매우 중요한 원칙이다.

```text
Timeout

≠

거래 실패
```

Timeout이 의미하는 것은

```text
정해진 시간 안에
결과를 받지 못했다.
```

는 것뿐이다.
따라서

```text
Timeout
 ↓
무조건 다시 송금
```

하면 중복 입금 위험이 있다.

---

## 21. 그래서 멱등성과 상태 머신이 필요하다

같은 거래가 다시 들어와도 돈은 한 번만 움직여야 한다.

```text
TX_ID = ABC123


첫 요청

ABC123
→ 입금 성공


응답 유실


재요청

ABC123
→ 이미 처리한 거래
→ 추가 입금 X
→ 기존 결과 반환
```

이게 **멱등성(Idempotency)** 이다.
그리고 전체 거래 상태도 추적해야 한다.

```text
INIT
 │
 ▼
VALIDATED
 │
 ▼
DEBITED
 │
 ▼
SENT
 │
 ▼
REMOTE_ACCEPTED
 │
 ▼
CONFIRMED
```

실패하면

```text
DEBITED
 │
 ├─ 전송 실패 → RETRY
 │
 └─ 상대 거절 → REVERSAL
```

같은 보상 흐름이 필요하다.

---

## 22. 실시간 처리 뒤에는 대사가 필요하다

A은행, 금융결제원, B은행의 거래 기록이 실제로 같은지 확인해야 한다.

```text
A은행 기록
     │
     ├────────┐
     ▼        ▼
금융결제원   B은행 기록
     │        │
     └───┬────┘
         ▼
   Reconciliation
         │
     ┌───┴───┐
     ▼       ▼
    일치    불일치
             │
             ▼
          조사/보정
```

거래번호, 금액, 처리상태 등을 기준으로 맞는지 확인한다.

---

## 23. 전체 아키텍처

전체를 한 장으로 보면 다음과 같다.

```text
                         고객
                          │
                          ▼
                    A은행 채널계
                          │
                  인증 / 한도 / FDS
                          │
                          ▼
                    A은행 이체시스템
                          │
               ┌──────────┴──────────┐
               ▼                     ▼
```

## 24. 금융에는 또 어떤 인프라 기관이 있을까?

타행송금에 직접 핵심적으로 등장하는 것은 **금융결제원과 한국은행**이지만 금융 전체에는 다른 기관도 있다.

| 기관 | 핵심 역할 |
| --- | --- |
| **금융결제원** | 은행 간 소액지급망, 오픈뱅킹, 지급지시 중계·청산 |
| **한국은행** | BOK-Wire+, 금융기관 간 최종결제, 결제유동성 |
| **한국거래소** | 주식·채권·파생상품 시장 운영과 매매 체결 |
| **한국예탁결제원** | 증권 보관·전자등록·증권결제 |
| **한국신용정보원** | 금융권 신용정보·마이데이터 관련 데이터 인프라 |
| **금융보안원** | 금융권 보안관제·침해대응·보안 지원 |
| **예금보험공사** | 금융회사 부실 시 예금자 보호 |

이 기관들이 모두 타행송금에 들어가는 것은 아니다.

```text
계좌이체
→ 금융결제원 + 한국은행


주식 거래
→ 한국거래소 + 한국예탁결제원


신용 / 마이데이터
→ 한국신용정보원


금융 보안
→ 금융보안원


금융회사 부실
→ 예금보험공사
```

처럼 금융 인프라의 서로 다른 영역을 담당한다고 보면 된다.

## 정리

타행송금의 핵심 흐름은 결국 다음 세 단계다.

```text
PAYMENT

고객
 ↓
A은행
 ↓
금융결제원
 ↓
B은행
 ↓
수취인


       ▼


CLEARING

금융결제원
 ↓
은행별 받을 돈 / 줄 돈 계산


       ▼


SETTLEMENT

한국은행
 ↓
BOK-Wire+
 ↓
은행들의 한국은행 계좌
 ↓
최종 결제
```

그리고 백엔드 관점에서는 이 안에

```text
Message Routing

Customer Ledger

Clearing

Settlement

Idempotency

State Machine

Reconciliation
```

이 함께 들어 있다.
따라서 **다른 은행으로 송금한다는 것은 단순한 API 호출이 아니라, 은행의 원장 시스템과 금융결제원의 소액결제망, 한국은행의 최종결제 인프라가 연결된 하나의 거대한 분산 금융 시스템을 이용하는 것**이라고 이해하면 된다.
