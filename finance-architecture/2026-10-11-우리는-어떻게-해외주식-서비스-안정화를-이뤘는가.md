## 토스증권은 해외주식 서비스를 어떻게 안정화했을까?

토스증권의 해외주식 서비스는 사용자가 국내에서 주문을 넣으면 해외 **브로커(Broker)** 를 거쳐 미국 거래소에서 실제 매매가 처리되는 구조다.
브로커는 주식 매매를 현지에서 처리를 해주는 역할을 하는 회사이다.

```text
사용자
  │
  │ 매수 / 매도
  ▼
토스증권
  │
  ▼
해외 Broker
  │
  ▼
미국 거래소
```

토스증권은 해외주식의 주문, 자산, 권리, 종목정보, 환전 등 거래와 정보를 원장에 기록하고 있다. 브로커와는 주로 FIX를 사용하고 일부 요청은 HTTP를 사용하며, 결과는 Kafka나 SQS 같은 Queue를 통해 비동기로 처리한다.

---

## 1. 해외주식 시스템에서 외부 Broker는 핵심 의존성이다

브로커와 통신은 HTTP, FIX 두 가지 프로토콜을 사용한다.
메인으로는 FIX 프로토콜을 사용하고 있고, 브로커 요구사항에 따라 HTTP를 부분적으로 사용하여 요청을 보낸다.

**FIX 프로토콜은 무엇이고 HTTP와 어떻게 다를까?**
**FIX(Financial Information eXchange)**는 증권사, 브로커, 거래소가 주문과 체결 정보를 주고받기 위해 만든 금융 거래용 메시지 표준이다.
쉽게 말해 HTTP가 범용적인 웹 통신 규칙이라면, FIX는 **주식 주문 업무에 특화된 공용 언어**다.

### FIX 메시지 예시

10주의 애플 주식을 매수하는 주문은 다음과 같은 `Tag=Value` 형식으로 표현할 수 있다.

```text
35=D          → 신규 주문
11=ORDER-123  → 주문 ID
55=AAPL       → 종목
54=1          → 매수
38=10         → 수량
40=2          → 지정가 주문
44=200        → 주문 가격
```

브로커는 주문 접수·일부 체결·완전 체결·취소 같은 상태를 `Execution Report` 메시지로 계속 전달한다.

```text
증권사                       Broker
  │                            │
  │── 신규 주문(FIX) ─────────▶│
  │◀── 주문 접수 ──────────────│
  │◀── 일부 체결 ──────────────│
  │◀── 완전 체결 ──────────────│
```

FIX 연결은 일반적으로 TCP 기반의 세션을 계속 유지한다. 세션에는 다음과 같은 기능도 포함된다.
- Heartbeat를 통한 연결 상태 확인
- 메시지 순서를 보장하는 Sequence Number
- 누락된 메시지를 다시 요청하는 Resend
- 연결이 끊어진 뒤 메시지를 복구하는 세션 관리

### HTTP와의 차이

| 구분 | FIX | HTTP |
| --- | --- | --- |
| 목적 | 금융 주문·체결 통신 | 범용 웹 통신 |
| 연결 방식 | 연결을 장시간 유지하는 세션 방식 | 일반적으로 요청·응답 방식 |
| 메시지 형식 | 금융 업무가 표준화된 `Tag=Value` | JSON, XML 등 자유로운 형식 |
| 통신 방향 | 양방향으로 메시지를 지속 전송 | 요청에 대한 응답을 반환 |
| 메시지 순서 | Sequence Number로 관리 | 애플리케이션이 별도로 관리 |
| 장애 복구 | 누락 메시지 재전송 기능 제공 | 별도의 재시도·복구 로직 필요 |
| 주요 용도 | 주문, 정정, 취소, 체결 결과 | 조회, 설정, 계좌·종목 정보 등 |

### 증권 거래에서 FIX를 사용하는 이유

주문을 보낸 직후 결과가 한 번에 결정되지 않을 수 있다. 주문이 접수된 뒤 일부만 체결되고, 나중에 나머지가 체결되거나 취소될 수도 있다.
FIX는 이러한 상태 변화를 하나의 세션에서 지속적으로 전달하고, 메시지의 순서와 누락 여부까지 관리한다. 따라서 실시간성과 신뢰성이 중요한 주문 처리에 적합하다.
반면 HTTP는 구현과 연동이 간단하므로 브로커가 제공하는 조회 API나 설정 변경처럼 일반적인 요청에 주로 사용한다.
즉, 본문의 의미는 **실시간 주문·체결처럼 금융 거래의 신뢰성이 중요한 통신에는 FIX를 사용하고, 일부 범용적인 요청에는 HTTP를 사용한다**는 뜻이다. FIX가 언제나 HTTP보다 빠르다는 의미는 아니며, 핵심 차이는 속도보다 금융 거래에 특화된 메시지와 세션 관리 기능에 있다.

먼저 사용자가 주문을 넣었다고 해보자.

```text
User
 │
 ▼
토스증권 주문 시스템
 │
 │ FIX / HTTP
 ▼
Broker
 │
 ▼
Exchange
```

Broker가 느려지면 주문 처리도 느려진다.

```text
Broker Response

100ms
300ms
1s
3s
5s...
```

브로커 응답이 계속 밀리면서 주문이 대기하기 시작했고 일부 요청은 5초 이상 걸리는 문제가 발생했다.

## 2. 왜 이런 문제가 갑자기 커졌을까?

두 가지 이유가 컸다.
첫 번째는 **미국 정규장 시작 시점의 트래픽 집중**이다.
> 원문 이미지: [원문에서 보기](https://toss.tech/article/28738)
토스증권 글에서는 정규장과 비정규장의 TPS 차이가 **20배 이상**이라고 설명한다.
두 번째는 사용자 증가다.
서비스 초기와 비교하면 해외주식 주문 요청량 자체가 **30배 이상** 증가했다.
즉

```text
사용자 증가
    │
    ▼
주문량 증가
    +
정규장 순간 트래픽
    │
    ▼
Broker 처리량 압박
    │
    ▼
응답 지연
    │
    ▼
주문 적체
```

구조가 됐다.

---

## 3. 특히 예약 주문이 문제였다

해외주식에는 예약 주문이 있다.
정규장이 열리기 전에 주문을 받아두고 실제 장이 시작되면 브로커로 전달한다.

```text
장 시작 전

예약 주문
예약 주문
예약 주문
예약 주문
...

        │
        ▼

정규장 시작

        │
        ▼

Broker로 전송
```

정규장 시작 뒤 **약 100만 건 이상**의 예약 주문을 한 번에 Broker로 보내면 외부 시스템에 큰 부하를 줄 수 있었다.

## 4. 첫 번째 해결: Broker가 감당할 만큼만 보낸다

필요했던 것은 단순하다.

```text
주문이 100만 건 있다고 해서

100만 건을 동시에 보내지 않는다.
```

Broker가 허용할 수 있는 TPS 수준으로 주문을 제한한다.

```text
Orders
████████████████████████

        │
        ▼
   Rate Limiter

        │
        ▼

Broker

초당 N건
```

이를 위해 **Resilience4j RateLimiter**를 사용했다.

---

## 5. RateLimiter 동작

예를 들어 TPS를 1,000으로 설정했다고 하자.

```text
limitRefreshPeriod = 1초

limitForPeriod = 1000
```

1초 동안 최대 1,000개의 Permit을 사용할 수 있다.

```text
1초 Window

Permit

1
2
3
...
1000
```

1001번째 요청은 바로 통과할 수 없다.

```text
Order #1001
     │
     ▼
RateLimiter
     │
     │ Permit 없음
     ▼
대기 / 실패
```

다음 Refresh 시점에 Permit이 다시 채워진다.

```text
0s

1000 permits

     ↓ 모두 사용

1s

1000 permits 재충전
```

이를 통해 Application 자체의 처리량이 아무리 높아도 Broker로 전달되는 TPS를 일정 수준으로 제한한다.

## 6. Batch 실행할 때 TPS를 결정한다

```kotlin
object RateLimiterCreator {

    // RateLimiter가 요청 허가(Permission)를 기다릴 최대 시간
    // 별도로 지정하지 않으면 5초 사용
    private val DEFAULT_TIMEOUT_DURATION = Duration.ofSeconds(5)

    /**
     * Resilience4j RateLimiter를 생성한다.
     *
     * @param limitRefreshPeriod 허용 횟수가 초기화되는 주기
     * @param limitForPeriod 한 주기 동안 허용할 최대 요청 수
     * @param name RateLimiter 식별 이름
     * @param timeoutDuration 요청 허가를 기다릴 최대 시간
     */
    fun of(
        limitRefreshPeriod: Duration,
        limitForPeriod: Int,
        name: String,
        timeoutDuration: Duration = DEFAULT_TIMEOUT_DURATION,
    ): RateLimiter {

        // RateLimiter 동작 설정 생성
        val config = RateLimiterConfig.custom()

            // 요청 허용 횟수를 갱신하는 주기
            // ex) 1초라면 매 1초마다 limitForPeriod만큼 다시 허용
            .limitRefreshPeriod(limitRefreshPeriod)

            // 한 주기(limitRefreshPeriod) 동안 허용할 최대 요청 수
            .limitForPeriod(limitForPeriod)

            // 허용 가능한 요청 수가 모두 소진됐을 때
            // 다음 요청이 Permission을 기다릴 최대 시간
            .timeoutDuration(timeoutDuration)

            .build()

        // 위 설정을 기본 설정으로 사용하는 RateLimiter Registry 생성
        val registry = RateLimiterRegistry.of(config)

        // Registry에서 name을 식별자로 RateLimiter 생성(또는 조회)
        val rateLimiter = registry.rateLimiter(name)

        return rateLimiter
    }
}
```

설정값들을 yml 파일로 관리할 수 있지만, 배치잡 파라미터로 TPS를 제어하고 배치를 실행할 때 TPS를 결정하고 싶어 코드를 관리하는 선택을 했다.
아래 이미지에 보이듯이 간단하게 파라미터만 넘기면 배치에서 브로커로 요청하는 TPS를 결정할 수 있다.
> 원문 이미지: [원문에서 보기](https://toss.tech/article/28738)

```text
Batch 실행

TPS = 500

     ↓

RateLimiter
500 request/sec
```

다른 상황에서는

```text
Batch 실행

TPS = 1000

     ↓

RateLimiter
1000 request/sec
```

처럼 바꿀 수 있다.
즉 Broker 상황에 따라 운영자가 처리량을 조절하기 쉽게 만들었다.

## 7. 하지만 Rate Limit만으로 충분하지 않다

RateLimiter가 해결하는 것은

```text
우리가 Broker에게
너무 많이 보내는 문제
```

다.
하지만 Broker 자체가 장애 나면?

```text
TPS 제한 O

그런데

Broker
   X
```

아무리 천천히 보내도 주문은 실패한다.
따라서 두 번째 문제가 남는다.
> **Broker가 이상하다는 것을 어떻게 빠르게 감지하고 다른 Broker로 전환할까?**

## 8. 사람이 새벽마다 보고 있을 수는 없다

미국 장은 한국 시간으로 밤과 새벽에 운영된다.

```text
한국

밤 / 새벽

       ↓

미국 시장 운영
```

Broker 장애를 사람이 직접 발견하고 전환한다면

```text
장애 발생
   │
   ▼
사람이 알림 확인
   │
   ▼
그래프 확인
   │
   ▼
장애 판단
   │
   ▼
Broker 전환
```

까지 시간이 걸린다.
주문이 계속 들어오는 금융 서비스에서는 이 시간이 곧 장애 규모가 된다.
그래서 **자동 이상 감지 + Broker Failover** 시스템을 만들었다.

## 10. 예를 들어 Broker API 실패가 증가한다

원문의 Grafana Rule 예시는

```text
최근 1분간 실패 API 개수 계산
```

후

```text

```

을 Alert 조건으로 사용했다.
하지만 순간적으로 한 번 튄 값만 보고 장애라고 판단하면 위험하다.
그래서

```text
Evaluation Interval

+

```

를 사용한다.

## 11. Evaluation Interval과 Pending Period

예를 들어

```text
Evaluation Interval = 30초

Pending Period = 3분
```

이라고 하자.
Grafana는 30초마다 조건을 확인한다.

```text
0s
30s
60s
90s
...
```

Error Count가 임계치를 넘어도 바로 Alert하지 않는다.

```text
Error > 100

       │
       ▼

3분 동안 계속 유지?
```

를 확인한다.

```text
잠깐 Spike

→ Alert X


3분 이상 지속

→ Alert O
```

일시적인 Noise와 실제 장애를 구분하기 위한 장치다.

## 12. 장애 상태를 Event로 만든다

이상 감지 시스템은 Broker 상태를 세 단계로 표현했다.

```kotlin
enum class SystemStatus {
    HEALTHY,    // 시스템이 정상
    CAUTION,    // 시스템에 문제가 있을 수도 있음. 알아서 판단
    CRITICAL    // 시스템 down
}
```

그리고 판단 결과를 Kafka Event로 발행한다.

```kotlin
@Component
class BrokerFailOverConsumer(
    private val brokerFailoverService: BrokerFailoverService,
    private val slackSender: SlackSender,
) {
    private val log = KotlinLogging.logger { }

    @KafkaListener(
        topics = ["topicName"],
        clientIdPrefix = "appName",
        containerFactory = "falioverContainerFactory"
    )
    fun consume(record: ConsumerRecord<String, String>) {
        val json = record.value()
        log.info { "system-status-event consume: $json" }

        val message = JsonUtil.fromJson(record.value(), SystemStatusRecord::class.java)

        when (message.status) {
            SystemStatus.CRITICAL -> {
                slackSender.sendCriticalSlackMessage(message)
                brokerFailoverService.failover()
            }
            SystemStatus.CAUTION -> {
                log.info { "브로커 상태 알림 수신: BrokerType=${message.type}, status=${message.status}" }
            }
            SystemStatus.HEALTHY -> {
                when (message.prevStatus) {
                    SystemStatus.CRITICAL -> slackSender.sendReturnHealthySlackMessage(message, message.prevStatus!!)
                    else -> log.info { "브로커 상태 알림 수신: BrokerType=${message.type}, status=${message.status}" }
                }
            }
        }
    }
```

```text
Grafana
   │
   ▼
Webhook
   │
   ▼
Anomaly System
   │
   ▼
Status 판단
   │
   ▼
Kafka Event
```

## 13. 왜 Kafka Event로 만들었을까?

장애 상태를 직접 모든 서비스에 API로 전달하면 시스템 간 결합도가 커진다.

```text
Detector
 ├─ Service A 호출
 ├─ Service B 호출
 └─ Service C 호출
```

Event로 만들면 다르다.

```text
               Kafka

Detector ───▶ System Status Topic
                    │
          ┌─────────┼─────────┐
          ▼         ▼         ▼
      주문 시스템   알림    다른 시스템
```

각 시스템은 동일한 상태 Event를 받아 자기 방식대로 대응할 수 있다.

```text
CRITICAL

주문 시스템
→ Broker Failover


알림 시스템
→ Slack


다른 시스템
→ 자체 대응
```

원문에서도 이상 감지 결과를 Kafka로 발행하고 여러 시스템이 이를 구독하는 구조를 사용했다.

---

## 14. Broker Failover

Main Broker가 정상일 때는

```text
Order
  │
  ▼
Main Broker
  │
  ▼
Exchange
```

로 처리한다.
상태가 `CRITICAL`이 되면 Kafka Consumer가 Event를 받는다.

```text
SystemStatus = CRITICAL

         │
         ▼
Kafka Consumer

         │
         ▼
brokerFailoverService.failover()
```

이후 주문 경로를 Sub Broker로 변경한다.

```text
Before

Order
  │
  ▼
Main Broker


After

Order
  │
  ▼
Sub Broker
```

---

## 15. 정상화도 감지한다

장애만 알리는 것이 아니다.

```text
Previous

CRITICAL


Current

HEALTHY
```

라면

```text
"Broker 정상화"
```

알림도 보낸다.
운영자는

```text
장애 발생

→ 전환

→ 복구 확인
```

의 전체 상태 변화를 추적할 수 있다.

## 17. 그런데 서비스가 커지면서 DB도 문제가 됐다

Broker 문제를 해결했다고 끝난 것이 아니다.
해외주식 사용자가 늘면서 증권 원장의 데이터도 크게 증가했다.
그 결과 단순 조회 API도

```text
500ms+

일부

1000ms+
```

까지 느려지는 경우가 증가했다.

## 18. 원장 DB에서 복잡한 조회가 병목이 됐다

증권 원장은 정규화된 여러 테이블로 구성될 수 있다.
예를 들어 사용자의 자산 정보를 조회할 때

```text
Account

+

Order

+

Balance

+

Asset

+

Product
```

등 여러 정보를 조합해야 할 수 있다.

```text
Table A
   │
Table B
   ├── JOIN / Query
Table C
   │
Table D
```

데이터가 작을 때는 괜찮다.
하지만 데이터가 커지면 비효율적인 Query가 성능 병목으로 나타난다.
그래서 **조회 목적에 맞게 여러 데이터를 Aggregate한 별도 저장소**를 고려했다.

---

## 19. Oracle Partition Key 딜레마

원본 Oracle DB에도 Partition이 필요했다.
그런데 Partition Key를 무엇으로 할지가 문제였다.
개발팀 관점:
모든 고객 요청은 계좌번호 조건을 찍고 조회하는 특성이 있기 때문에 계좌번호를 파티션 키로 잡고 싶었다.

```text
대부분 요청

WHERE account_no = ?

        ↓

Account Number를
Partition Key로 하고 싶음
```

DBA 관점:
DBA 입장에서는 성능 향상도 중요하지만 디스크 저장도 같이 고려한다면 날짜를 파티션 키로 잡는 게 유리하기 때문에 날짜 단위로 파티션 키를 잡는 것을 권장했다.
다른 DB에 비해 Oracle DB는 상대적으로 확장에 불리하기 때문에 디스크 관리도 같이 고민해야 헀다.

```text
오래된 데이터

조회 빈도 ↓

압축 가능

        ↓

Date를 Partition Key로
```

였다.

---

## 20. 두 요구사항 모두 타당했다

개발팀은 조회 성능이 중요했다.

```text
Account 단위 조회

→ Account 기준 Partition
```

DBA는 Storage 운영이 중요했다.

```text
Date 기준 Partition

→ 오래된 Partition 압축

→ Disk 절감
```

하나의 RDB Partition Key로 두 요구사항을 동시에 완벽하게 해결하기 어려웠다.
그래서 역할을 분리했다.

## 21. 원본은 Oracle, 조회는 MongoDB

최종적으로

```text
Oracle

→ 원본 원장 데이터

→ Date Partition

→ 저장/운영 효율


MongoDB

→ 비즈니스 조회 데이터

→ Account 중심 조회

→ 확장성
```

구조를 선택했다.

## 22. MongoDB를 선택한 이유

MongoDB를 후보군에 넣은 이유는 Oracle과 같은 RDB는 파티션 키가 없으면 모든 파티션을 검색하기 때문에 파티션 키가 필요하지만, **MongoDB는 샤드 키가 없어도 어느 정도 준수한 성능 보장이 되기 때문이다.**
MongoDB는 샤드 키가 없이 쿼리를 날려도 모든 노드로 브로드캐스트 요청을 보내 해당 쿼리를 수행하고 mongos(라우터)에서 결과를 조합해서 변환해줘요. **즉, 모든 노드에서 병렬처리를 하기 때문에 적절한 인덱스만 구성이 되면 어느 정도 준수한 성능****이 보장이 돼요.**

**Target Query vs Scatter-Gather Query**
`mongos`는 MongoDB Sharding 환경에서 요청을 적절한 Shard로 전달하는 **Query Router**다.
예를 들어 Shard Key가 `date`이고 데이터가 다음과 같이 분산되어 있다고 하자.

```text
Shard A → 1~4월 데이터
Shard B → 5~8월 데이터
Shard C → 9~12월 데이터
```

Query에 Shard Key가 포함되면 `mongos`는 데이터가 있는 Shard를 알 수 있다.

```text
db.orders.find({ date: "2026-09-26" })
```

따라서 9월 데이터를 가진 Shard C에만 요청을 보낸다. 이를 **Targeted Query**라고 한다.
반면 Query에 Shard Key가 없다면 데이터가 어느 Shard에 있는지 알 수 없다.

```text
db.orders.find({ accountId: 123 })
```

이 경우 `mongos`는 모든 Shard에 요청을 보내고 결과를 병합한다.

```text
mongos
 ├─ Shard A에서 accountId=123 검색
 ├─ Shard B에서 accountId=123 검색
 └─ Shard C에서 accountId=123 검색
          ↓
      결과 병합
```

이를 **Scatter-Gather Query**라고 한다.
각 Shard가 병렬로 검색하고 `accountId`에 적절한 Index가 있다면 필요한 조회 성능을 확보할 수 있다. 다만 모든 Shard의 CPU와 네트워크를 사용하고, 가장 느린 Shard가 전체 응답 시간을 결정할 수 있으므로 Targeted Query보다 비용이 크다.
즉, MongoDB는 **Shard Key 없이도 유연하게 조회할 수 있지만, 그 대가로 여러 Shard를 검색하는 비용을 부담한다.**

```text
Client
  │
  ▼
mongos
  │
  ├──▶ Shard A
  ├──▶ Shard B
  └──▶ Shard C
          │
          ▼
     결과 병합
```

Targeted Query보다는 비용이 크지만, 여러 Shard에서 병렬로 처리할 수 있고 적절한 Index가 있다면 필요한 조회 성능을 확보할 수 있다고 판단했다.

---

## 23. MongoDB는 Aggregate된 조회 모델

원장 여러 테이블을 매번 조합하는 대신 조회 목적의 데이터를 MongoDB에 만들어둔다.

```text
Oracle

Account
Order
Asset
Balance
...

      │
      ▼
  Aggregate
      │
      ▼
MongoDB Document
```

그러면 API에서는 복잡한 Join 대신 조회 모델을 바로 읽을 수 있다.

```text
API
 │
 ▼
MongoDB
 │
 ▼
Account Aggregate
```

## 24. 기존 데이터를 어떻게 옮겼을까?

문제였던 Oracle Query 자체가 느렸기 때문에 Oracle에서 직접 대량 Migration을 하면 운영 DB에 부담을 줄 수 있었다.
그래서 이미 사내 Data Warehouse에서 사용하던 Hadoop 기반 **Impala**를 이용했다.

```text
Oracle Data
    │
    ▼
Hadoop / DW
    │
    ▼
Impala
    │
    │ 병렬 조회
    ▼
Migration
    │
    ▼
MongoDB
```

> 원문 이미지: [원문에서 보기](https://toss.tech/article/28738)
별도 대규모 Migration 환경을 새로 만들기보다 이미 존재하는 데이터 인프라를 활용했다.

## 25. Migration 이후에는 Kafka로 동기화

한 번 데이터를 복사했다고 끝나는 것이 아니다.
그 이후 Oracle에서 계속 거래가 발생한다.

```text
Migration 완료

     │

새 주문
새 체결
새 자산 변화
...
```

MongoDB에도 계속 반영해야 한다.
이미 관련 Kafka Event가 존재하고 있었기 때문에 이를 활용했다.

```text
Oracle / Business Event
        │
        ▼
       Kafka
        │
        ▼
   Consumer
        │
        ▼
     MongoDB
```

> 원문 이미지: [원문에서 보기](https://toss.tech/article/28738)
이렇게 원천 데이터와 MongoDB 사이의 지연을 최소화했다.

## 정리

토스증권 해외주식 안정화 사례는 하나의 거대한 시스템을 새로 만든 이야기가 아니다.
문제마다 이미 잘 만들어진 도구를 적절하게 조합했다.

```text
트래픽 문제

→ Resilience4j RateLimiter


장애 감지

→ Grafana / Kibana


장애 전파

→ Kafka Event


Broker 장애

→ Failover


대규모 조회

→ MongoDB


초기 Migration

→ Impala


실시간 동기화

→ Kafka
```

핵심은 **오버엔지니어링하지 않았다는 점**이다.

```text
문제 발생
   │
   ▼
병목의 본질 확인
   │
   ▼
이미 검증된 도구 확인
   │
   ▼
필요한 만큼만 구현
   │
   ▼
운영 자동화
```

특히 해외주식처럼 외부 Broker에 강하게 의존하는 시스템에서는

```text
외부 시스템이
절대 장애 나지 않는다
```

를 전제로 설계할 수 없다.
대신

```text
얼마나 보낼 것인가?

언제 장애라고 판단할 것인가?

장애가 나면 어디로 우회할 것인가?

데이터가 커지면 어떤 저장소로 역할을 분리할 것인가?
```

를 설계해야 한다.
결국 안정적인 금융 서비스는 **장애를 없애는 시스템이 아니라, 장애가 발생해도 영향 범위를 제한하고 빠르게 다른 경로로 전환할 수 있는 시스템**에 가깝다.
