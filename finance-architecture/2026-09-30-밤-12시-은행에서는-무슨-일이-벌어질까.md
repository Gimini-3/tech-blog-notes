# 밤 12시 은행에서는 무슨 일이 벌어질까?

- 읽은 날짜: 2026-09-30
- 회사/작성 주체:
- 노션 정리: [원본 페이지](https://app.notion.com/p/859a987f6c40838ea5f601487de8250a)

---

은행 앱을 사용하다 보면 가끔 이런 안내를 볼 수 있다.

```text
시스템 점검으로 인해
23:50 ~ 00:10 동안
일부 서비스 이용이 제한됩니다.
```

왜 하필 자정 근처일까?
은행 시스템에서는 하루 동안 수많은 거래가 발생한다.

```text
입금
출금
이체
대출
이자
수수료
자동이체
카드대금
...
```

그런데 이 거래들을 단순히 계속 쌓아두기만 할 수는 없다.
하루가 끝나면

```text
오늘 거래는 모두 정상 처리됐는가?

오늘 발생한 이자는 얼마인가?

예약된 자동이체가 있는가?

회계 장부와 실제 거래가 맞는가?

내일부터 적용해야 할 상태는 무엇인가?
```

를 정리하고 **다음 영업일을 준비해야 한다.**
이 과정을 보통 **EOD(End Of Day)** 라고 한다.

---

## 1. EOD는 단순히 "밤 12시 작업"이 아니다

먼저 하나를 구분해야 한다.

```text
현실의 시간

2026-09-22 23:59
        ↓
2026-09-23 00:00
```

와

```text
은행 시스템의
Business Date
```

는 반드시 같은 것은 아니다.
은행의 코어뱅킹 시스템은 별도의 **영업일자(Business Date)** 를 관리할 수 있다.

```text
실제 시간

09/23 00:05


은행 시스템

Business Date
09/22
```

아직 9월 22일 EOD가 끝나지 않았다면 시스템은 이전 영업일을 처리하고 있을 수 있다.
Oracle FLEXCUBE 같은 코어뱅킹 시스템도 EOD가 끝난 뒤 시스템 날짜를 다음 영업일로 변경하고, 그 날짜를 각종 자동 처리와 거래의 기준으로 사용하도록 설계되어 있다.
따라서 정확하게는
> **밤 12시가 돼서 EOD를 하는 것이 아니라, 영업일을 마감하고 다음 영업일로 넘어가기 위해 EOD를 수행한다.**
라고 이해하면 된다.

---

## 2. 실시간 처리와 Batch 처리

은행의 모든 작업을 같은 방식으로 처리하는 것은 아니다.
크게 보면 두 종류가 있다.

```text
          은행 업무

      ┌──────┴──────┐
      ▼             ▼

  Online 처리     Batch 처리

   즉시 처리       모아서 처리
```

#### Online

사용자가 요청하면 즉시 처리한다.

```text
사용자
  │
  │ 10만원 이체
  ▼
은행 서버
  │
  ▼
계좌 반영
  │
  ▼
응답
```

이체나 잔액조회처럼 사용자 응답 시간이 중요한 작업이다.

---

#### Batch

실시간으로 처리할 필요가 없는 많은 작업을 모아서 처리한다.

```text
하루 동안 데이터 적재
        │
        │
        ▼
   영업 종료
        │
        ▼
 ┌───────────────┐
 │ Batch Process │
 └───────────────┘
        │
        ├─ 이자 계산
        ├─ 수수료 처리
        ├─ 상태 갱신
        └─ 보고서 생성
```

이런 작업이 EOD의 중요한 구성 요소다.

---

## 3. 왜 굳이 Batch로 처리할까?

예를 들어 은행 고객이 천만 명이고 매일 모든 계좌에 대해 계산해야 하는 작업이 있다고 해보자.
거래가 발생할 때마다

```text
거래
 ↓
이자 계산
 ↓
수수료 계산
 ↓
통계 계산
 ↓
회계 집계
 ↓
보고서 반영
```

을 전부 실시간으로 수행한다면 온라인 거래가 지나치게 무거워진다.
대신

```text
낮

사용자 거래에 집중
──────────────▶


밤 / 영업일 전환

대량 후처리
──────────────▶
```

처럼 분리할 수 있다.
그래서 전통적인 금융 시스템에서는 Batch가 매우 중요했다.

---

## 4. EOD가 시작되기 전에 거래를 마감한다

EOD를 하는 중에도 오늘 날짜의 거래가 계속 들어오면 문제가 생긴다.

```text
EOD 계산 중

Account A
Balance = ?

        ↑

동시에 새로운 거래 발생
```

어디까지가 오늘 거래인지 애매해진다.
그래서 먼저 **거래 입력을 마감하는 단계**가 필요하다.
Oracle FLEXCUBE에서는 이를
**EOTI(End Of Transaction Input)**
라고 부른다.

```text
Transaction Input

입금
출금
이체
대출 거래
...

       │

       ▼

     EOTI

"오늘 거래 입력 종료"
```

EOTI는 해당 영업일의 거래 입력과 승인이 끝난 뒤 EOD 단계로 넘어가는 첫 번째 경계다.

---

## 5. 그다음 자동 회계 처리도 끝낸다

거래 입력이 끝났다고 모든 작업이 끝난 것은 아니다.
시스템이 자동으로 만들어야 할 회계 처리도 있다.

```text
거래 입력 종료
     │
     ▼
자동 처리
     │
     ├─ 이자
     ├─ 수수료
     ├─ 만기 처리
     └─ 기타 회계 Entry
```

이 작업까지 끝나면 **EOFI(End Of Financial Input)** 단계로 이동한다.

```text
EOTI
  │
  ▼
자동 회계 Batch
  │
  ▼
EOFI

"오늘 회계 Entry 종료"
```

EOFI 이후에는 해당 영업일에 더 이상 회계 Entry를 추가하지 않는 것이 핵심이다. 이 시점이면 당일 최종 잔액을 기준으로 재무 보고서 같은 작업을 수행할 수 있다.

---

## 6. 그러면 EOD에서는 무엇을 할까?

은행마다 시스템과 상품이 다르기 때문에 EOD Job도 다르다.
하지만 코어뱅킹 시스템에서는 일반적으로 이런 종류의 처리를 볼 수 있다.

```text
                EOD
                 │
        ┌────────┼────────┐
        │        │        │
        ▼        ▼        ▼

      이자     상품 처리    회계
      계산     /상태 변경   집계

        │        │        │
        └────────┼────────┘
                 ▼
             검증/보고
```

대표적인 예를 하나씩 보자.

---

## 7. 이자 계산

예금이나 대출에서는 시간이 지나면 이자가 발생한다.
예를 들어 연 3.65% 예금이라고 단순화해보자.

```text
잔액 10,000,000원

오늘 하루가 지남
       │
       ▼
하루치 이자 발생
```

이런 값을 매일 누적하는 것을 **Interest Accrual**이라고 한다.

```text
Day 1
이자 발생

Day 2
이자 발생

Day 3
이자 발생

   ...

       │
       ▼

월말 / 지급일
실제 이자 지급
```

여기서 중요한 차이가 있다.

#### Accrual

```text
이자가 발생했다고
회계적으로 인식
```

#### Liquidation

```text
실제 고객 계좌에
이자를 지급하거나 차감
```

같은 것이 아니다.
코어뱅킹 제품에서도 EOD/EOTI에서 이자 accrual을 수행하고, 정해진 지급일의 BOD에 자동 liquidation을 수행하는 형태가 사용될 수 있다.

---

## 8. 자동이체와 예약 작업

오늘 실행해야 하는 예약 거래도 있다.
예를 들어

```text
매월 25일

월세 500,000원 자동이체
```

같은 Standing Instruction을 등록했다고 하자.
날짜가 바뀌면서

```text
오늘 실행할 Instruction 찾기
          │
          ▼
   실행 대상 생성
          │
          ▼
     거래 처리
```

과정이 필요하다.
코어뱅킹 시스템에는 이런 Standing Instruction이나 Periodic Instruction을 EOD/BOD Batch에서 실행하는 기능이 존재한다.

---

## 9. 대출도 날짜가 중요하다

대출 역시 날짜 기반 이벤트가 많다.

```text
대출 실행일

상환 예정일

이자 납입일

연체 시작일

만기일
```

예를 들어 오늘이 대출 상환일이라면

```text
Business Date 변경
       │
       ▼
오늘 상환 예정 Loan 검색
       │
       ▼
상환 처리
       │
       ├─ 정상
       │
       └─ 잔액 부족
              │
              ▼
          미납/연체 처리
```

같은 Batch가 실행될 수 있다.
따라서 은행에서는 **날짜를 바꾼다는 것 자체가 비즈니스 이벤트**다.

---

## 10. 계좌 상태도 바뀔 수 있다

어떤 계좌가 일정 기간 연체 상태에 있으면 상태가 변경될 수도 있다.

```text
NORMAL
   │
   │ 연체 지속
   ▼
OVERDUE
   │
   │ 더 장기 연체
   ▼
DELINQUENT
```

이를 사람이 매일 수백만 계좌를 확인할 수는 없다.
그래서

```text
EOD Batch

모든 대상 계좌 확인
       │
       ▼
Rule 평가
       │
       ▼
상태 변경
```

형태의 처리가 사용된다.
FLEXCUBE에도 EOD 시 계좌 상태를 계산하고 변경하는 Batch가 존재한다.

---

## 11. 회계 장부도 마감해야 한다

은행에서는 고객 계좌만 중요한 것이 아니다.
내부적으로는 수많은 회계 Entry가 존재한다.

```text
고객 A 입금

        ↓

고객예금 계정

        +

현금 / 타행 계정

        ↓

회계 Entry
```

하루 동안 발생한 Entry를 기반으로

```text
자산

부채

수익

비용

예수금

대출금
```

등을 집계해야 한다.
그래서 EOD 이후에는 당일의 최종 데이터로

```text
GL
General Ledger

일계표

각종 내부 보고서

대외 보고용 데이터
```

등을 만들 수 있다.
EOFI 이후 최신 잔액이 확정되면 당일 금융 보고서를 생성할 수 있다는 것도 코어뱅킹 EOD 설계의 중요한 이유다.

---

## 12. Reconciliation도 중요하다

하루 동안 은행은 외부 시스템과 계속 통신한다.

```text
은행

├─ 금융결제원
├─ 카드망
├─ ATM
├─ VAN
├─ 증권
└─ 해외망
```

우리 시스템에는

```text
거래 성공
```

이라고 기록돼 있는데 외부기관에는

```text
거래 없음
```

이라면 문제가 된다.
그래서 서로의 기록을 비교한다.

```text
내부 거래내역
       │
       │
       ▼
     비교
       ▲
       │
외부기관 거래내역
```

이를 **Reconciliation, 대사**라고 한다.
일치하지 않는 거래는

```text
Mismatch
   │
   ├─ 누락
   ├─ 중복
   ├─ 금액 불일치
   └─ 상태 불일치
```

등으로 확인하고 별도로 처리한다.
실제 코어뱅킹 제품의 EOD Batch에도 switch reconciliation, network settlement 같은 작업이 포함될 수 있다.

---

## 13. 이렇게 많은 Batch를 누가 실행할까?

여기서 등장하는 것이 **Scheduler**다.
수십\~수백 개의 Batch를 사람이 직접

```text
12:01 이거 실행

12:03 저거 실행

12:10 다음 거 실행
```

할 수는 없다.
Scheduler가 정해진 순서와 조건에 따라 Job을 실행한다.

```text
              Scheduler
                  │
          ┌───────┼───────┐
          ▼       ▼       ▼

       Job A    Job B    Job C
```

그런데 단순히 시간만 보고 실행하는 것도 아니다.

---

## 14. Batch에는 선후관계가 있다

예를 들어 다음 Job이 있다고 해보자.

```text
A. 오늘 거래 마감

B. 이자 계산

C. 잔액 확정

D. 회계 보고서 생성
```

C가 끝나기 전에 D를 실행하면 잘못된 보고서가 만들어질 수 있다.
그래서 Dependency가 필요하다.

```text
거래 마감
    │
    ▼
이자 계산
    │
    ▼
잔액 확정
    │
    ▼
보고서 생성
```

Scheduler는 이런 **Job Dependency**를 관리한다.

---

## 15. 독립적인 Job은 병렬로 돌릴 수도 있다

반대로 서로 관련 없는 Job이라면 동시에 실행할 수 있다.

```text
              Job A
            /       \
           ▼         ▼
        Job B       Job C
           │         │
           └────┬────┘
                ▼
              Job D
```

예를 들어 B와 C가 서로 독립적이라면 병렬로 처리해 EOD 시간을 줄일 수 있다.
Oracle FLEXCUBE도 EOD를 Scheduler Framework로 실행하면서 여러 세션을 사용해 Multi Thread 방식으로 처리할 수 있도록 지원한다.

---

## 16. 실제 Scheduler 관점에서는

단순하게 보면 이런 구조다.

```text
                Scheduler
                    │
                    ▼
              Job Repository
                    │
           실행 대상 Job 조회
                    │
                    ▼
            Dependency 확인
                    │
            ┌───────┴───────┐
            │               │
          만족             미충족
            │               │
            ▼               ▼
         실행            대기
            │
            ▼
      Worker / Executor
            │
            ▼
       Batch 실행
            │
       ┌────┴────┐
       ▼         ▼
    SUCCESS    FAILED
```

실행 결과는 반드시 기록한다.

```text
Job ID

Business Date

Start Time

End Time

Status

Processed Count

Error Count

Retry Count
```

그래야 운영자가
> "오늘 EOD 어디까지 끝났지?"
를 확인할 수 있다.

---

## 17. Batch가 중간에 실패하면?

예를 들어 백만 개 계좌의 이자를 계산하고 있었다.

```text
1
2
3
...
499,999
500,000
   │
   X
DB 장애
```

여기서 가장 안 좋은 방법은

```text
처음부터 다시 실행
```

이다.
이미 처리한 50만 계좌에 이자가 또 들어갈 수도 있다.
그래서 금융 Batch에서 중요한 것이 **재실행 가능성**이다.

```text
Retry

Restart

Checkpoint

Idempotency
```

같은 설계가 필요하다.

---

## 18. Batch도 멱등성이 중요하다

예를 들어

```text
Account 100

오늘 이자 +1,000원
```

을 처리했다고 하자.
그런데 Batch가 죽어서 재시작했다.
단순하게

```text
balance += 1000
```

을 다시 실행하면

```text
+1,000
+1,000

총 +2,000
```

이 된다.
그래서

```text
account_id
business_date
interest_type
```

등을 이용해

```text
오늘 이자를 이미 처리했는가?
```

를 확인하거나, 동일 작업의 중복 적용을 막는 설계가 필요하다.

```text
Job 실행
   │
   ▼
처리 여부 확인
   │
 ┌─┴─────────┐
 │           │
미처리      처리됨
 │           │
 ▼           ▼
처리        Skip
```

온라인 결제뿐 아니라 Batch에서도 멱등성이 중요한 이유다.

---

## 19. 실패한 Job 때문에 다음 Job을 실행해도 될까?

예를 들어

```text
Interest Batch
     │
     X 실패
     │
     ▼
GL Report Batch
```

이자를 계산하지 못했는데 회계 보고서를 만들면 안 된다.
그래서 Scheduler에서는

```text
Job A SUCCESS

       │
       ▼

Job B 실행
```

같은 조건을 둔다.

```text
Job A FAILED

       │
       X

Job B 실행 금지
```

EOD는 결국 하나의 거대한 **Workflow / DAG**라고 볼 수 있다.

---

## 20. EOD가 끝나면 날짜를 바꾼다

모든 당일 작업이 끝났다.

```text
거래 마감       O

이자 계산       O

자동처리        O

회계 처리       O

검증            O
```

그러면 EOD 상태로 이동한다.

```text
Business Date

2026-09-22

      │
      ▼

     EOD
```

이제 시스템 날짜를 다음 영업일로 변경한다.

```text
2026-09-22

      │
      ▼

Date Change

      │
      ▼

2026-09-23
```

여기서 중요한 것은 단순히 `+1 day`가 아니라는 점이다.

```text
금요일

9월 25일

     │
     ▼

다음 영업일

9월 28일 월요일
```

처럼 은행의 **Holiday Calendar**를 기반으로 다음 영업일을 계산할 수 있다.
FLEXCUBE 역시 `Previous Working Date`, `Today`, `Next Working Date`를 관리하고 다음 영업일은 지점의 휴일 캘린더를 기준으로 결정한다.

---

## 21. BOD가 시작된다

날짜가 바뀌었다고 바로 업무를 시작하는 것은 아니다.
이번에는 **BOD(Beginning Of Day)** 가 있다.

```text
EOD
 │
 ▼
Date Change
 │
 ▼
BOD
 │
 ▼
새로운 영업일
```

BOD에서는

```text
오늘 실행할 거래 찾기

오늘 만기 상품 확인

자동 이자 지급

예약된 Instruction 처리

오늘 적용할 상태/한도 갱신
```

같은 작업을 수행할 수 있다.
Oracle FLEXCUBE에서도 BOD를 **시스템 날짜가 변경된 뒤 거래 입력을 시작하기 전의 단계**로 정의하고, 예정된 이자·수수료 등의 자동 liquidation을 이 단계에서 수행할 수 있도록 한다.

---

## 22. 전체 흐름을 한 번에 보면

은행의 하루를 매우 단순화하면 다음과 같다.

```text
             BOD
              │
              ▼
        새로운 영업일 시작
              │
              ▼
      ┌────────────────┐
      │ Transaction    │
      │ Input          │
      │                │
      │ 입금 / 출금     │
      │ 이체 / 대출     │
      │ 각종 거래       │
      └───────┬────────┘
              │
              ▼
            EOTI
      거래 입력 마감
              │
              ▼
          EOD Batch
              │
       ┌──────┼──────┐
       ▼      ▼      ▼
      이자   상태     회계
      계산   갱신     처리
       │      │      │
       └──────┼──────┘
              ▼
            EOFI
       회계 입력 마감
              │
              ▼
         검증 / 보고
              │
              ▼
             EOD
              │
              ▼
         Date Change
              │
              ▼
             BOD
```

EOD는 단일 프로그램 하나가 아니라 **여러 단계와 여러 Batch Job으로 이루어진 업무 사이클**에 가깝다.

---

## 23. 그러면 밤 점검 시간에는 무조건 은행이 멈출까?

그렇지는 않다.
과거에는 EOD 동안 전체 시스템을 막는 방식이 흔했지만, 현대 금융 서비스는 24시간 서비스를 요구한다.
그래서 아키텍처적으로는

```text
고객 Online System

계속 서비스
──────────────▶


        동시에


Back Office / Core Banking

EOD 처리
──────────────▶
```

처럼 영향을 분리하거나, 특정 거래를 임시 상태로 받아 두었다가 영업일 전환 이후 반영하는 구조 등을 사용할 수 있다.
코어뱅킹 시스템에서도 지점이나 업무가 거래 불가능한 상태일 때 요청을 `tanked` 상태로 저장한 뒤, 다시 사용 가능한 상태가 되면 Batch에서 처리하는 방식이 존재한다.
따라서

```text
EOD = 은행 전체 서버 종료
```

는 아니다.
더 정확하게는
> **영업일을 안전하게 마감하고 다음 영업일로 전환하기 위한 일련의 처리 과정**
이라고 보는 것이 맞다.

---

## 24. 결국 Scheduler가 중요한 이유

EOD 작업을 보면 이런 특징이 있다.

```text
수많은 Job

+

복잡한 Dependency

+

대량 데이터

+

실패 가능성

+

정해진 시간 안에 완료
```

그래서 Scheduler는 단순한

```text
"밤 12시에 프로그램 실행"
```

도구가 아니다.
실제로는

```text
             Scheduler
                 │
                 ▼
         Workflow 관리
                 │
      ┌──────────┼──────────┐
      ▼          ▼          ▼
 Dependency    Retry      Parallel
    관리        관리        실행
      │          │          │
      └──────────┼──────────┘
                 ▼
             Monitoring
```

역할을 한다.
EOD 전체가 정상적으로 끝나야 다음 영업일을 안전하게 시작할 수 있기 때문이다.

---

## 정리

은행의 밤은 단순히 서버를 점검하는 시간이 아니다.

```text
하루 동안
수많은 거래 발생
       │
       ▼
     EOTI
 거래 입력 마감
       │
       ▼
    Batch 처리
       │
       ├─ 이자
       ├─ 수수료
       ├─ 자동처리
       ├─ 상태 변경
       ├─ 회계
       ├─ 대사
       └─ 보고
       │
       ▼
     EOFI
       │
       ▼
      EOD
       │
       ▼
 Business Date 변경
       │
       ▼
      BOD
       │
       ▼
 다음 영업일 시작
```

그리고 이 수많은 작업을 순서대로 실행하고, 병렬화하고, 실패를 감지하고, 필요한 경우 재실행시키는 역할을 **Batch Scheduler**가 담당한다.
즉, 우리가 보는

```text
"자정 시스템 점검"
```

뒤에는 사실
**오늘의 금융 상태를 확정하고 내일의 금융 상태를 만드는 거대한 데이터 처리 파이프라인**이 돌아가고 있는 것이다.
백엔드 관점에서는 EOD를 단순한 예약 작업이 아니라

```text
대규모 Batch Processing

+

Workflow / DAG

+

Idempotency

+

Retry / Recovery

+

Business Date

+

Accounting Consistency
```

문제로 보면 금융 시스템 아키텍처를 훨씬 깊게 이해할 수 있다.
