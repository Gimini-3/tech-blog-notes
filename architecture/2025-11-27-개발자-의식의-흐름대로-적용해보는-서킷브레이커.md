# 1. 공통 플랫폼의 필요성과 잠재적 위험
서비스 규모가 커지면 기능 중복 개발을 막고 비용을 효율화하기 위해 **공통 플랫폼**을 도입한다. 하지만 공통 플랫폼 사용 시 주의할 점이 존재한다. 모든 소프트웨어는 버그와 장애 가능성을 내포하고 있으며, 공통 플랫폼의 장애는 이를 사용하는 하위 서비스로 전파될 수 있다는 점이다.
이를 해결하는 가장 좋은 방법은 비동기(Asynchronous) 연동이지만, 실시간 데이터가 필요한 조회성 기능 등에서는 동기(Synchronous) 연동이 불가피하다. 이때 동기 통신 구간에서 장애 전파를 차단하는 핵심 기술이 바로 **서킷브레이커(Circuit Breaker)**이다.
# 2. 서킷브레이커(Circuit Breaker)란?
서킷브레이커는 외부 시스템 호출 실패율이 일정 임계치를 넘어가면, 연동을 차단(Open)하여 불필요한 대기를 막고 장애가 전파되는 것을 방지하는 기술이다. 이후 대상 시스템이 정상화되면 다시 연결을 복구한다.
### 주요 상태(State)와 동작 원리
서킷브레이커는 `Sliding Window` 알고리즘을 통해 상태를 변경한다.
- **CLOSED (정상):** 평상시 상태이다. 호출이 정상적으로 수행된다.
- **OPEN (차단):** 실패율이 임계치를 초과한 상태이다. 요청을 보내지 않고 즉시 에러를 반환하거나 Fallback 로직을 수행한다.
- **HALF_OPEN (반개방):** OPEN 상태에서 일정 시간이 지난 후 진입한다. 제한된 횟수만큼 호출을 허용하여 성공 여부를 확인한다. 성공 시 CLOSED로, 실패 시 다시 OPEN으로 돌아간다.
# 3. 서킷브레이커의 판단 기준: 슬라이딩 윈도우 
서킷브레이커가 장애라고 판단하고 회로를 끊는(OPEN) 기준은 무엇일까? 단순히 한 번 실패했다고 바로 차단하면 너무 민감하게 반응하게 된다. 그래서 '최근의 데이터'를 수집해서 판단하는데, 이때 사용하는 알고리즘이 **슬라이딩 윈도우(Sliding Window)**이다.
슬라이딩 윈도우는 데이터를 기록하는 '창문(Window)'을 옆으로 밀면서(Sliding) 최근 데이터를 계속 갱신하는 방식이다.
### **횟수 기반 (COUNT_BASED):**
- 최근 N번의 호출 결과를 저장한다.
- 예: `slidingWindowSize=10`이면, 최근 10번의 호출 중 실패가 몇 번인지 계산한다. 11번째 호출이 들어오면 가장 오래된 1번째 기록은 지워진다.
### **시간 기반 (TIME_BASED):**
- 최근 N초 동안의 호출 결과를 저장한다.
- 예: `slidingWindowSize=10`이면, 최근 10초 동안 발생한 모든 호출의 실패율을 계산한다.
### **상태 변경(OPEN)의 의미**
설정된 윈도우 안에서 실패율이 임계치(예: 50%)를 넘으면 서킷브레이커는 **OPEN** 상태로 변한다.
- **OPEN 상태:** 외부 시스템으로 가는 길을 아예 막아버린다.
- **동작:** 외부 시스템을 실제로 호출하지 않고, 즉시 에러를 뱉거나 미리 준비된 대체 동작(Fallback)을 수행한다. 이를 통해 불필요한 대기 시간을 없애고 시스템 리소스를 보호한다.
# 4. Fallback과 비즈니스 예외 처리
서킷브레이커 구현에서 가장 고민해야 할 지점은 "무엇을 실패로 볼 것인가"와 "실패 시 무엇을 보여줄 것인가(Fallback)"이다.
## 4.1 Fallback 메서드
`@CircuitBreaker` 어노테이션을 사용하여 적용 대상 메서드를 지정한다.
```java
public class PlatformExecutor {

    // name: 설정 파일에서 사용할 인스턴스 이름
    // fallbackMethod: 실패 시 수행할 대체 메서드
    @CircuitBreaker(name = "toPlatform", fallbackMethod = "fallback")
    public PlatformResultDto execute(Condition condition) {
        // 외부 플랫폼 호출 로직
        return externalApiClient.call(condition);
    }

    // 일반적인 예외에 대한 Fallback
    private PlatformResultDto fallback(Condition condition, Exception exception) {
        log.warn("fallback 실행. condition:{}", condition, exception);
        return PlatformResultDto.empty(); // 빈 객체 반환 등 비즈니스 로직 수행
    }

    // 서킷이 OPEN 되어 호출 자체가 차단되었을 때의 Fallback
    private PlatformResultDto fallback(Condition condition, CallNotPermittedException exception) {
        log.warn("[CircuitBreaker : OPEN] 차단됨. condition:{}", condition);
        return PlatformResultDto.cached(); // 캐시 데이터 반환 등
    }
}
```
### Fallback Method 주의사항
- **실행 조건:** Fallback은 서킷브레이커의 상태(OPEN/CLOSED)와 관계없이, 대상 메서드에서 예외(Exception)가 발생하면 실행된다.
- **예외 전파:** Fallback이 실행되면 원본 예외는 상위 메서드로 전파되지 않는다. 따라서 비즈니스 로직상 예외를 상위로 던져야 한다면 Fallback 내부 처리에 주의가 필요하다.
## 4.2 무엇을 실패로 볼 것인가? 
서킷브레이커는 기본적으로 **Exception(예외)**이 발생해야 실패로 카운팅한다. 하지만 HTTP 통신에서 상태 코드는 200(OK)이지만, 응답 본문(Body)이 비어있거나 논리적인 오류 코드가 내려오는 경우가 있다.
- **상황:** 외부 몰(Mall)의 상품 목록을 조회했는데, 빈 리스트(`[]`)가 반환되었다.
- **판단:**
	- **정상:** 해당 카테고리에 진짜 상품이 없는 경우.
	- **장애:** 외부 시스템의 DB 오류로 데이터를 못 가져온 경우.
- **대응:** 만약 이것이 장애 상황이라면, 서킷브레이커가 이를 감지할 수 있도록 **개발자가 직접 코드로 확인하여 Exception을 강제로 발생시켜야 한다.** 그래야 서킷브레이커가 실패 횟수를 누적하고 상태를 OPEN으로 변경할 수 있다. 즉, 단순히 HTTP Status Code에 의존하지 말고, 비즈니스 로직에 맞춰 '실패'를 정의해야 한다.
```java
// 예시: 비즈니스 로직에 따른 예외 처리와 Fallback
@CircuitBreaker(name = "backendA", fallbackMethod = "fallback")
public String doSomething() {
    Response response = externalApi.call();
    
    // HTTP 200이어도 데이터가 이상하면 예외를 던져서 실패로 기록하게 해야 한다.
    if (response.getBody() == null) {
        throw new InvalidResponseException("데이터 없음"); 
    }
    return response.getBody();
}

// Fallback 메서드
private String fallback(Exception e) {
    return "대체 데이터 반환"; // 장애 시 기본값 제공
}
```
# 5. Observability: 로그 모니터링 및 설정
서킷브레이커가 제대로 동작하는지 확인하기 위해서는 상태 변화에 대한 로그 확보와 모니터링이 필수적이다.
## 5.1 Event Consumer를 통한 로깅
`RegistryEventConsumer`를 구현하여 상태 전이(State Transition) 발생 시 로그를 남길 수 있다.
```java
public class CircuitBreakerRegistryEventConsumer implements RegistryEventConsumer<CircuitBreaker> {
    @Override
    public void onEntryAddedEvent(EntryAddedEvent<CircuitBreaker> entryAddedEvent) {
        entryAddedEvent.getAddedEntry().getEventPublisher()
            .onFailureRateExceeded(event -> 
                log.warn("{} 실패율 초과: {}%", event.getCircuitBreakerName(), event.getFailureRate()))
            .onStateTransition(event -> 
                log.info("{} 상태 변경: {} -> {}", 
                    event.getCircuitBreakerName(), 
                    event.getStateTransition().getFromState(), 
                    event.getStateTransition().getToState()));
    }
}
```
## 5.2 핵심 설정 값 (application.properties)
설정은 `application.properties`에서 관리하며, 서비스의 트래픽 특성에 맞춰 튜닝해야 한다.
```java
// 슬라이딩 윈도우 크기: 최근 10번의 호출을 기준으로 판단
resilience4j.circuitbreaker.configs.default.sliding-window-size=10
// 실패율 임계값: 50% 이상 실패하면 Circuit OPEN
resilience4j.circuitbreaker.configs.default.failure-rate-threshold=50
// OPEN 상태 유지 시간: 10초 동안 차단 후 HALF_OPEN으로 전환
resilience4j.circuitbreaker.configs.default.wait-duration-in-open-state=10s
// 윈도우 타입: 횟수 기반 (COUNT_BASED)
resilience4j.circuitbreaker.configs.default.sliding-window-type=COUNT_BASED
```
## 5.3 시각화 (Grafana)
Resilience4j는 Prometheus 메트릭을 제공한다. 이를 수집하여 Grafana 대시보드에 연동하면 실시간으로 서킷브레이커의 상태와 실패율을 시각화하여 운영 효율을 높일 수 있다.
# 6. 결론
서킷브레이커 도입은 단순히 에러를 막는 것을 넘어 운영의 안정성을 가져온다.
1. **장애 격리:** 외부 시스템이 죽어도 내 서비스는 살아남는다 (Fail Fast).
2. **자동 복구:** 개발자가 밤중에 개입하지 않아도, 외부 시스템이 살아나면 자동으로 연결을 복구한다.
3. **가시성 확보:** Consumer와 모니터링 도구(Grafana 등)를 연동하여 현재 시스템의 연동 상태를 한눈에 파악할 수 있다.
장애는 피할 수 없다. 하지만 서킷브레이커를 통해 장애의 확산을 막고 우아하게 대처하는 시스템을 구축하는 것은 가능하다.
# 7. 느낀점
대규모에서 외부 시스템에 의존하게 되면 엄청난 문제가 발생할 것이라고 생각했는데 실제로 어떤 방식으로 외부 시스템에 장애가 발생했을 때 대처하는지 알 수 있는 글이었다. 이런 방식들을 직접 구현해봄으로써 단순히 외부 API 호출이 아닌 설계까지 신경 써야겠다.
