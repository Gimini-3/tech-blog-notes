## 이벤트 기반 아키텍처가 필요했던 이유

초기 배달의민족은 하나의 애플리케이션과 하나의 데이터베이스로 구성된 모놀리식 구조였다.

서비스가 성장하면서 주문량과 트래픽이 빠르게 증가했고, 하나의 시스템에서 모든 기능을 처리하는 구조는 한계에 도달했다. 이후 기능과 도메인을 여러 마이크로서비스로 분리하기 시작했다.
하지만 시스템을 물리적으로 분리했다고 해서 서비스 간 결합이 자동으로 낮아지는 것은 아니다.
다음과 같은 정책이 있다고 가정해 보자.

> 회원의 본인인증이 초기화되면 가족계정에서도 해당 회원이 탈퇴되어야 한다.
> 회원과 가족계정이 하나의 애플리케이션에 있을 때는 본인인증 초기화 로직에서 가족계정 탈퇴 메서드를 직접 호출할 수 있다.
> 마이크로서비스로 분리한 뒤에는 이 호출이 HTTP 요청으로 바뀐다. 회원시스템이 가족계정 시스템의 탈퇴 API를 호출하는 방식이다.
> 물리적으로는 시스템이 분리되었지만 회원시스템은 여전히 다음 내용을 알아야 한다.

- 가족계정 시스템이 존재한다.
- 본인인증이 초기화되면 가족계정 탈퇴가 필요하다.
- 어떤 API를 호출해야 하는지 알아야 한다.
- 가족계정 시스템의 장애와 응답 실패를 처리해야 한다.
  결국 호출 방식만 바뀌었을 뿐, 회원시스템이 가족계정의 정책을 알고 있다는 논리적인 의존 관계는 그대로 남아 있다.

## 비동기 통신만으로는 결합이 사라지지 않는다

동기 HTTP 호출은 상대 시스템의 응답을 기다려야 한다.
가족계정 시스템의 응답이 느리거나 장애가 발생하면 회원의 본인인증 초기화 요청도 영향을 받는다.
이를 피하기 위해 별도 스레드에서 비동기로 HTTP 요청을 보낼 수 있다. 주 요청 스레드는 회원의 본인인증만 초기화하고, 가족계정 탈퇴 요청은 별도 스레드가 처리하는 방식이다.
이렇게 하면 응답 대기 시간과 장애 전파를 줄일 수 있다. 하지만 회원시스템이 가족계정 시스템의 업무를 알고 있다는 사실은 달라지지 않는다.
메시징 시스템을 사용해도 마찬가지다.
회원시스템이 메시지 브로커에 다음과 같은 메시지를 전달한다고 가정해 보자.

> 가족계정에서 이 회원을 탈퇴시켜라.
> HTTP 호출은 사라졌지만 회원시스템은 여전히 가족계정이 해야 할 일을 알고 있다.
> 특정 대상에게 어떤 작업을 수행하라고 지시하는 메시지를 Command라고 한다.

```text
Command 방식

[회원시스템]
본인인증 초기화
      │
      └─ "가족계정을 탈퇴시켜라"
                    │
                    ▼
              [메시지 브로커]
                    │
                    ▼
             [가족계정 시스템]

Event 방식

[회원시스템]
본인인증 초기화
      │
      └─ "본인인증이 초기화되었다"
                    │
                    ▼
              [메시지 브로커]
                    │
          ┌─────────┼─────────┐
          ▼         ▼         ▼
     가족계정     보안 시스템   알림 시스템
```

가족계정의 정책이 탈퇴에서 일시 정지로 변경되면 Command 메시지를 발행하는 회원시스템도 함께 수정될 가능성이 높다.
반면 회원시스템이 `본인인증이 초기화되었다`는 사실만 발행하면 가족계정 시스템이 자신의 정책에 따라 탈퇴나 일시 정지를 결정할 수 있다.
회원시스템은 가족계정 시스템이 이벤트를 받아 무엇을 처리하는지 알 필요가 없다.

## 무엇을 이벤트로 발행해야 하는가

이벤트는 다른 시스템이 해야 할 작업이 아니라, 자신의 도메인에서 이미 발생한 사실을 표현해야 한다.
Command는 특정 작업을 요청한다.

- 가족계정을 탈퇴시켜라.
- 쿠폰을 발급하라.
- 알림을 전송하라.
- 포인트를 차감하라.
  Event는 이미 발생한 사실을 표현한다.
- 회원이 가입했다.
- 회원이 로그인했다.
- 회원의 본인인증이 초기화되었다.
- 회원이 탈퇴했다.
- 회원의 휴대전화 번호가 변경되었다.
  이벤트 발행자는 자신의 도메인에서 발생한 사실만 전달한다. 이벤트를 구독한 시스템은 그 사실을 바탕으로 자신의 정책을 수행한다.
  예를 들어 회원 탈퇴 이벤트 하나를 여러 시스템이 구독할 수 있다.
- 가족계정 시스템은 가족계정에서도 회원을 제거한다.
- 쿠폰 시스템은 남아 있는 쿠폰을 만료 처리한다.
- 알림 시스템은 탈퇴 완료 알림을 전송한다.
- 보안 시스템은 회원 탈퇴 기록을 저장한다.
  회원시스템은 각 구독자가 어떤 작업을 수행하는지 몰라도 된다. 새로운 구독자가 추가되어도 회원 탈퇴 로직은 변경되지 않는다.
  이것이 이벤트를 통해 서비스 간 결합을 느슨하게 만드는 핵심이다.

## 회원시스템의 세 가지 이벤트 계층

회원시스템은 이벤트를 모두 같은 방식으로 처리하지 않고 세 가지 계층으로 구분했다.

1. 애플리케이션 이벤트
2. 내부 이벤트
3. 외부 이벤트
   각 이벤트는 전달 범위와 목적이 다르다.

### 애플리케이션 이벤트

하나의 애플리케이션 프로세스 안에서 사용한다.
Spring의 `ApplicationEventPublisher`, `@EventListener`, `@TransactionalEventListener`를 이용해 핵심 도메인 로직과 부가 작업을 분리한다.

### 내부 이벤트

회원시스템 내부에서 처리해야 하는 부가 정책을 메시징 시스템으로 분리한다.
AWS SNS와 SQS를 이용해 작업을 비동기로 처리하고, 작업별 재시도와 독립적인 확장이 가능하도록 구성한다.

### 외부 이벤트

회원시스템의 상태 변화를 다른 마이크로서비스에 전달한다.
특정 외부 시스템의 요구사항에 의존하지 않도록 일반화된 형태로 제공한다.

```text
[회원 도메인 로직]
회원가입, 로그인, 본인인증 초기화
             │
             ▼
     애플리케이션 이벤트
             │
       ┌─────┴─────┐
       ▼           ▼
  이벤트 저장    SNS 발행
                    │
                    ▼
               내부 이벤트
                    │
          ┌─────────┼─────────┐
          ▼         ▼         ▼
      부가 정책   기록 처리   외부 이벤트 생성
                              │
                              ▼
                         외부 이벤트
                              │
                              ▼
                       다른 마이크로서비스
```

## 애플리케이션 이벤트로 도메인 로직 분리하기

이벤트 기반 구조는 마이크로서비스 사이에서만 필요한 것이 아니다.
하나의 애플리케이션 안에서도 핵심 도메인 로직과 부가 작업이 섞이면 결합도가 높아질 수 있다.
회원가입 이후 다음 작업이 필요하다고 가정해 보자.

- 회원 데이터 저장
- 회원가입 이벤트 저장
- SNS 메시지 발행
- 감사 로그 작성
- 통계 데이터 기록
  회원가입 서비스가 이 작업을 모두 직접 처리하면 회원가입 로직이 메시징 시스템, 로그, 통계 처리에 의존하게 된다.
  회원시스템은 회원가입 로직에서 회원을 저장하고 애플리케이션 이벤트만 발행하도록 구성했다. 이벤트 저장과 SNS 발행은 별도의 이벤트 구독자가 담당한다.

메시징 시스템이 SNS에서 다른 기술로 변경되더라도 회원가입 도메인 로직이 아니라 이벤트 구독자만 수정하면 된다.

### 트랜잭션 실행 시점

Spring의 `@TransactionalEventListener`를 사용하면 구독자가 실행되는 시점을 트랜잭션 단계에 맞춰 설정할 수 있다.
`BEFORE_COMMIT`은 기존 트랜잭션이 커밋되기 전에 실행된다.
회원 데이터와 이벤트 기록을 반드시 함께 저장해야 한다면 이벤트 저장 구독자를 같은 데이터베이스 트랜잭션 안에서 실행할 수 있다.
`AFTER_COMMIT`은 기존 트랜잭션이 정상적으로 커밋된 뒤 실행된다.
SNS 발행과 같은 외부 통신을 커밋 이후로 분리하면 SNS 장애로 인해 회원가입 트랜잭션이 실패하는 문제를 줄일 수 있다.
하지만 DB 커밋 이후 애플리케이션이 종료되거나 SNS 발행에 실패하면 회원 데이터만 저장되고 이벤트는 전달되지 않을 수 있다.
이 문제는 이벤트 저장소를 통해 해결한다.

## 내부 이벤트로 핵심 행위와 부가 정책 분리하기

회원 로그인 과정에는 여러 작업이 함께 수행될 수 있다.

- 회원을 로그인 상태로 변경한다.
- 현재 디바이스의 로그인 정보를 저장한다.
- 동일 회원이 로그인한 다른 디바이스를 로그아웃한다.
- 동일 디바이스에 로그인된 다른 회원을 로그아웃한다.
  이 작업을 하나의 로그인 메서드에서 모두 처리하면 로그인 기능의 핵심이 무엇인지 파악하기 어렵다.
  회원시스템은 로그인 기능의 핵심 행위를 다음과 같이 정의했다.
  > 회원을 로그인 상태로 변경한다.
  > 디바이스 로그인 기록과 다른 디바이스 로그아웃은 로그인과 함께 수행되어야 하는 정책이지만, 핵심 행위와는 분리할 수 있다.
  > 따라서 로그인 서비스는 회원 상태를 변경하고 로그인 이벤트를 발행하는 역할만 담당한다.
  > 이후 SNS와 SQS를 이용해 부가 작업을 별도의 소비자로 분리한다.
- 디바이스 로그인 기록 소비자
- 동일 회원의 다른 디바이스 로그아웃 소비자
- 동일 디바이스의 다른 회원 로그아웃 소비자

각 작업은 독립적으로 실행된다.
특정 작업이 실패해도 로그인 요청 전체를 실패시키지 않고 해당 SQS 메시지만 재시도할 수 있다. 특정 소비자의 처리량이 많다면 해당 소비자만 별도로 확장할 수도 있다.
다만 모든 작업을 무조건 비동기로 분리하는 것은 적절하지 않다.
비동기 처리를 사용하면 회원은 로그인 상태지만 다른 디바이스는 아직 로그아웃되지 않은 상태가 잠시 존재할 수 있다.
핵심 행위와 부가 정책을 구분할 때는 다음 질문을 기준으로 판단할 수 있다.

> 이 작업이 지금 완료되지 않으면 요청 자체를 실패시켜야 하는가?
> 즉시 완료되어야 한다면 핵심 트랜잭션에 포함한다.
> 약간 늦게 처리되어도 되고 실패 시 재시도할 수 있다면 이벤트 기반 비동기 처리 대상으로 분리할 수 있다.

## 내부 이벤트와 외부 이벤트를 분리한 이유

회원시스템은 내부 이벤트를 외부 마이크로서비스에 그대로 공개하지 않았다.
내부 이벤트와 외부 이벤트의 목적이 다르기 때문이다.
내부 이벤트는 회원시스템 내부 작업을 효율적으로 처리하는 것이 목적이다.
생산자와 소비자가 같은 시스템 안에 있기 때문에 구독자가 필요로 하는 정보를 비교적 자유롭게 추가할 수 있다.
로그인 내부 이벤트에는 다음과 같은 정보가 포함될 수 있다.

- 회원 번호
- 디바이스 번호
- 로그인 방식
- 세션 정보
- 이전 로그인 상태
  이벤트 구조가 변경되어도 같은 시스템 안에서 생산자와 소비자를 함께 수정하고 배포할 수 있다.
  반면 외부 이벤트는 다른 시스템과의 결합을 줄이는 것이 목적이다.
  외부 시스템이 요구하는 데이터를 이벤트에 계속 추가하면 회원시스템이 외부 시스템의 비즈니스 변화에 영향을 받는다.
  가족계정 시스템이 새로운 정보를 요구할 때마다 외부 이벤트를 변경한다면, 결국 회원시스템이 가족계정 시스템의 내부 정책을 알게 된다.
  따라서 외부 이벤트는 특정 구독자의 요구사항이 아니라 회원 도메인에서 발생한 사실을 중심으로 구성해야 한다.

## 외부 이벤트 일반화와 ZERO-PAYLOAD

회원시스템은 외부 이벤트를 다음 형태로 일반화했다.

> 언제, 어떤 회원에게, 어떤 행위와 속성 변화가 발생했는가.
> 이를 표현하기 위해 다음 정보를 이벤트에 포함한다.

- 회원 식별자
- 이벤트 타입
- 변경된 속성
- 이벤트 발생 시각
  회원의 휴대전화 번호가 변경된 경우 다음과 같이 표현할 수 있다.
- 회원 번호: `M000012345`
- 이벤트 타입: `MEMBER_INFORMATION_CHANGED`
- 변경 속성: `MOBILE_PHONE_NUMBER`
- 발생 시각: `2022-04-12 14:30:00`
  외부 시스템은 이벤트 타입과 변경 속성을 이용해 자신이 처리해야 하는 이벤트인지 판단한다.
  AWS SNS의 메시지 필터링 기능을 사용하면 각 구독자에게 필요한 이벤트만 전달할 수도 있다.

### ZERO-PAYLOAD 방식

외부 시스템이 실제 업무를 처리하려면 이벤트에 포함된 정보보다 더 많은 데이터가 필요할 수 있다.
알림 시스템이 휴대전화 번호 변경 이벤트를 받은 뒤 다음 정보가 필요하다고 가정해 보자.

- 현재 휴대전화 번호
- 이메일 주소
- 알림 수신 동의 여부
- 회원 상태
  이 정보를 모두 이벤트에 포함하면 이벤트 구조가 계속 커지고, 회원시스템이 외부 시스템의 요구사항에 의존하게 된다.
  회원시스템은 이를 피하기 위해 ZERO-PAYLOAD 방식을 선택했다.
  이벤트에는 회원 ID, 이벤트 타입, 변경 속성처럼 사건을 식별하기 위한 최소 정보만 넣는다. 상세 정보가 필요한 외부 시스템은 회원 API를 호출해 최신 상태를 조회한다.

```text
[회원 정보 변경]
        │
        └─ 최소 정보 이벤트 발행
            - 회원 식별자
            - 이벤트 타입
            - 변경 속성
            - 발생 시각
                      │
                      ▼
               [외부 시스템]
                      │
                      └─ 회원 API 조회
                              │
                              ▼
                         최신 상태 사용
```

이 방식은 외부 시스템의 요구사항이 변경되어도 이벤트 구조를 자주 수정하지 않아도 된다는 장점이 있다.
또한 이벤트가 순서대로 도착하지 않더라도 API를 통해 현재의 최신 상태를 확인할 수 있다.
반면 다음과 같은 부분은 추가로 고려해야 한다.

- 회원 API 조회 트래픽 증가
- API 장애와 타임아웃
- 소비자 재시도 정책
- 과거 시점이 아니라 조회 시점의 최신 데이터를 사용한다는 점
  따라서 ZERO-PAYLOAD는 과거 상태 자체보다 최신 상태를 이용하는 것이 중요한 경우에 적합하다.

## 이벤트 발행 유실 문제

애플리케이션 이벤트를 DB 트랜잭션 안에서 SNS로 발행하면 이벤트 전달을 어느 정도 보장할 수 있다.
하지만 SNS가 장애 상태라면 회원가입이나 로그인과 같은 핵심 기능의 트랜잭션도 실패한다.
메시징 시스템의 장애가 회원시스템의 장애로 이어지는 것이다.
이를 막기 위해 SNS 발행을 DB 트랜잭션이 커밋된 이후로 분리할 수 있다.
하지만 이번에는 이벤트 유실 문제가 발생한다.

```text
1. 회원 데이터 저장 성공
2. DB 트랜잭션 COMMIT
3. 애플리케이션 종료 또는 네트워크 장애
4. SNS 이벤트 발행 실패

결과

회원 상태는 변경되었지만
다른 시스템에는 이벤트가 전달되지 않음
```

DB 저장과 SNS 발행은 서로 다른 시스템에서 수행된다.
DB 저장만 성공하고 SNS 발행은 실패할 수 있다. 이처럼 두 시스템에 데이터를 나누어 기록하면서 정합성이 깨질 수 있는 문제를 Dual Write 문제라고 한다.

## 이벤트 저장소와 Transactional Outbox

회원시스템은 SNS 발행 자체를 도메인 트랜잭션에 포함하지 않았다.
대신 이벤트를 데이터베이스에 저장하는 것을 중요한 도메인 행위로 정의했다.
회원 데이터와 이벤트 데이터를 동일한 RDBMS의 같은 트랜잭션에 저장한다.
회원 데이터 저장에 성공했지만 이벤트 저장에 실패하면 전체 트랜잭션이 롤백된다. 반대로 이벤트만 저장되고 회원 상태 변경이 실패하는 상황도 발생하지 않는다.
비즈니스 데이터와 발행할 이벤트를 동일한 로컬 트랜잭션으로 저장하는 구조는 Transactional Outbox Pattern으로 볼 수 있다.
별도의 이벤트 전용 데이터베이스를 사용하면 회원 데이터베이스와 이벤트 데이터베이스 사이의 분산 트랜잭션 문제가 발생한다.
따라서 이벤트 저장소도 회원 도메인과 동일한 RDBMS를 사용했다.
이벤트 저장소에는 다음 정보가 기록된다.

- 이벤트 ID
- 회원 번호
- 이벤트 타입
- 변경된 속성
- 이벤트 생성 시각
- 발행 여부
- 발행 완료 시각
- 이벤트 발생 사유
- 이벤트 수행 시스템
- 이벤트 수행 주체
  하나의 행위에서 여러 속성이 변경될 수 있기 때문에 변경 속성은 JSON 형태로 저장하고 애플리케이션에서 처리하도록 구성했다.

## 이벤트 발행을 보장하는 흐름

전체 이벤트 발행 과정은 다음과 같다.

```text
1. 회원 도메인 행위 수행
   회원가입, 로그인, 본인인증 초기화

                │
                ▼

2. 동일한 DB 트랜잭션에서 저장
   회원 데이터 변경
   member_event 저장
   published = false

                │
                ▼

3. DB 트랜잭션 COMMIT

                │
                ▼

4. SNS로 내부 이벤트 발행

                │
                ▼

5. SQS 소비자가 이벤트 수신

                │
                ▼

6. 발행 확인 소비자가 상태 변경
   published = true
   published_at = 현재 시각
```

SNS로 이벤트가 정상적으로 전달되면 별도의 구독자가 이벤트 ID를 받아 발행 상태를 완료로 변경한다.
이벤트가 저장된 뒤 일정 시간이 지나도 `published=false`라면 SNS 발행 과정에서 누락되었을 가능성이 있다.
회원시스템은 생성 후 5분이 지났지만 아직 발행되지 않은 이벤트를 조회해 다시 SNS로 전달하는 배치 프로그램을 구성했다.
배치 프로그램은 직접 `published=true`로 변경하지 않는다.
이벤트를 다시 발행하고, 메시지가 정상적으로 전달되면 기존의 발행 확인 소비자가 상태를 변경한다.
최초 발행과 재발행이 동일한 흐름으로 처리되는 구조다.

## 이벤트 재발행과 특정 소비자 재처리

이벤트 저장소에는 과거에 발생한 이벤트가 남아 있다.
이를 이용하면 다양한 조건으로 이벤트를 조회하고 다시 발행할 수 있다.

- 특정 기간에 발생한 이벤트
- 특정 회원의 이벤트
- 특정 이벤트 타입
- 특정 변경 속성
- 내부 이벤트 또는 외부 이벤트
- 특정 소비자가 다시 처리해야 하는 이벤트
  알림 시스템의 소비자 로직에 오류가 있어 일부 회원에게 알림이 전달되지 않았다면 해당 기간과 이벤트 타입을 조회해 관련 이벤트만 다시 발행할 수 있다.
  SNS 메시지 속성에 `target` 값을 추가하면 모든 구독자가 아니라 특정 소비자에게만 이벤트를 전달하는 것도 가능하다.
  평상시에는 `ALL` 값을 사용해 모든 구독자가 이벤트를 받도록 한다. 특정 소비자만 재처리해야 한다면 해당 소비자의 식별자를 `target`에 지정한다.
  이를 통해 정상적으로 처리한 소비자에게 중복 이벤트를 보내지 않고 문제가 발생한 소비자만 다시 처리할 수 있다.

## 회원 활동 기록 테이블 통합

회원시스템은 개인정보를 다루기 때문에 회원 활동을 추적할 수 있어야 한다.
고객센터 문의 대응, 부정 사용자 추적, 수사기관 협조 등을 위해 기존에는 여러 기록 테이블이 존재했다.

- 로그인 기록
- 개인정보 변경 기록
- 본인인증 기록
- 회원 탈퇴 기록
- 계정 상태 변경 기록
  이벤트 저장소에는 회원에게 발생한 주요 행위와 속성 변화가 일관된 형식으로 저장된다.
  여기에 수행 시스템, 수행 주체, 수행 사유까지 기록하면서 이벤트 저장소가 회원 활동 기록과 감사 로그의 역할도 수행하게 되었다.
  결과적으로 여러 용도로 나뉘어 있던 기록 테이블을 하나의 회원 이벤트 저장소로 통합할 수 있었다.
  이벤트 저장소를 활동 이력으로 사용한다면 개인정보 보관 기간, 접근 권한, 암호화, 데이터 삭제 정책도 함께 고려해야 한다.

## 전체 구조에서 얻은 효과

### 서비스 간 결합 감소

회원시스템은 외부 시스템이 어떤 작업을 수행하는지 알 필요 없이 자신의 상태 변화만 발행한다.

### 도메인 로직의 응집도 향상

로그인이나 회원가입과 같은 핵심 행위와 통계, 기록, 알림 같은 부가 작업을 분리할 수 있다.

### 장애 격리

부가 작업이 실패해도 핵심 요청 전체가 실패하지 않는다. 실패한 메시지만 별도로 재시도할 수 있다.

### 독립적인 확장

작업량이 많은 소비자만 개별적으로 확장할 수 있다.

### 이벤트 유실 방지

회원 데이터와 이벤트를 같은 데이터베이스 트랜잭션에 저장해 데이터 변경과 이벤트 기록의 정합성을 보장한다.

### 과거 이벤트 재처리

특정 기간, 회원, 이벤트 타입을 기준으로 필요한 이벤트만 다시 발행할 수 있다.

### 회원 활동 추적

이벤트 저장소를 통해 회원에게 발생한 행위와 상태 변화를 일관된 방식으로 확인할 수 있다.

## 느낀 점

이벤트 기반 아키텍처에서 중요한 것은 메시징 시스템을 사용하는 것 자체가 아니라 어떤 내용을 이벤트로 발행하는지에 있다는 점이 인상 깊었다.
다른 시스템이 해야 할 작업을 직접 지시하기보다 자신의 도메인에서 발생한 사실을 전달해야 서비스 간 결합을 제대로 낮출 수 있다.
또한 이벤트를 비동기로 발행하는 것에서 끝나는 것이 아니라, 이벤트 유실과 재처리까지 함께 설계해야 한다. 이벤트 저장소와 재발행 구조를 통해 실패 이후의 복구 방법을 마련한 점이 특히 인상적이었다.
