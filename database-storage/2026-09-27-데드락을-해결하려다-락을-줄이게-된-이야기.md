신규 유저가 상품을 구매하고 이용까지 완료하면 포인트를 지급하는 이벤트가 있었다.
문제는 한 유저에게 여러 이벤트가 동시에 들어올 수 있다는 점이었다.

```text
한 명의 User

   ├─ 주문 이벤트
   ├─ 이용완료 이벤트
   └─ 취소 이벤트

        ↓

동시에 처리될 수 있음
```

같은 유저의 상태를 여러 요청이 동시에 수정할 수 있기 때문에 처음에는 가장 단순한 방법을 선택했다.
> 같은 유저의 상태를 변경할 때 비관적 락을 걸자.
그런데 동시성 테스트를 돌리자 예상하지 못한 에러가 발생했다.

```text
Deadlock found when trying to get lock;
try restarting transaction
```

결국 문제를 해결하는 과정은 **락을 더 잘 거는 것**이 아니라,
**왜 이렇게 많은 락이 필요한 구조가 되었는지 찾아가는 과정**이 됐다.

---

## 1. 먼저 이벤트 처리 구조

이벤트는 Kafka를 통해 비동기로 처리되고 있었다.
> 원문 이미지: [원문에서 보기](https://techblog.gccompany.co.kr/%EB%8D%B0%EB%93%9C%EB%9D%BD%EC%9D%84-%ED%95%B4%EA%B2%B0%ED%95%98%EB%A0%A4%EB%8B%A4-%EB%9D%BD%EC%9D%84-%EC%A4%84%EC%9D%B4%EA%B2%8C-%EB%90%9C-%EC%9D%B4%EC%95%BC%EA%B8%B0-97bf2b0c91b6)
여기에는 두 가지 문제가 있었다.

```text
1. Kafka At-Least-Once
   → 같은 이벤트가 중복 전달될 수 있음

2. 서로 다른 Topic
   → 이벤트 간 처리 순서를 보장할 수 없음
```

예를 들어 실제 비즈니스 순서는

```text
주문 → 이용완료 → 취소
```

였더라도 Consumer에서는

```text
취소 → 주문 → 이용완료
```

처럼 처리될 가능성이 있다.

## 2. 같은 user_id를 Kafka Key로 쓰면 안 될까?

Kafka에서는 같은 Partition 내부의 순서를 보장한다.
그래서 보통

```text
key = user_id
```

로 설정하면 같은 유저의 이벤트를 같은 Partition으로 보낼 수 있다.

```text
Topic A

Partition 0

User 1
User 1
User 1

→ 순서 보장
```

하지만 여기서는 이벤트가 **서로 다른 Topic**에 있었다.

```text
Order Topic
   │
   └─ user 1

Checkout Topic
   │
   └─ user 1

Cancel Topic
   │
   └─ user 1
```

Kafka의 순서 보장은

```text
같은 Topic
+
같은 Partition
```

안에서만 성립한다.
따라서 `user_id`가 같더라도 서로 다른 Topic 사이의 순서는 보장되지 않는다.
결국 애플리케이션과 DB에서 동시성을 안전하게 처리해야 했다.

## 3. DB 구조

두 개의 주요 테이블이 있었다.
> 원문 이미지: [원문에서 보기](https://techblog.gccompany.co.kr/%EB%8D%B0%EB%93%9C%EB%9D%BD%EC%9D%84-%ED%95%B4%EA%B2%B0%ED%95%98%EB%A0%A4%EB%8B%A4-%EB%9D%BD%EC%9D%84-%EC%A4%84%EC%9D%B4%EA%B2%8C-%EB%90%9C-%EC%9D%B4%EC%95%BC%EA%B8%B0-97bf2b0c91b6)
유저별 전체 이벤트 상태는 `rookie_reward`에 저장하고, 개별 주문의 처리 상태는 `rookie_reward_step`에 저장했다.
`rookie_reward`는 유저당 하나의 row만 존재하면서 전체 진행 상태를 관리한다
반면 `rookie_reward_step`은 주문마다 하나씩 row가 쌓이는 구조이다.

## 4. 처음 생각: User Row를 Mutex처럼 사용하자

같은 User의 이벤트가 동시에 처리될 수 있으니

```text
rookie_reward
```

의 한 Row를 잠그기로 했다.

```text
Transaction A
      │
      ▼
SELECT ... FOR UPDATE
WHERE user_id = 1

      │
      │ X-Lock
      ▼

rookie_reward(User 1)

      ▲
      │ wait
Transaction B
```

이렇게 하면 한 유저에 대한 처리가 직렬화된다.

## 5. 그런데 Row가 아직 없다면?

`FOR UPDATE`는 기본적으로 잠글 Row가 있어야 한다.
그래서 먼저 Row를 생성한 뒤 락을 잡았다.

```text
1. User row 존재 확인

2. 없으면 INSERT

3. SELECT ... FOR UPDATE
```

코드 흐름은 다음과 같았다.

```text
exists?

   │
   ├─ NO → INSERT
   │
   ▼
SELECT ... FOR UPDATE
```

그런데 Kafka는 같은 이벤트를 다시 전달할 수 있기 때문에 생성 과정도 멱등해야 했다.

---

## 6. 중복 INSERT를 어떻게 처리할까?

후보는 세 가지였다.

```text
REPLACE INTO

INSERT IGNORE

INSERT ... ON DUPLICATE KEY UPDATE
```

#### REPLACE INTO

```text
기존 Row 존재

DELETE

새 Row INSERT
```

기존 누적 상태가 사라질 수 있기 때문에 사용할 수 없었다.

#### INSERT IGNORE

```text
없음 → INSERT

있음 → Duplicate 무시
```

#### ON DUPLICATE KEY UPDATE

```text
없음 → INSERT

있음 → UPDATE
```

처음에는 이 방식이 가장 명확해 보여 사용했다.

---

## 7. ON DUPLICATE KEY UPDATE의 문제

실제로 변경할 데이터가 없는데도 중복이면 UPDATE가 실행됐다.

```sql
INSERT INTO rookie_reward (...)
VALUES (...)
ON DUPLICATE KEY UPDATE
updated_at = NOW();
```

즉 이미 User Row가 존재해도

```text
Duplicate 발견
      │
      ▼
UPDATE 수행
      │
      ▼
Row Lock
      │
      ▼
Redo / 변경 비용
```

이 발생한다.
더 문제는 이 Row가 여러 이벤트에서 계속 접근하는 **Hot Row**였다는 것이다.

```text
Order Event ───────┐
Checkout Event ────┼──▶ rookie_reward(User 1)
Cancel Event ──────┘
```

그래서 불필요한 UPDATE를 없애기 위해 `INSERT IGNORE`로 변경했다.

---

## 8. 그런데 INSERT IGNORE로 바꾸자 데드락이 발생했다

변경한 구조는 단순했다.

```text
INSERT IGNORE
      │
      ▼
SELECT ... FOR UPDATE
```

하지만 동시성 테스트를 돌리자 데드락이 발생했다.

```text
Deadlock found when trying to get lock
```

원인은 **INSERT IGNORE가 중복을 확인할 때 잡는 S-Lock**이었다.

---

## 9. INSERT IGNORE 내부 동작

이미 User Row가 있다고 해보자.

```text
rookie_reward

user_id = 1
```

Transaction A가 실행된다.

```text
INSERT IGNORE user_id = 1
```

중복 Key인지 확인해야 한다.
이 과정에서 해당 Record에 **S-Lock(Shared Lock)** 을 잡는다.

```text
Transaction A

        S-Lock
           │
           ▼

    user_id = 1
```

그런데 S-Lock은 여러 Transaction이 동시에 가질 수 있다.

```text
Transaction A ── S ──┐
                     ▼
                 User 1
                     ▲
Transaction B ── S ──┘
```

여기까지는 문제가 없다.
S-Lock끼리는 호환되기 때문이다.

---

## 10. 그다음 FOR UPDATE가 실행된다

****S-Lock vs X-Lock****

| **구분** | **S-Lock (Shared Lock)** | **X-Lock (Exclusive Lock)** |
| --- | --- | --- |
| 의미 | **공유 락** | **배타 락** |
| 주로 사용 | 데이터 **읽기(Read)** | 데이터 **수정(Write)** |
| 다른 S-Lock | ✅ 허용 | ❌ 불가 |
| 다른 X-Lock | ❌ 불가 | ❌ 불가 |
| 목적 | 읽는 동안 데이터 변경 방지 | 수정하는 동안 다른 접근 제한 |

#### **핵심**

- **S-Lock**: 여러 트랜잭션이 **동시에 읽을 수 있음**, 수정은 못 함.
- **X-Lock**: 한 트랜잭션이 **독점**, 다른 트랜잭션의 S/X-Lock 획득을 막음.

```text
             요청
보유 Lock    S-Lock    X-Lock
-----------------------------
S-Lock        O          X
X-Lock        X          X
```

한 줄로 기억하면:
**S = 같이 읽기 가능 / X = 나만 사용**

다음 코드가 문제였다.

```text
INSERT IGNORE

      ↓

SELECT ... FOR UPDATE
```

`FOR UPDATE`는 Row를 변경할 가능성이 있으므로 **X-Lock(Exclusive Lock)** 이 필요하다.
Transaction A 입장에서는

```text
S-Lock

   ↓

X-Lock 필요
```

가 된다.
Transaction B도 똑같다.

```text
Transaction A

S 보유
│
└── X 요청
        │
        │ Transaction B의 S 때문에 대기


Transaction B

S 보유
│
└── X 요청
        │
        │ Transaction A의 S 때문에 대기
```

결국

```text
Transaction A
      │
      │ B의 S-Lock을 기다림
      ▼
Transaction B
      ▲
      │ A의 S-Lock을 기다림
      │
```

순환 대기가 만들어진다.
**Deadlock**이다.

---

## 11. S → X Lock Upgrade Deadlock

전체 흐름을 다시 보면 명확하다.

```text
Transaction A                 Transaction B

INSERT IGNORE                 INSERT IGNORE

      │                             │
      ▼                             ▼

S-Lock(User1)                S-Lock(User1)

      │                             │
      ▼                             ▼

FOR UPDATE                    FOR UPDATE

      │                             │
      ▼                             ▼

X-Lock 요청                  X-Lock 요청

      │                             │
      ▼                             ▼

B의 S 때문에 WAIT           A의 S 때문에 WAIT

           \                 /
            \               /
             ─── DEADLOCK ──
```

처음에는
> UPDATE를 줄였으니 더 좋은 구조겠지?
라고 생각했지만,
실제로는 **앞 Query가 어떤 락을 남기고 다음 Query가 어떤 락을 요구하는지**까지 함께 봐야 했다.

---

## 12. 그런데 왜 ON DUPLICATE KEY UPDATE에서는 괜찮았을까?

두 방식의 차이는 락 흐름이었다.

#### INSERT IGNORE

```text
Duplicate 발생

      ↓

S-Lock

      ↓

FOR UPDATE

      ↓

X-Lock Upgrade
```

동시에 여러 Transaction이 S-Lock을 보유할 수 있기 때문에 승격 과정에서 데드락이 생길 수 있다.
반대로 기존의 `ON DUPLICATE KEY UPDATE`는 중복 시 실제 UPDATE를 수행하는 구조였기 때문에 처음부터 쓰기와 관련된 락을 요구하게 된다.
즉 문제는 단순히

```text
INSERT IGNORE가 나쁘다
```

가 아니라,

```text
INSERT IGNORE
      +
FOR UPDATE
```

라는 **쿼리 조합의 락 흐름**이었다.

---

## 13. 그런데 데드락이 하나 더 있었다

첫 번째 문제를 분석하고 코드를 더 따라가자 또 다른 패턴이 발견됐다.
대부분 이벤트는

```text
rookie_reward
      │
      ▼
rookie_reward_step
```

순서로 락을 잡았다.
그런데 일부 경로는 반대였다.

```text
rookie_reward_step
      │
      ▼
rookie_reward
```

각각만 보면 문제가 없어 보인다.
하지만 동시에 실행되면 달라진다.

---

## 14. 두 번째 데드락: ABBA

Transaction A:

```text
Reward Lock
     │
     ▼
Step Lock
```

Transaction B:

```text
Step Lock
     │
     ▼
Reward Lock
```

동시에 실행하면

```text
Transaction A

Reward Lock 획득
     │
     ▼
Step Lock 기다림
     │
     │
     │
     ▼

Transaction B

Step Lock 획득
     │
     ▼
Reward Lock 기다림
```

즉

```text
A는 B를 기다림

B는 A를 기다림
```

전형적인 **ABBA Deadlock**이다.

---

## 15. 해결: 락 순서를 통일한다

모든 경로에서

```text
rookie_reward
       ↓
rookie_reward_step
```

순서로 락을 잡도록 통일했다.

```text
Transaction A

Reward
  │
  ▼
Step


Transaction B

Reward
  │
  ▼
Step
```

이제 한 Transaction이 Reward를 가지고 있으면 다른 Transaction은 처음부터 기다린다.

```text
A

Reward Lock
    │
    ▼
Step Lock


B

Reward Lock WAIT
```

반대 방향의 순환 대기가 만들어지지 않는다.

---

## 16. 그런데 Step을 먼저 조회해야 User ID를 알 수 있었다

일부 경로에서는 구조적인 문제가 있었다.

```text
step
 │
 │ 여기서 userId 확인
 ▼
reward
```

따라서 Step을 아예 먼저 조회하지 않을 수는 없었다.
그래서
**조회와 락 획득을 분리**했다.

```text
Step 일반 조회
      │
      ▼
userId 확인
      │
      ▼
Reward Lock
      │
      ▼
Step Lock
```

이제 실제 락 획득 순서는 다른 이벤트와 동일하게 유지할 수 있었다.

---

## 17. 그런데 JPA 1차 캐시 문제가 생겼다

Step을 먼저 조회했기 때문에 JPA Persistence Context에는 이미 Step 객체가 존재한다.

```text
1차 캐시

Step(id=1)
status = OLD
```

그다음 다시

```text
SELECT ... FOR UPDATE
```

를 해도 DB에는 최신 데이터를 대상으로 락이 잡히지만, 애플리케이션에서는 이미 가지고 있던 Entity를 사용할 수 있다.

```text
DB

status = NEW
Lock 획득


Application

status = OLD
```

즉,
> DB에는 최신 Row를 잠갔는데 애플리케이션은 이전 객체를 보고 있는 상황
을 고려해야 했다.
그래서

```java
entityManager.refresh(
    step,
    LockModeType.PESSIMISTIC_WRITE
);
```

를 이용해 DB의 최신 상태를 다시 읽으면서 락을 획득하도록 했다.

## 18. 그런데 더 근본적인 질문이 생겼다

두 종류의 데드락을 해결했지만 하나의 의문이 남았다.
> 왜 모든 이벤트가 `rookie_reward`를 잠가야 하지?
이 테이블에는 다음과 같은 Counter들이 있었다.

```text
orderCounter

checkoutCounter

rewardCounter
```

각 이벤트가 들어올 때마다 Counter를 증가시켰다.

```text
Order Event
     │
     ▼
orderCounter++


Checkout Event
     │
     ▼
checkoutCounter++


Reward Event
     │
     ▼
rewardCounter++
```

즉 이벤트 종류는 달라도 마지막에는 항상 같은 Row를 UPDATE했다.

---

## 19. 결국 이 Row가 Hot Row가 됐다

한 유저에게 이벤트가 몰리면

```text
Order ─────────┐
Checkout ──────┤
Cancel ────────┼──▶ rookie_reward(User 1)
Reward ────────┘
```

모든 Transaction이 한 Row 앞에서 기다린다.

```text
                    rookie_reward
                       User 1
                         ▲
                         │
       ┌─────────────────┼─────────────────┐
       │                 │                 │
    Tx A WAIT         Tx B WAIT         Tx C WAIT
```

이 자체가 바로 Deadlock을 의미하는 것은 아니다.
하지만 락 대기 시간이 늘어나고, 여러 Transaction이 다른 Row Lock까지 함께 오래 보유하게 된다.
결과적으로 **락이 서로 얽힐 가능성 자체가 커진다.**

## 20. 질문을 바꿨다

처음 질문은
> 이 Row를 어떻게 안전하게 잠글까?
였다.
하지만 이제는
> **정말 이 Row를 계속 수정해야 할까?**
로 바뀌었다.
Counter를 살펴보니 사실 `rookie_reward_step`에서 계산할 수 있는 값이었다.

```text
기존

rookie_reward

checkoutCounter = 5
```

대신

```text
rookie_reward_step

CHECKOUT
CHECKOUT
CHECKOUT
CHECKOUT
CHECKOUT

      ↓

COUNT = 5
```

처럼 계산할 수 있었다.

---

## 21. Counter를 없앤다

한 User에게 생성되는 Step 수가 현실적으로 수백 건 이하였기 때문에, 매번 Count Query를 수행하는 비용을 감당할 수 있다고 판단했다.

```text
AS-IS

Event
  │
  ▼
Counter +1
  │
  ▼
rookie_reward UPDATE
  │
  ▼
Lock 필요
```

변경 후:

```text
TO-BE

필요한 시점
    │
    ▼
reward_step 조회
    │
    ▼
COUNT 계산
```

즉 Counter 컬럼 몇 개를 없앤 것이 중요한 것이 아니다.
**Counter UPDATE가 없어지면서 Lock을 잡아야 할 이유 자체가 사라졌다.**

---

## 22. FOR UPDATE도 제거할 수 있었다

Counter를 제거하니 대부분의 이벤트에서 `rookie_reward`를 수정하지 않아도 됐다.
그러면 당연히

```text
SELECT ... FOR UPDATE
```

도 필요하지 않다.
기존:

```text
INSERT
   │
   ▼
FOR UPDATE
   │
   ▼
상태 변경
```

변경:

```text
INSERT
   │
   ▼
일반 SELECT
   │
   ▼
필요한 경우에만 상태 변경
```

Lock을 잘 관리하는 대신 **Lock 자체를 줄였다.**

---

## 23. INSERT 작업도 짧은 Transaction으로 분리

최종적으로 생성 작업은 `REQUIRES_NEW`로 분리했다.

```java
@Transactional(
    propagation = Propagation.REQUIRES_NEW
)
public Optional<RookieReward> getOrCreateUserInfo(...) {

    rookieRewardRepository.insertNewUser(...);

    return rookieRewardRepository.findByUserId(userId);
}
```

**`Propagation.REQUIRES_NEW`란?**
Spring의 `@Transactional` 옵션으로, **기존 트랜잭션을 잠시 중단하고 새로운 트랜잭션을 시작하라**는 뜻입니다.
이 글에서는 새 트랜잭션 안에서 `INSERT IGNORE → SELECT → COMMIT`을 빠르게 끝내서:
- `INSERT IGNORE`가 잡은 락을 빨리 해제하고
- 최신 데이터로 다시 조회하려는 목적입니다.
새 트랜잭션의 커밋·롤백은 바깥 트랜잭션과 독립적입니다. 대신 동시에 DB 커넥션을 하나 더 사용하므로 커넥션 풀 크기를 고려해야 합니다.

왜 굳이 새로운 Transaction을 사용할까?
`INSERT IGNORE`가 중복을 확인하면서 잡은 S-Lock은 SQL이 끝났다고 바로 없어지는 것이 아니라 **Transaction 종료까지 유지될 수 있다.**

---

## 24. 긴 Transaction에서는 Lock도 오래 살아있다

기존 구조:

```text
┌──────────────── Long Transaction ────────────────┐

INSERT IGNORE

     │ S-Lock 획득

     ▼

여러 비즈니스 로직

     ▼

다른 DB 작업

     ▼

Commit

     │
     └── 여기서 Lock 해제

└───────────────────────────────────────────────────┘
```

Lock을 오래 가지고 있게 된다.
변경 후:

```text
Outer Transaction


        ┌── REQUIRES_NEW ──┐

        INSERT IGNORE
             │
             ▼
           SELECT
             │
             ▼
           COMMIT
             │
         Lock Release

        └───────────────────┘


Outer Transaction 계속
```

즉 Lock의 생명주기가

```text
전체 메시지 처리시간
```

에서

```text
User 생성 처리시간
```

으로 짧아졌다.

---

## 25. REQUIRES_NEW에는 또 하나의 이유가 있었다

MySQL InnoDB의 기본 `REPEATABLE READ`에서는 바깥 Transaction에서 이미 조회가 발생한 경우 기존 Read View를 사용할 가능성을 고려해야 했다.

```text
Outer Transaction

SELECT
  │
  ▼
Read View 생성

       ↓

다른 Transaction
INSERT + COMMIT

       ↓

Outer Transaction에서
다시 SELECT
```

기존 Snapshot 때문에 최신 Row를 바로 보지 못할 가능성을 고려한 것이다.
그래서 생성과 조회를 새로운 Transaction에서 처리했다.

```text
REQUIRES_NEW

새 Transaction
     │
     ▼
INSERT IGNORE
     │
     ▼
새로운 조회
     │
     ▼
COMMIT
```

결과적으로 `REQUIRES_NEW`는

```text
① 생성 과정 Lock 수명 단축

② 생성 직후 조회 최신성 확보
```

두 역할을 하게 됐다.

---

## 26. 물론 REQUIRES_NEW도 공짜는 아니다

바깥 Transaction이 Connection 하나를 사용하고 있는 상태에서 새로운 Transaction을 실행한다.

```text
Outer TX

Connection 1
    │
    │ 유지
    │

REQUIRES_NEW

Connection 2
```

따라서 동시 Consumer 수가 많다면 Connection Pool을 고려해야 한다.
또 내부 Transaction에서 반환된 Entity는 바깥 Persistence Context에서는 **Detached 상태**가 된다.
그래서 반환 Entity는 수정 용도가 아니라

```text
존재 여부

식별 정보
```

를 확인하는 용도로만 사용했다.

---

## 27. Redis 분산 락은 왜 사용하지 않았을까?

다른 선택지도 있었다.

```text
User 1

       │
       ▼

Redis Distributed Lock

       │
       ▼

DB Update
```

하지만 실제 보호 대상은 DB Row다.
Redis Lock을 추가하면

```text
Redis Lock 획득
        │
        ▼
DB Transaction
        │
        ▼
DB Commit
        │
        ▼
Redis Lock Release
```

라는 두 시스템 간 상태를 관리해야 한다.
장애가 발생하면

```text
Redis Lock 해제

vs

DB Commit
```

시점이 어긋나는 문제까지 고려해야 한다.
반면 DB Row Lock은

```text
DB Transaction Commit

        =

DB Lock Release
```

를 같은 시스템에서 관리한다.
따라서 굳이 외부 Lock 시스템을 추가하지 않았다.

## 28. 낙관적 락은 왜 사용하지 않았을까?

`@Version`을 사용하는 Optimistic Lock도 후보였다.

```text
Tx A

version = 1
UPDATE


Tx B

version = 1
UPDATE

      ↓

Version Conflict
```

한 Transaction은 실패하고 Retry해야 한다.
하지만 이 시스템에서는 같은 User에게 이벤트가 동시에 몰릴 가능성이 있었다.

```text
Conflict
   │
   ▼
Retry
   │
   ▼
Conflict
   │
   ▼
Retry
```

충돌 자체가 드물다고 보기 어려웠다.
그래서 당시 상황에서는 DB에서 순차적으로 처리하는 방식이 더 단순하다고 판단했다.

## 29. 전체 변화

#### 처음

```text
Event
  │
  ▼
ON DUPLICATE KEY UPDATE
  │
  ▼
FOR UPDATE
  │
  ▼
rookie_reward Counter UPDATE
  │
  ▼
rookie_reward_step UPDATE
```

문제:

```text
불필요한 UPDATE

Hot Row

긴 Lock

높은 경합
```

---

#### 중간

```text
Event
  │
  ▼
INSERT IGNORE
  │
  │ S-Lock
  ▼
FOR UPDATE
  │
  │ X-Lock
  ▼
Update
```

문제:

```text
S → X Lock Upgrade

       ↓

Deadlock
```

그리고 일부 요청에서는

```text
reward → step

vs

step → reward
```

로 Lock 순서까지 달라 ABBA Deadlock이 있었다.

---

#### 최종

```text
                    Event
                      │
                      ▼

             User 정보 존재 확인
                      │
                      ▼

             ┌─ REQUIRES_NEW ─┐
             │                │
             │ INSERT IGNORE  │
             │       │        │
             │       ▼        │
             │    SELECT      │
             │       │        │
             │     COMMIT     │
             └────────────────┘
                      │
                      ▼
              실제 이벤트 처리
                      │
                      ▼
              rookie_reward_step
                      │
                      ▼
             필요한 상태만 변경


rookie_reward Counter 제거

FOR UPDATE 대부분 제거
```

즉 최종 해결책은

```text
더 강한 Lock

        X

Lock을 덜 필요로 하는 데이터 구조
```

였다.

## 30. 동시성 테스트

변경 후 기존에 Deadlock을 재현했던 조건으로 다시 테스트했다.
결과적으로 해당 테스트에서는 Deadlock이 더 이상 발생하지 않았다.
제거한 조건은 다음과 같다.

```text
S-Lock → X-Lock 승격 구조 제거

락 획득 순서 통일

불필요한 Hot Row UPDATE 제거

생성 시 잡은 Lock의 수명 단축
```

다만
> 앞으로 어떤 상황에서도 Deadlock이 절대 발생하지 않는다.
는 의미는 아니다.
실제로 발생했던 Deadlock 조건을 제거했다는 의미다.

---

## 31. 그래도 데드락은 발생할 수 있다

InnoDB는 Deadlock을 발견하면 한 Transaction을 선택해 Rollback한다.
Kafka Consumer 입장에서는 해당 메시지가 정상 처리되지 않았으므로 Offset Commit 역시 완료되지 않을 수 있다.
그러면 같은 메시지가 다시 소비될 수 있다.

```text
Kafka Event
     │
     ▼
Transaction
     │
     X Deadlock
     │
     ▼
Rollback

Offset Commit X
     │
     ▼
Event 재소비
```

그래서 애플리케이션 자체가 재실행되어도 같은 결과를 만들어야 한다.

```text
생성

→ INSERT IGNORE


상태 변경

→ 현재 상태를 기준으로 멱등 처리
```

Kafka의 At-Least-Once와 DB Transaction을 함께 고려한 것이다.

## 정리

처음에는 문제를 이렇게 봤다.

```text
동시 요청 발생

      ↓

비관적 락으로 막자
```

하지만 실제로는 락 하나의 문제가 아니었다.

```text
INSERT IGNORE
      +
FOR UPDATE
      ↓
Lock Upgrade Deadlock


서로 다른 Lock 순서
      ↓
ABBA Deadlock


Counter를 위한 공통 Row UPDATE
      ↓
Hot Row
      ↓
Lock 경합 증가
```

결국 중요한 질문은
> **락을 어떻게 더 안전하게 걸까?**
가 아니었다.

```text
정말 이 데이터는
동시에 수정되어야 하는가?

        ↓

정말 UPDATE가 필요한가?

        ↓

정말 FOR UPDATE가 필요한가?

        ↓

정말 이 Lock이 필요한가?
```

였다.
이 사례의 핵심은 데드락을 발견한 뒤 Retry를 추가하거나 더 강한 락을 사용한 것이 아니다.
**데이터 구조를 다시 살펴보고, Counter와 불필요한 UPDATE를 제거하면서 락을 필요로 하는 이유 자체를 줄였다는 점**이다.
결국 동시성 문제를 만났을 때는

```text
어떤 Lock을 잡는가?

얼마나 오래 잡는가?

어떤 순서로 잡는가?

        +

애초에 그 Lock이 필요한가?
```

까지 함께 봐야 한다.
**좋은 Lock 설계는 락을 잘 거는 것에서 끝나는 게 아니라, 필요 없는 락을 없애는 것까지 포함한다.**
