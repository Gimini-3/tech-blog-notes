카카오톡 메시징 서버는 평소에도 대규모 트래픽을 처리하지만, 특정 순간에는 평소와 전혀 다른 형태의 부하를 받는다.
대표적으로

```text
평소 메시징 트래픽

메시지 전송
채팅방 입장
채팅방 목록 조회
메시지 조회

        ↓

비교적 고른 분포
```

와

```text
신년 00:00

"새해 복 많이 받아!"

        ↓

메시지 전송 요청 폭증
```

은 서버가 받는 부하의 모양 자체가 다르다.
그래서 카카오 톡메시징팀은 **서버가 어느 지점에서 한계를 드러내는지 미리 확인하기 위한 상시 스트레스 테스트 환경**을 운영하고 있다. 여기서 스트레스 테스트는 시스템의 한계를 넘는 트래픽 급증이나 자원 고갈 상황을 만들어 장애 발생 지점과 복구 능력을 확인하는 성능 검증이다.

---

## 1. 스트레스 테스트는 단순히 RPS를 많이 넣는 테스트가 아니다

처음에는 이렇게 생각하기 쉽다.

```text
Client

요청 요청 요청 요청 요청
        │
        ▼
      Server
        │
        ▼
"몇 RPS까지 버티지?"
```

하지만 실제 목적은 더 깊다.

```text
부하 증가
   │
   ▼
Latency 변화
   │
   ▼
어떤 Resource가 먼저 포화?
   │
   ▼
왜 포화?
   │
   ▼
어떤 코드 / 설정이 원인?
```

즉 스트레스 테스트는 **성능 측정이면서 동시에 병목을 찾아가는 디버깅 과정**에 가깝다.

---

## 2. 테스트 환경은 두 축으로 나뉜다

카카오의 스트레스 테스트 환경은 크게 두 서버군으로 구성된다.

```text
┌────────────────────┐
│ Stress Clients     │
│                    │
│ Locust Workers     │
└─────────┬──────────┘
          │
          │ Traffic
          ▼
┌────────────────────┐
│ Target Servers     │
│                    │
│ 실제 서버와 동일 스펙 │
└────────────────────┘
```

#### Target Server

테스트 대상 서버는 운영 서버와 최대한 동일한 조건을 유지한다.

```text
JVM Heap

CPU

Memory Limit

Network

Runtime 설정
```

장비 조건이 달라지면 측정 결과 자체의 의미가 약해지기 때문이다.

---

## 3. 부하 발생기는 Locust를 사용한다

부하를 만드는 쪽에서는 주로 **Locust**를 사용한다.

```text
Locust Master
      │
      ├─ Worker 1
      ├─ Worker 2
      ├─ Worker 3
      ├─ ...
      └─ Worker N
```

필요하면 수백 개 Pod까지 확장한다.

```text
평소

Worker × 10


Stress Test

Worker × 300
```

여기서 중요한 것은 **클라이언트가 먼저 병목이 되면 안 된다는 것**이다.

```text
원하는 것

Client 여유 있음
      │
      ▼
Server가 먼저 한계 도달


원하지 않는 것

Client CPU 100%
      │
      ▼
Traffic 생성 못함
      │
      ▼
"Server가 한계인가?" 착각
```

따라서 부하 발생 클라이언트에는 넉넉한 자원을 할당해 측정 노이즈를 줄인다. 일부 테스트에서는 JMH도 사용한다.

---

## 4. 실제 서비스와 같은 트래픽 비율을 만들어야 한다

RPS가 같아도 요청 종류가 다르면 서버가 받는 부하는 전혀 다를 수 있다.
카카오 메시징의 예를 보면 평시와 신년 자정의 요청 비율이 다르다.

```text
                평시          신년 00시

메시지 전송      52%            61%

채팅방 입장      23%            27%

채팅방 목록      18%             8%

메시지 조회       7%             4%
```

신년에는 **Write 계열 요청의 비중이 증가한다.**
따라서 단순하게

```text
100K RPS
```

만 맞추는 것이 아니라

```text
100K RPS

├─ Send 61K
├─ Join 27K
├─ Room List 8K
└─ Read 4K
```

처럼 실제 트래픽 형태를 재현해야 한다.

---

## 5. 테스트 시나리오는 설정값 조합으로 만든다

새로운 시나리오가 생길 때마다 부하 코드를 처음부터 새로 만들지는 않는다.
카카오에서는 여러 설정값을 조합해 다양한 시나리오를 만든다.

```text
Stress Scenario

├─ Task 비율
│
├─ directChatCount
│
├─ multiChatCount
│
├─ maxFriendCount
│
└─ target module
```

예를 들어

```text
시나리오 A

1:1 채팅 위주
친구 수 적음
평시 Traffic
```

와

```text
시나리오 B

대형 단톡방
친구 수 수백 명
메시지 Write 비중 ↑
```

를 설정값만 바꿔 빠르게 재현할 수 있다.

## 6. 어떤 변경에 스트레스 테스트를 할까?

모든 코드 변경마다 대규모 스트레스 테스트를 돌리는 것은 아니다.
주로

```text
성능에 영향을 줄 가능성이 있는 변경

        또는

과거 장애가 발생했던 영역

        또는

큰 구조 변경
```

을 대상으로 한다.
대표적으로 네 가지 사례가 있다.

```text
A. Observability / Logging

B. Protocol / Framework

C. OS / Security Infrastructure

D. Domain Worst Scenario
```

---

## 7. Case A — 로그나 메트릭 추가도 성능 테스트 대상이다

관측성 기능은 공짜가 아니다.
예를 들어

```text
Application
   │
   ├─ Business Logic
   │
   ├─ Metrics
   │
   ├─ Logging
   │
   └─ Tracing
```

이 있다.
Metric 수집 주기가 지나치게 짧거나 로깅량이 너무 많으면

```text
Metric 수집 증가
      │
      ▼
CPU 증가

Memory 증가

Network 증가
```

가 발생할 수 있다.
카카오에서도 과거 메트릭 수집 주기로 인해 실제 Application Load가 증가한 경험이 있었고, 이후 Logstash, Fluent Bit, OpenTelemetry 같은 관측 인프라 변경에도 성능 검증을 수행한다.

---

## 8. Case B — WebFlux냐 Virtual Thread냐도 숫자로 결정한다

기술 선택을

```text
"WebFlux가 I/O에 좋다"

"Virtual Thread가 좋다"
```

라는 일반론만으로 결정하지 않는다.
실제로 후보를 같은 환경에 올린다.

```text
                같은 Traffic

                     │

       ┌─────────────┴────────────┐
       ▼                          ▼

    Framework A               Framework B

       │                          │
       ▼                          ▼

RPS / Latency / CPU       RPS / Latency / CPU
```

그리고 CPU Bound와 I/O Bound 조건을 따로 변화시키며 비교한다.
카카오 메시징의 C++ → Kotlin 포팅에서도 스트레스 테스트를 통해 시스템 메트릭 차이를 확인했고, 결과를 바탕으로 GC 튜닝까지 진행했다.

---

## 9. Case C — OS나 백신도 장애 원인이 될 수 있다

애플리케이션 코드는 그대로인데 서버 성능이 나빠질 수도 있다.
예를 들어

```text
OS 변경

보안 Agent

백신

Monitoring Agent
```

도 Resource를 사용한다.

```text
Application
    │
    ├─ CPU
    ├─ Memory
    └─ I/O

Security Agent
    │
    ├─ CPU
    ├─ Memory
    └─ I/O
```

트래픽이 낮을 때는 티가 안 나지만 고부하에서는 병목으로 드러날 수 있다.
카카오는 OS 변경이나 보안·모니터링 Agent 추가 역시 스트레스 테스트 후 운영에 적용한다.

---

## 10. Case D — 도메인 최악의 상황을 재현한다

메시징 서비스에는 일반적인 API 서버와 다른 극단적인 상황이 있다.

```text
한 채팅방에서
수백 명이 동시에 Write


신년 00:00
메시지 Burst


수백 명 단톡방
동시 입장
```

이런 트래픽은 평균 Traffic만 테스트해서는 발견하기 어렵다.

```text
Average Traffic

      O


Worst Case Burst

      X?
```

그래서 실제 서비스에서 발생 가능한 최악의 패턴을 별도 Scenario로 만든다.

## 11. 테스트가 끝나면 가장 먼저 Endpoint부터 본다

테스트 결과를 분석하는 순서도 중요하다.
카카오의 접근은 바깥에서 안쪽으로 내려가는 형태다.

```text
Layer 1

Endpoint


   ↓ 문제 있음


Layer 2

System Resource


   ↓


Layer 3

JVM Runtime


   ↓


Layer 4

Object / Code
```

즉 처음부터 Heap Dump를 뜨는 것이 아니다.

---

## 12. Layer 1 — RPS

가장 먼저 처리량을 본다.

```text
User 증가

10
20
50
100
200
300

    │
    ▼

RPS
```

정상이라면 어느 시점까지는 거의 선형으로 증가한다.

```text
RPS
│
│              /
│            /
│          /
│        /
│      /
│____/____________ User
```

그런데 포화 상태가 되면

```text
RPS
│
│          ─────────
│        /
│      /
│    /
│___/_______________ User
          ↑
        Saturation
```

처럼 더 이상 증가하지 않는다.
이 지점이 서버 처리량의 한계 후보가 된다.

---

## 13. Layer 1 — P50 / P95 / P99 Latency

평균 응답시간 하나만 보면 Tail Latency를 놓칠 수 있다.

```text
P50
→ 일반 사용자

P95
→ 느린 상위 5%

P99
→ 가장 느린 상위 1%
```

예를 들어

```text
RPS 증가

P50  20ms ──────────────

P95  30ms ────────╮
                   ╰──── 200ms

P99  40ms ──────╮
                 ╰────── 1s
```

처럼 P95/P99가 먼저 튄다면 서버 내부 Queue나 Resource가 포화되고 있다는 신호일 수 있다.

---

## 14. Layer 1 — Error Rate

다음은 에러다.

```text
5xx

Timeout

Business Error / 4xx
```

에러 종류에 따라 의심할 영역이 달라진다.

```text
5xx 증가
→ 서버 처리 한계 / 내부 실패 의심


Timeout 증가
→ 서버 지연 또는 Client 병목


400 증가
→ Test Scenario / Business Logic 확인
```

즉 Error Rate 하나만 보는 게 아니라 **에러 종류를 분리해서 본다.**

---

## 15. Layer 2 — 시스템 자원을 본다

Endpoint에서 이상을 발견했다면 이제 시스템 Resource를 본다.

```text
Endpoint 문제

      │
      ▼

CPU
Memory
Disk I/O
Network
File Descriptor
```

관계는 대략 이렇게 좁힐 수 있다.

```text
CPU ↑
→ Thread / CPU Profile


Memory ↑
→ JVM Heap


Disk / Network I/O ↑
→ 외부 호출 / Client / Thread


Network Bandwidth 포화
→ Network 한계
```

---

## 16. Layer 3 — JVM 상태

시스템 자원에서 문제가 보이면 JVM 내부로 들어간다.

### Thread State

```text
RUNNABLE

WAITING

TIMED_WAITING

BLOCKED
```

예를 들어

```text
BLOCKED ↑

→ Lock 경합 의심
```

```text
WAITING ↑

→ 외부 시스템 응답 / Resource 대기 의심
```

처럼 원인 범위를 좁힐 수 있다.

---

## 17. Executor Queue는 처리량 한계를 미리 보여준다

Thread Pool의 Queue가 계속 증가한다면

```text
Incoming Request
       │
       ▼
   Executor Queue
       │
       ▼
Worker Threads
```

들어오는 속도가 처리 속도보다 빠르다는 뜻이다.

```text
Incoming

100K/s

    ↓

Queue +++++++++++

    ↓

Processing

80K/s
```

차이는 계속 누적된다.

```text
초당

20K씩 Queue 증가
```

결국 Timeout으로 이어질 수 있다.

---

## 18. GC는 다른 병목을 연쇄적으로 만든다

고부하 상황에서 객체 할당량이 급증하면

```text
Traffic ↑
   │
   ▼
Object Allocation ↑
   │
   ▼
Heap ↑
   │
   ▼
GC ↑
```

로 이어진다.
문제가 심해지면

```text
Heap 증가
    │
    ▼
GC Pause 증가
    │
    ▼
CPU Load 증가
    │
    ▼
Executor Queue 증가
    │
    ▼
Read Timeout
```

처럼 하나의 문제가 다른 Resource까지 전파된다.
카카오의 실제 스트레스 테스트에서도 Heap 점유 증가가 GC, CPU, Queue, Timeout으로 이어진 사례가 있었다.

---

## 19. Layer 4 — Heap Dump, CPU Profile, Thread Dump

메트릭만으로 원인을 찾지 못하면 코드 수준으로 내려간다.

#### Heap Dump

```text
JVM Heap
 │
 ├─ Object A 2GB
 ├─ Object B 500MB
 ├─ Object C 300MB
 └─ ...
```

어떤 객체가 살아남고 있는지, 어떤 GC Root에서 참조되는지 확인한다.

#### CPU Profiling

```text
CPU
 │
 ├─ Method A 40%
 ├─ Method B 25%
 ├─ Method C 15%
 └─ ...
```

JFR이나 async-profiler의 Flame Graph로 CPU 소비 위치를 찾는다.

#### Thread Dump

```text
Thread 1

BLOCKED
 at Foo.lock()


Thread 2

WAITING
 at HttpClient.read()
```

어떤 Stack에서 Blocking이나 Waiting이 발생하는지 확인한다.

## 20. 전체 분석은 디버깅 트리처럼 진행한다

```text
                     Stress Test
                         │
                         ▼
                RPS / Latency / Error
                         │
                   정상? ├── YES → 종료
                         │
                         NO
                         ▼
                CPU / Memory / I/O
                         │
                어떤 Resource?
             ┌───────────┼───────────┐
             ▼           ▼           ▼
            CPU        Memory        I/O
             │           │           │
             ▼           ▼           ▼
       CPU Profile      Heap       Thread/
                       / GC        Client
             │           │           │
             └───────────┼───────────┘
                         ▼
                    JVM Runtime
                         │
                         ▼
               Thread / Executor
                         │
                         ▼
                  Object / Stack
                         │
                         ▼
                      Code Fix
```

이게 이 글에서 가장 중요한 스트레스 테스트 분석 방식이다.

---

## 21. 그런데 어디까지 분석해야 할까?

항상 Heap Dump나 Flame Graph까지 갈 필요는 없다.
목적에 따라 다르다.

```text
Endpoint 지표 정상
→ 여기서 종료 가능


System Resource 한계
→ Scale Up / Out


JVM 문제
→ JVM / GC / Thread 튜닝


Object / Method 문제
→ Code Fix
```

즉 테스트의 깊이는 **처음에 설정한 목적**이 결정한다.

## 22. 스트레스 테스트를 의사결정에 쓰는 5가지 원칙

카카오에서는 테스트 결과를 단순 그래프로 끝내지 않고 실제 의사결정 근거로 만들기 위해 다섯 가지 원칙을 둔다.

```text
1. 측정 목적

2. 현재 서비스 구조 분석

3. 후보군 추리기

4. 비교군 통제

5. 결과 정리 및 팀 공유
```

---

## 23. 가장 중요한 원칙은 한 실험에 한 변수

예를 들어 Framework A와 B를 비교한다고 하자.
잘못된 실험:

```text
Before

Java 17
Heap 4GB
Framework A
Worker 32


After

Java 21
Heap 8GB
Framework B
Worker 64
```

결과가 좋아져도 무엇 때문인지 모른다.
좋은 실험:

```text
Before

Framework A

Everything Else Same


After

Framework B

Everything Else Same
```

즉

```text
한 실험 = 한 변수
```

가 중요하다.
TPS, Traffic Pattern, Test Duration, Machine Spec, JVM Heap 등 나머지 조건을 최대한 통제한다.

---

## 24. 대당 성능으로 비교해야 할 때도 있다

운영 서버가 100대인데 테스트 서버를 100대 준비할 수는 없다.
예를 들어

```text
Production

120 Servers


Stress Test

10 Servers
```

라면 총 RPS만 직접 비교하기 어렵다.
그래서

```text
Server당 RPS

Server당 CPU

Server당 Memory
```

를 기준으로 비교한다.
예를 들어

```text
변경 전

CPU 60%
120대 필요


변경 후

CPU 65%
130대 필요 예상
```

라면 단순히

```text
CPU +5%p
```

가 아니라

```text
인프라 +10대
```

라는 운영 의사결정으로 바꿔 표현할 수 있다.

## 25. 스트레스 테스트에서 가장 귀찮은 건 반복이다

한 번의 테스트는 대략 이런 과정으로 이루어진다.

```text
1. Target Build

2. Target Deploy

3. Stress Client Build / Deploy

4. Worker 수백 개 Scale Out

5. Locust 실행

6. 사용자 수 점진적 증가

7. 약 50분간 테스트

8. Grafana 지표 수집

9. 그래프 Capture

10. 결과 Report 작성
```

그런데 설정 하나 바꾸면?

```text
다시 1번부터
```

이다.
실제로 한 테스트에서도 이 과정을 여러 번 반복한다.

## 26. 그래서 AI에는 분석보다 반복 작업부터 맡겼다

팀에서는 Claude Code와 Codex 등을 이용해 반복 업무를 Skill 단위로 나눴다.

```text
/deploy-target

/deploy-stress

/run-stress

/render-dashboard

/make-report
```

각 역할은 다음과 같다.

```text
/deploy-target
→ Server Build + Push + Deploy + Health Check


/deploy-stress
→ Stress Client Build + Deploy + Worker Scale


/run-stress
→ Locust 명령 + Health Check + Traffic Control


/render-dashboard
→ PromQL 조회 + Test 구간 Dashboard HTML 생성


/make-report
→ 지표 Parsing + 분석 Report 생성
```

## 27. LLM은 이 Skill들의 Orchestrator가 된다

작업을 작은 단위로 분리해놓으면 사용자는 이런 식으로 요청할 수 있다.

```text
"Round 3과 같은 조건인데
compression type만
application/json으로 바꿔서 비교해줘."
```

그러면 LLM이

```text
사용자 의도
    │
    ▼
deploy-target
    │
    ▼
deploy-stress
    │
    ▼
run-stress
    │
    ▼
render-dashboard
    │
    ▼
make-report
```

순서로 작업을 조합한다.
즉 AI가 직접 스트레스 테스트라는 거대한 일을 마법처럼 수행하는 것이 아니라, **잘 정의된 작은 Tool들을 선택하고 연결하는 Orchestrator 역할**을 한다.

## 28. Subagent로 지표 수집도 병렬화했다

Dashboard 하나에도 수많은 Metric이 있다.

```text
Heap / GC

Client Pool

System Resource
```

한 Agent가 하나씩 처리하면 오래 걸린다.
그래서

```text
                Main Agent
                    │
       ┌────────────┼────────────┐
       ▼            ▼            ▼
   Subagent A   Subagent B   Subagent C

 Client Metric    JVM         System

       │            │            │
       └────────────┼────────────┘
                    ▼
                 Summary
```

처럼 동시에 분석한다.
Main Context에는 Raw PromQL을 모두 집어넣지 않고 Subagent가 분석한 결론만 전달한다.

## 30. AI에게 맡기기 어려운 것

반대로 AI가 해결하기 어려운 것도 있었다.
가장 중요한 것은 **테스트 방법론 자체에 대한 경험**이다.
처음에는 비교군 두 서버에 같은 RPS를 넣어 비교했다.

```text
Server A ← 10K RPS

Server B ← 10K RPS
```

하지만 저부하와 고부하 사이의 병목 지점을 찾기 어려웠다.
시니어 개발자의 조언은 달랐다.

```text
한 서버에

User 10
  ↓
50
  ↓
100
  ↓
150
  ↓
200

순서로 올려

부하 곡선 전체를 보자.
```

이 접근 덕분에 Baseline과 Saturation Point를 한 그래프에서 볼 수 있게 됐다.

## 31. AI Report는 그럴듯하게 틀릴 수 있다

실제로 자동 생성 Report가

```text
"성능 아주 좋음!"
```

이라고 했지만 실제 환경이 잘못된 사례도 있었다.
한 사례에서는 Client Code 문제 때문에 실제 Server Error가 제대로 감지되지 않았다.
또 다른 사례에서는

```text
Before Image

A


After Image

실제로는 Cache 때문에
여전히 A
```

였는데 AI는 둘의 결과가 같다는 것을

```text
"변경 후 성능도 훌륭합니다."
```

처럼 해석했다.
즉 AI는 제공된 데이터가 잘못됐는지 자동으로 보장해주지 않는다.

## 35. 이 글의 핵심

처음 보면 스트레스 테스트는

```text
Traffic 많이 보내기
       │
       ▼
서버 죽는지 보기
```

처럼 보인다.
하지만 실제로는

```text
실서비스와 비슷한 Scenario 설계
           │
           ▼
부하를 점진적으로 증가
           │
           ▼
RPS / Latency / Error 관찰
           │
           ▼
System Resource 확인
           │
           ▼
JVM Runtime 분석
           │
           ▼
Object / Stack Level 분석
           │
           ▼
병목 원인 규명
           │
           ▼
수정
           │
           ▼
재측정
           │
           ▼
숫자로 의사결정
```

이라는 하나의 **성능 디버깅 Loop**다.
그리고 AI가 가장 잘하는 부분은 그 사이 반복되는

```text
배포

부하 실행

지표 수집

그래프 생성

보고서 초안
```

을 자동화하는 것이다.
반대로

```text
어떤 테스트를 해야 하는가?

무엇이 정상인가?

어떤 Trade-off를 받아들일 것인가?

결과가 정말 믿을 만한가?
```

를 결정하는 것은 여전히 개발자의 역할이다.

## 정리

이 글을 한 줄로 정리하면 이렇다.

```text
스트레스 테스트

= 부하 생성 테스트

X


스트레스 테스트

= 시스템의 한계점을 찾고
  그 원인을 코드까지 추적해
  운영 의사결정의 숫자 근거를 만드는 과정
```

분석 순서는

```text
Endpoint
   ↓
System Resource
   ↓
JVM
   ↓
Object / Stack
```

로 내려가고,
AI 활용은

```text
반복 작업
   ↓
Skill로 분리
   ↓
LLM이 Orchestration
   ↓
Subagent 병렬 분석
   ↓
Report 자동 생성
```

으로 발전했다.
결국 가장 중요한 원칙은
**“AI에게 판단을 맡긴 것이 아니라, 판단에 필요한 반복 작업을 맡겼다.”**
는 점이다.
