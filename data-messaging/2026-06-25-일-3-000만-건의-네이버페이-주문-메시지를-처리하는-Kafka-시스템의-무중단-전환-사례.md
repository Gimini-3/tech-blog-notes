---

대규모 서비스에서 Kafka는 이벤트를 안정적으로 전달하기 위한 핵심 인프라로 자주 사용된다.

하지만 Kafka 기반 시스템은 한 번 구축하고 여러 서비스가 의존하기 시작하면, 시간이 지날수록 변경하기 어려워진다.

특히 주문, 결제, 정산처럼 핵심 도메인과 연결된 메시징 시스템은 단순히 “새 Kafka로 바꾸자” 수준으로 접근할 수 없다.

메시지가 누락되거나 중복 소비되거나 순서가 꼬이면 실제 운영 장애로 이어질 수 있기 때문이다.

이 글에서는 네이버페이 D2의 「일 3,000만 건의 네이버페이 주문 메시지를 처리하는 Kafka 시스템의 무중단 전환 사례」를 읽고, 핵심 내용을 정리해보려 한다.

---

## 1. 기존 주문 메시징 시스템의 역할

네이버페이 주문 시스템에서는 주문과 관련된 다양한 이벤트가 발생한다.

예를 들면 다음과 같다.

```
고객이 결제를 완료했을 때
판매자가 상품을 발송했을 때
택배사가 배송을 완료했을 때
고객이 구매를 확정했을 때
```

이런 주문 흐름은 주문 시스템 내부에서만 끝나는 것이 아니다.

정산, 배송, 알림, 구매 확정, 사용자 주문 내역 등 여러 시스템이 주문 상태 변경을 알아야 한다.

그래서 주문 시스템은 Kafka를 통해 주문 메시지를 발행하고, 여러 컨슈머 서비스가 해당 메시지를 소비하는 구조를 사용하고 있었다.

```
주문 시스템
→ Kafka
→ 정산 서비스
→ 배송 서비스
→ 알림 서비스
→ 주문 내역 서비스
→ 기타 연관 시스템
```

즉, Kafka는 주문 이벤트를 여러 시스템으로 전달하는 중심 통로 역할을 하고 있었다.

---

## 2. 기존 구조: 트랜잭셔널 아웃박스 패턴

기존 주문 메시징 시스템은 트랜잭셔널 아웃박스 패턴을 사용하고 있었다.

주문 이벤트가 발생했을 때 API 서버가 바로 Kafka 메시지를 만드는 방식이 아니라, 먼저 DB 트랜잭션 안에서 Outbox Table에 최소한의 데이터를 저장한다.

```
주문 API
→ 주문 상태 변경
→ Outbox Table에 주문 번호, 주문 액션 타입 저장
→ 트랜잭션 커밋
```

이후 별도의 배치 모듈이 Outbox Table을 주기적으로 조회하면서 메시지를 생성하고 Kafka에 발행한다.

```
Outbox Table
→ Polling Publisher
→ 주문 데이터 조회 및 메시지 생성
→ Kafka 발행
```

이 구조를 사용한 이유는 명확하다.

주문 메시지는 500개 이상의 필드를 가진 대용량 메시지였다.

주문 API가 사용자의 요청을 처리하는 과정에서 이 메시지를 직접 생성한다면 응답 시간이 길어지고 서버 자원도 많이 사용된다.

또한 DB 저장과 Kafka 발행을 분리해서 처리하면 정합성 문제가 발생할 수 있다.

예를 들어 주문 DB 저장은 성공했지만 Kafka 발행이 실패하면, 주문은 생성되었는데 다른 시스템은 그 사실을 모르게 된다.

```
DB 저장 성공
Kafka 발행 실패
→ 정산, 알림, 배송 시스템은 주문 발생 사실을 모름
```

반대로 Kafka 메시지는 발행되었는데 DB 트랜잭션이 실패해도 문제가 된다.

```
Kafka 메시지 발행 성공
DB 저장 실패
→ 실제로 존재하지 않는 주문 이벤트가 전파됨
```

트랜잭셔널 아웃박스 패턴은 이런 문제를 줄이기 위해 사용된다.

주문 상태 변경과 Outbox 기록을 하나의 DB 트랜잭션으로 묶고, 이후 별도 모듈이 Outbox 데이터를 읽어 Kafka에 발행하는 방식이다.

## 3. 기존 구조에서 발생한 문제

기존 아키텍처는 오랫동안 잘 동작했지만, 네이버페이 주문량이 늘어나면서 몇 가지 문제가 발생했다.

### 3.1 공용 Kafka 리소스 경쟁

기존에는 주문 메시지 전용 Kafka가 아니라 공용 Kafka를 사용하고 있었다.

```
공용 Kafka 클러스터
├── 주문 메시지 토픽
├── 알림 메시지 토픽
├── 정산 메시지 토픽
├── 로그 메시지 토픽
└── 기타 서비스 토픽
```

공용 Kafka를 사용하면 여러 토픽이 같은 클러스터의 리소스를 공유한다.

따라서 주문 메시지 트래픽이 많아지면 다른 토픽에 영향을 줄 수 있고, 반대로 다른 서비스의 트래픽이 많아지면 주문 메시지도 영향을 받을 수 있다.

주문 메시지는 결제 내역, 정산, 배송 등 핵심 흐름과 연결되어 있기 때문에 다른 토픽과 리소스를 경쟁하는 구조는 점점 위험해질 수밖에 없었다.

---

### 3.2 메시지 발행 지연

주문량이 많아지면서 Outbox Table에 쌓이는 데이터도 많아졌다.

Polling Publisher가 짧은 주기로 Outbox Table을 조회해 메시지를 발행하더라도, 발행해야 할 메시지가 많아지면 지연이 발생할 수 있다.

```
주문 이벤트 발생
→ Outbox Table에 데이터 저장
→ 배치 모듈이 조회
→ 메시지 생성
→ Kafka 발행
```

이 과정이 지연되면 사용자는 결제했는데 주문 내역이 늦게 보일 수 있고, 정산 처리도 늦어질 수 있다.

주문 메시지 발행 지연은 단순한 내부 지연이 아니라 사용자 경험과 운영 처리에 직접적인 영향을 줄 수 있는 문제였다.

---

### 3.3 이벤트 발생 시점과 메시지 생성 시점의 불일치

가장 인상 깊었던 문제는 메시지 발행 지연으로 인해 메시지 내용이 달라질 수 있다는 점이었다.

기존 구조에서는 Outbox Table에 전체 주문 메시지를 저장하는 것이 아니라, 주문 번호와 액션 타입 같은 최소한의 키 데이터만 저장했다.

그리고 배치 모듈이 나중에 이 키를 기반으로 주문 데이터를 다시 조회해 메시지를 생성했다.

문제는 그 사이에 주문 상태가 바뀔 수 있다는 것이다.

예를 들어보자.

```
12:00:00 결제 완료 이벤트 발생
→ Outbox Table에 orderId=100, actionType=PAYMENT_COMPLETED 저장

12:00:03 판매자가 상품 발송 처리
→ 주문 상태가 SHIPPING으로 변경

12:00:10 배치 모듈이 Outbox 데이터를 읽고 주문 메시지 생성
```

원래 12:00:00에 발생한 메시지는 “결제 완료 시점의 주문 상태”를 담아야 한다.

하지만 12:00:10에 DB를 조회하면 이미 주문 상태가 배송 중으로 바뀌어 있을 수 있다.

그 결과 결제 완료 이벤트 메시지에 배송 중 상태가 포함될 수 있다.

이벤트 메시지는 “그 시점에 어떤 일이 발생했는가”를 표현해야 한다.

그런데 메시지 생성이 늦어지면서 발행 시점의 최신 데이터가 섞이면 이벤트의 의미가 흐려진다.

## 4. 개선 방향: 전용 Kafka와 CDC 기반 구조

네이버페이는 위 문제를 해결하기 위해 크게 두 가지 방향으로 아키텍처를 개편했다.

```
1. 주문 메시지 전용 Kafka 클러스터 사용
2. CDC 기반 트랜잭션 로그 테일링 방식으로 Outbox 구현 개선
```

---

## 5. 주문 메시지 전용 Kafka 클러스터

첫 번째 개선은 주문 메시지를 위한 전용 Kafka 클러스터를 사용하는 것이었다.

기존에는 공용 Kafka를 사용했기 때문에 여러 토픽이 같은 리소스를 사용했다.

하지만 주문 메시지는 네이버페이 핵심 흐름과 연결된 중요한 메시지였기 때문에, 다른 서비스의 트래픽에 영향을 받지 않도록 분리할 필요가 있었다.

```
기존 구조:
주문 메시지 → 공용 Kafka

개선 구조:
주문 메시지 → 주문 메시지 전용 Kafka
```

전용 Kafka 클러스터를 사용하면 주문 메시지 처리량과 안정성을 더 독립적으로 관리할 수 있다.

또한 주문 메시지에 맞춰 Kafka 리소스를 조정할 수 있기 때문에 운영 안정성도 높아진다.

---

## 6. Polling Publisher에서 CDC로 변경

두 번째 개선은 Outbox Table을 처리하는 방식을 바꾼 것이다.

기존 구조는 Polling Publisher 방식이었다.

```
배치 모듈이 주기적으로 Outbox Table 조회
→ 새 데이터가 있으면 메시지 생성
→ Kafka 발행
```

Polling 방식은 구현이 단순하지만 한계가 있다.

- 주기적으로 DB를 조회해야 한다.
- 조회 주기에 따라 지연이 생길 수 있다.
- 트래픽이 많아질수록 DB 조회 부담이 커진다.
- 발행 지연이 발생하면 메시지 생성 시점의 데이터가 달라질 수 있다.

이를 개선하기 위해 네이버페이는 자체 개발한 CDC를 활용해 트랜잭션 로그 테일링 방식으로 개편했다.

CDC는 Change Data Capture의 약자로, DB에서 발생한 변경 사항을 감지하는 기술이다.

트랜잭션 로그 테일링 방식은 DB가 내부적으로 남기는 트랜잭션 로그를 읽어 변경 사항을 따라가는 방식이다.

```
DB Transaction Log
→ CDC 모듈
→ Outbox 변경 감지
→ 주문 메시지 생성
→ Kafka 발행
```

Polling처럼 주기적으로 테이블을 조회하는 것이 아니라, DB 변경 로그를 기반으로 처리하기 때문에 대량 데이터 처리에 더 적합하다.

## 7. 신규 시스템의 가장 큰 위험: 메시지 신뢰성

아키텍처를 개선한다고 해서 바로 신규 시스템으로 전환할 수 있는 것은 아니다.

이번 개편에서는 단순히 Kafka 브로커만 바뀐 것이 아니라, 주문 메시지를 발행하는 모듈 자체도 새로 만들어졌다.

쿼리 최적화와 로직 재설계가 포함되었기 때문에 사실상 새로운 프로젝트에 가까운 변경이었다.

이때 가장 중요한 문제는 신규 메시지가 기존 메시지와 동일한 신뢰성을 가질 수 있는가였다.

주문 메시지는 많은 시스템이 소비하고 있고, 필드 수도 많다.

따라서 다음과 같은 문제가 발생할 수 있다.

```
주문 메시지 스펙이 달라짐
주문 메시지 발행이 누락됨
주문 메시지가 중복 발행됨
의도하지 않은 주문 메시지가 발행됨
```

네이버페이는 신규 메시지의 신뢰성을 확보하기 위해 운영 환경에서 기존 메시지와 신규 메시지를 비교하는 검증 시스템을 구축했다.

검증은 크게 두 가지로 나뉜다.

```
1. 메시지 정합성 검증
2. 메시지 발행 검증
```

---

## 8. 메시지 정합성 검증

메시지 정합성 검증은 기존 메시지와 신규 메시지의 내용이 같은지 비교하는 과정이다.

흐름은 다음과 같다.

```
1. 정합성 검증 컨슈머가 기존 주문 메시지를 소비한다.
2. 기존 메시지에서 주문 Key 데이터를 추출한다.
3. 신규 메시지 생성 로직을 실행해 검증용 메시지를 만든다.
4. 기존 메시지와 검증용 메시지를 비교한다.
5. 차이가 있으면 로그로 남긴다.
```

즉, 기존 메시지를 기준으로 신규 메시지 생성 로직이 동일한 결과를 만드는지 확인한 것이다.

예를 들어 기존 메시지에는 특정 필드가 있는데 신규 메시지에는 없다면 메시지 스펙이 달라진 것이다.

또 암호화되어야 하는 필드가 신규 메시지에서는 암호화되지 않았다면 보안상 큰 문제가 될 수 있다.

다만 모든 필드를 무조건 동일하게 비교할 수는 없다.

메시지 생성 시점에 따라 달라지는 값도 있기 때문이다.

예를 들어 생성 시각, traceId, 처리 시각 같은 값은 기존 메시지와 신규 메시지에서 다를 수 있다.

따라서 반드시 같아야 하는 필드와 차이를 허용해야 하는 필드를 구분해 검증 민감도를 조절해야 한다.

---

## 9. 메시지 발행 검증

정합성 검증이 메시지 내용 비교라면, 발행 검증은 메시지가 정확히 발행되었는지를 확인하는 과정이다.

발행 검증에서는 메시지 전체 내용보다 메시지의 존재 여부가 중요하다.

그래서 메시지를 식별할 수 있는 Key 데이터만 별도 저장소에 저장하고 비교한다.

```
기존 주문 메시지 소비
→ 기존 메시지 Key 저장

신규 주문 메시지 소비
→ 신규 메시지 Key 저장

발행 검증 배치
→ 양쪽 Key 비교
```

이 비교를 통해 다음 문제를 찾을 수 있다.

```
기존에는 있는데 신규에는 없음
→ 발행 누락

기존에는 없는데 신규에는 있음
→ 의도하지 않은 발행

신규에 같은 Key가 여러 번 있음
→ 중복 발행
```

실제 검증 과정에서는 누락된 필드, 기존과 다른 값으로 생성된 필드, 암호화 누락, 기존 시스템에 새로 추가된 스펙 등이 발견되었다고 한다.

이 부분이 특히 중요하다.

대규모 시스템 전환에서 검증 시스템은 단순한 테스트 보조 수단이 아니라, 운영 전환의 신뢰도를 높이는 핵심 장치가 된다.

---

## 10. Kafka 브로커 전환의 어려움

메시지 신뢰성을 검증한 뒤에도 남은 큰 문제가 있었다.

바로 기존 Kafka 브로커에서 신규 Kafka 브로커로 컨슈머들을 이전하는 일이었다.

Kafka에서 컨슈머는 자신이 어디까지 메시지를 읽었는지 Offset으로 관리한다.

```
offset 0: 주문 A 결제 완료
offset 1: 주문 B 결제 완료
offset 2: 주문 A 배송 시작
offset 3: 주문 C 결제 완료
```

컨슈머 그룹은 각자 어디까지 읽었는지를 Kafka에 저장한다.

```
정산 컨슈머 그룹 offset = 10000
알림 컨슈머 그룹 offset = 9800
배송 컨슈머 그룹 offset = 10300
```

문제는 Kafka 브로커를 바꾸면 이 Offset 정보가 이어지지 않을 수 있다는 것이다.

컨슈머가 신규 Kafka로 이동했는데 신규 Kafka에 기존 Offset 정보가 없다면, 컨슈머는 어디서부터 읽어야 할지 알 수 없다.

이 경우 두 가지 문제가 발생할 수 있다.

```
latest부터 읽음
→ 이전 메시지 누락 가능

earliest부터 읽음
→ 이미 처리한 메시지 중복 소비 가능
```

주문 메시지를 소비하는 컨슈머가 모두 멱등성을 보장한다면 중복 소비를 어느 정도 허용할 수 있다.

하지만 오래된 시스템과 여러 부서에서 운영하는 컨슈머가 많다면 모든 컨슈머가 멱등성을 보장한다고 가정하기 어렵다.

따라서 단순히 “처음부터 다시 읽고 중복은 컨슈머가 알아서 처리하자”는 방식은 사용할 수 없었다.

---

## 11. MirrorMaker를 이용한 점진적 전환

네이버페이가 선택한 방식은 MirrorMaker를 이용한 점진적 전환이었다.

MirrorMaker는 Kafka 클러스터 간에 토픽을 복제할 수 있는 도구다.

기존 Kafka에 들어오는 메시지를 신규 Kafka로 복제해 컨슈머가 단계적으로 이동할 수 있게 만든다.

전환 과정은 다음과 같다.

```
1. 신규 발행 모듈의 신규 Kafka 직접 발행을 중지한다.
2. MirrorMaker로 기존 Kafka의 주문 메시지를 신규 Kafka로 복제한다.
3. 컨슈머들이 각자 Kafka 리스너를 신규 Kafka로 변경한다.
```

이렇게 하면 모든 컨슈머를 한 번에 바꾸지 않아도 된다.

```
기존 발행 모듈
→ 기존 Kafka
→ MirrorMaker
→ 신규 Kafka
→ 전환된 컨슈머
```

아직 전환하지 않은 컨슈머는 기존 Kafka를 계속 소비하고, 전환한 컨슈머는 신규 Kafka를 소비하면 된다.

이 방식 덕분에 여러 컨슈머가 개별 일정에 맞춰 점진적으로 이동할 수 있었다.

---

## 12. 메시지만 복제하면 충분하지 않다

Kafka 브로커 전환에서 중요한 점은 메시지만 복제해서는 안 된다는 것이다.

컨슈머 그룹 Offset도 함께 복제해야 한다.

기존 Kafka에서 컨슈머가 offset 10000까지 읽었다면, 신규 Kafka에서도 동일한 위치부터 이어서 읽을 수 있어야 한다.

```
기존 Kafka:
settlement-consumer-group offset = 10000

신규 Kafka:
settlement-consumer-group offset = 10000
```

이를 위해 MirrorMaker로 메시지뿐 아니라 컨슈머 그룹 Offset도 함께 동기화해야 한다.

또한 컨슈머가 신규 Kafka로 이동할 때 컨슈머 그룹 ID를 기존과 동일하게 유지해야 한다.

Offset은 컨슈머 그룹 ID를 기준으로 저장되기 때문이다.

만약 그룹 ID를 바꾸면 신규 Kafka 입장에서는 완전히 새로운 컨슈머 그룹으로 인식된다.

```
기존 그룹 ID:
settlement-consumer-group

변경 후 그룹 ID:
settlement-consumer-group-v2
```

이 경우 기존 Offset을 이어받을 수 없고, 메시지 누락이나 중복 소비가 발생할 수 있다.

---

## 13. 전환 시 주의할 점

MirrorMaker를 사용하더라도 주의할 점이 있다.

첫 번째는 기존 Kafka와 신규 Kafka를 동시에 소비하지 않는 것이다.

Blue-Green 배포 방식으로 전환할 때 기존 버전은 기존 Kafka를 보고, 신규 버전은 신규 Kafka를 보게 되면 같은 컨슈머가 두 Kafka를 동시에 소비하는 상황이 생길 수 있다.

```
Blue 컨슈머 → 기존 Kafka
Green 컨슈머 → 신규 Kafka
```

이 경우 Offset이 꼬이거나 중복 소비가 발생할 수 있다.

따라서 전환 시점에는 한 컨슈머 그룹이 두 Kafka를 동시에 소비하지 않도록 주의해야 한다.

두 번째는 Offset 동기화가 실시간이 아니라는 점이다.

MirrorMaker의 컨슈머 그룹 Offset 동기화는 주기적으로 이루어진다.

기존 Kafka에서 offset 10100까지 처리했더라도, 신규 Kafka에는 아직 offset 10000까지만 반영되어 있을 수 있다.

```
기존 Kafka offset = 10100
신규 Kafka offset = 10000
```

이 상태에서 컨슈머를 신규 Kafka로 전환하면 10000부터 다시 읽게 되어 일부 메시지가 중복 소비될 수 있다.

따라서 Offset 동기화 주기를 고려해 전환 과정에서 짧은 중단 시간을 확보하는 것이 안전하다.

---

## 14. Producer 전환: 발행 제어 스위치

모든 컨슈머가 신규 Kafka로 이동한 뒤에는 메시지를 발행하는 Producer 쪽도 전환해야 한다.

이때 네이버페이는 주문 API에 발행 제어 스위치를 추가했다.

발행 제어 스위치는 전체 트래픽을 한 번에 신규 발행 모듈로 넘기지 않고, 특정 기준에 따라 일부만 신규 모듈을 사용하게 하는 방식이다.

```
1% 신규 발행 모듈 사용
→ 문제 없음 확인

5% 신규 발행 모듈 사용
→ 문제 없음 확인

10% 신규 발행 모듈 사용
→ 문제 없음 확인

100% 전환
```

이런 방식은 전환 과정의 위험을 줄이는 데 효과적이다.

문제가 생기더라도 영향 범위를 제한할 수 있고, 빠르게 롤백할 수 있다.

---

## 15. 발행 제어 키와 Kafka 파티션 키

Producer 전환에서 특히 중요한 점은 발행 제어 키와 Kafka 파티션 키를 맞추는 것이다.

Kafka는 같은 파티션 안에서는 메시지 순서를 보장하지만, 서로 다른 파티션 간 전체 순서는 보장하지 않는다.

따라서 순서가 중요한 주문 메시지는 같은 기준으로 같은 파티션에 들어가야 한다.

예를 들어 주문 ID를 파티션 키로 사용하면 같은 주문의 이벤트는 같은 파티션으로 들어간다.

```
orderId=100 결제 완료 → partition 2
orderId=100 배송 시작 → partition 2
orderId=100 구매 확정 → partition 2
```

문제는 전환 과정에서 기존 발행 모듈과 신규 발행 모듈이 동시에 존재한다는 점이다.

기존 발행 모듈의 메시지는 다음 경로를 탄다.

```
기존 발행 모듈
→ 기존 Kafka
→ MirrorMaker
→ 신규 Kafka
```

신규 발행 모듈의 메시지는 바로 신규 Kafka로 간다.

```
신규 발행 모듈
→ 신규 Kafka
```

두 경로의 지연 시간이 다르기 때문에 메시지 순서가 뒤바뀔 수 있다.

예를 들어 원래 순서는 다음과 같아야 한다.

```
1. 결제 완료
2. 배송 시작
```

그런데 결제 완료 메시지는 기존 발행 모듈을 타고, 배송 시작 메시지는 신규 발행 모듈을 타면 배송 시작 메시지가 더 먼저 신규 Kafka에 도착할 수 있다.

```
1. 배송 시작
2. 결제 완료
```

주문 도메인에서 이런 순서 역전은 큰 문제가 될 수 있다.

따라서 발행 제어 스위치의 기준은 Kafka 파티션 키와 맞춰야 한다.

그래야 순서가 중요한 메시지가 기존 모듈과 신규 모듈에 섞여 발행되는 문제를 줄일 수 있다.

---

## 16. 최종 구조

전환이 끝난 뒤에는 기존 Kafka로 더 이상 주문 메시지가 생성되지 않고, MirrorMaker 복제도 종료된다.

최종 구조는 다음과 같다.

```
주문 API
→ 신규 주문 메시지 발행 모듈
→ 신규 Kafka 브로커
→ 여러 컨슈머 서비스
```

이번 전환은 크게 두 단계로 나눌 수 있다.

```
1단계: Consumer 전환
기존 Kafka 메시지를 신규 Kafka로 복제하고,
컨슈머 그룹 Offset도 함께 복제해 컨슈머들을 점진적으로 이동

2단계: Producer 전환
발행 제어 스위치를 통해 일부 트래픽부터 신규 발행 모듈로 전환
문제 여부를 확인하면서 점진적으로 100% 전환
```

---

## 17. 이 사례에서 배운 점

이 사례에서 가장 인상 깊었던 점은 Kafka 전환을 단순한 인프라 교체로 보지 않았다는 것이다.

Kafka 브로커를 바꾸는 작업은 단순히 서버 주소를 변경하는 일이 아니다.

컨슈머 그룹 Offset, 메시지 순서, 중복 소비, 메시지 누락, 기존 컨슈머의 멱등성 여부까지 함께 고려해야 한다.

또한 신규 시스템을 만들었을 때 바로 운영 트래픽을 넘기지 않고, 기존 시스템과 신규 시스템을 비교하는 검증기를 먼저 구축한 점도 중요하다.

대규모 시스템에서는 “테스트 환경에서 잘 동작했다”는 것만으로 충분하지 않다.

실제 운영 데이터와 실제 메시지 흐름을 기준으로 신규 시스템이 기존 시스템과 동일하게 동작하는지 확인해야 한다.

마지막으로 전환은 한 번에 끝내는 작업이 아니라 점진적으로 위험을 줄여가는 과정이라는 점도 배울 수 있다.

컨슈머는 MirrorMaker를 활용해 개별적으로 이동시키고, Producer는 발행 제어 스위치를 통해 일부 트래픽부터 전환했다.

이런 전략 덕분에 대규모 Kafka 시스템을 순간적인 중단을 제외하고 무중단에 가깝게 전환할 수 있었다.
