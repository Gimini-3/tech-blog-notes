# 아파치 플링크와 CDC의 만남. 플링크 CDC 맛보기

- 읽은 날짜: 2026-08-26
- 회사/작성 주체: Kakao
- 원문: [아파치 플링크와 CDC의 만남. 플링크 CDC 맛보기](https://tech.kakao.com/posts/632)

---

카카오 데이터분석플랫폼 조직은 여러 서비스의 데이터를 모아 지표를 만들고 있었다.
그런데 지표를 만들기 위해 서비스에서 사용하는 운영 DB를 직접 조회하면 실제 서비스에 부담을 줄 수 있다.

```text
사용자 요청 ───────────────┐
                           ▼
                     ┌───────────┐
                     │ 운영 MySQL │
                     └───────────┘
                           ▲
                           │
                  분석 쿼리까지 접근
                           │
                    데이터 분석 시스템

              → 운영 DB 부하 증가
```

그래서 운영 DB의 데이터를 별도의 DB로 복제하고, 분석은 복제된 데이터를 대상으로 수행하는 구조가 필요했다.

```text
┌────────────┐      실시간 동기화      ┌────────────┐
│ 서비스 DB   │ ───────────────────▶ │ 분석용 DB   │
└────────────┘                       └────────────┘
     ▲                                    │
     │ 서비스 요청                         └─ 지표/분석
```

이때 필요한 것이 CDC(Change Data Capture) 다.

## 1. CDC란?

CDC는 데이터베이스에서 발생한 변경 사항을 감지해 다른 시스템에 전달하는 방식이다.

```text
Source DB

INSERT ─┐
UPDATE ─┼──▶ CDC ──▶ Target
DELETE ─┘
```

하지만 CDC를 처음 시작할 때는 변경 사항만 가져와서는 안 된다.
기존 데이터도 먼저 복사해야 한다.
그래서 CDC는 크게 두 단계로 나뉜다.

```text
           CDC 시작
              │
              ▼
┌─────────────────────────┐
│ ① Snapshot             │
│ 기존 데이터를 전체 복사  │
└────────────┬────────────┘
             │
             ▼
┌─────────────────────────┐
│ ② Binlog Stream        │
│ 이후 변경 내용을 계속 추적 │
└─────────────────────────┘
```

Snapshot → Binlog Stream
이 흐름이 CDC의 기본 구조다.

## 2. Apache Flink

Flink는 실시간 데이터를 처리하기 위한 분산 스트림 처리 프레임워크다.
일반적으로 외부 시스템에서 데이터를 가져와 처리한 뒤 다른 시스템으로 전달한다.

```text
Kafka / DB
    │
    ▼
┌────────────┐
│   Flink    │
│            │
│ map        │
│ filter     │
│ window     │
└─────┬──────┘
      │
      ▼
Kafka / DB / S3 / Hadoop
```

Flink의 중요한 특징 중 하나는 분산 처리다.
하나의 작업을 여러 TaskManager가 나눠 처리할 수 있다.

### JobManager와 TaskManager

Flink의 실행 구조에는 크게 두 가지 구성 요소가 있다.

```text
               ┌──────────────┐
               │  JobManager  │
               │ 작업 관리/분배 │
               └──────┬───────┘
                      │
            ┌─────────┼─────────┐
            ▼         ▼         ▼
      ┌─────────┐ ┌─────────┐ ┌─────────┐
      │ Task    │ │ Task    │ │ Task    │
      │ Manager │ │ Manager │ │ Manager │
      └─────────┘ └─────────┘ └─────────┘
```

JobManager

- 전체 Job 관리
- 실행할 작업 생성
- TaskManager에 작업 분배
  TaskManager
- 실제 작업 수행
- 외부 시스템에서 데이터 읽기
- 데이터 처리
  TaskManager 내부에는 다시 Task Slot이 존재한다.

```text
TaskManager

┌─────────────────────────┐
│ Slot 0  → Task 실행     │
│ Slot 1  → Task 실행     │
│ Slot 2  → Task 실행     │
│ Slot 3  → Task 실행     │
└─────────────────────────┘
```

이 Slot을 여러 개 사용하면서 하나의 작업을 병렬로 처리할 수 있다.

## 3. Flink가 데이터를 나눠 읽는 방법

Flink의 Source에는 중요한 세 가지 개념이 있다.

- Split
- SplitEnumerator
- SourceReader
  구조를 단순화하면 다음과 같다.

```text
                 JobManager
                     │
              SplitEnumerator
                     │
              Split 생성 및 분배
          ┌──────────┼──────────┐
          ▼          ▼          ▼
       Split 1    Split 2    Split 3
          │          │          │
          ▼          ▼          ▼
      SourceReader SourceReader SourceReader
          │          │          │
          ▼          ▼          ▼
      TaskManager TaskManager TaskManager
```

Split은 쉽게 말하면

> "어디부터 어디까지 읽어라"
> 라는 정보를 담고 있는 객체다.
> 예를 들어 DB에서 다음과 같이 나눠 읽을 수 있다.

```text
Split 1 → id 1 ~ 10,000
Split 2 → id 10,001 ~ 20,000
Split 3 → id 20,001 ~ 30,000
```

JobManager가 Split을 만들고 TaskManager에 나눠주면 여러 TaskManager가 동시에 데이터를 읽을 수 있다.

## 4. 장애가 발생하면? Checkpoint

분산 시스템에서는 작업 도중 장애가 발생할 수 있다.
만약 수억 건의 데이터를 읽다가 Flink가 죽었는데 처음부터 다시 시작해야 한다면 큰 문제가 된다.
Flink는 이를 위해 Checkpoint를 사용한다.

```text
데이터 처리

──────●────────●────────●──────▶

      CP1      CP2      CP3
                ▲
                │
           마지막 상태 저장
```

Checkpoint에는 현재 어디까지 처리했는지에 대한 상태가 저장된다.
장애가 발생하면

```text
처음부터 다시 실행 ❌

마지막 Checkpoint
        │
        ▼
   처리 재개 ⭕
```

가 가능하다.
이 기능은 대규모 Snapshot을 수행할 때 특히 중요하다.

## 5. 그런데 Debezium도 CDC를 할 수 있지 않을까?

CDC에서 많이 사용하는 기술 중 하나가 Debezium이다.
보통 다음과 같은 구조로 사용한다.

```text
MySQL
  │
  ▼
Debezium
Source Connector
  │
  ▼
Kafka
  │
  ▼
Sink Connector
  │
  ▼
Target DB
```

Debezium도 Snapshot과 Binlog Stream을 함께 처리할 수 있다.
문제는 대용량 테이블의 Snapshot이다.
수천만~수억 건의 데이터가 들어 있는 테이블을 한 번에 가져오면 Snapshot 시간이 매우 길어질 수 있다.
그래서 실제로는 Snapshot만 별도의 도구로 처리하는 경우도 있다.

```text
Snapshot
MySQL ──▶ mysqldump / Spark ──▶ Target

Binlog
MySQL ──▶ Debezium ──▶ Kafka ──▶ Target
```

이렇게 하면 Snapshot 성능은 좋아지지만,
Snapshot과 실시간 CDC를 서로 다른 시스템으로 운영해야 한다.
관리해야 할 시스템도 늘어난다.

## 6. 그래서 Flink CDC

Flink CDC도 내부적으로 Debezium을 기반으로 하지만 Flink의 분산 처리 능력을 활용할 수 있다.
핵심은 Incremental Snapshot이다.
큰 테이블을 여러 Chunk로 나눈다.

```text
MySQL Table

1 ───────────────────────── 1억

        ↓ Chunk 분할

┌────────┐
│ 1~1만  │ ──▶ Task 1
├────────┤
│ 1만~2만│ ──▶ Task 2
├────────┤
│ 2만~3만│ ──▶ Task 3
├────────┤
│   ...  │
└────────┘
```

그리고 여러 Task가 동시에 Snapshot을 수행한다.

```text
                    MySQL
                      │
        ┌─────────────┼─────────────┐
        ▼             ▼             ▼
     Chunk 1       Chunk 2       Chunk 3
        │             │             │
        ▼             ▼             ▼
     Task 0         Task 1         Task 2
```

Snapshot을 병렬 처리할 수 있기 때문에 대용량 데이터에서 성능을 높일 수 있다.
Checkpoint도 사용할 수 있어 중간에 장애가 발생해도 전체 Snapshot을 처음부터 다시 시작할 필요가 없다.

## 7. Flink CDC가 실제로 동작하는 과정

전체 동작을 먼저 보면 다음과 같다.

```text
① MySQL 설정 확인
        │
        ▼
② 대상 DB / Table 탐색
        │
        ▼
③ Snapshot Split 생성
        │
        ▼
④ 여러 Task가 병렬 Snapshot
        │
        ▼
⑤ Snapshot 완료
        │
        ▼
⑥ GTID 기준점 결정
        │
        ▼
⑦ Binlog Stream 시작
        │
        ▼
⑧ 변경 데이터 실시간 반영
```

### MySQL 설정 확인

CDC를 수행하려면 Binlog를 제대로 읽을 수 있어야 한다.
그래서 Flink CDC는 먼저 MySQL의 설정을 확인한다.
대표적으로 다음 설정이 중요하다.

```text
binlog_format            = ROW
binlog_row_image         = FULL
binlog_row_value_options = ""
```

또 CDC용 계정에는 Snapshot과 Binlog를 읽을 수 있는 권한이 필요하다.
그다음 `SHOW DATABASES`, `SHOW FULL TABLES` 등을 통해 사용자가 지정한 DB와 테이블을 찾는다.

```text
MySQL
 │
 ├── database1
 │     ├── table1  ← CDC 대상
 │     └── table2
 │
 └── database2
```

## 8. Snapshot 내부 동작

대상 테이블을 찾으면 Snapshot을 시작한다.
먼저 데이터를 나눌 기준인 Chunk Key를 선택한다.
보통 `id`처럼 값의 분포가 비교적 고른 컬럼을 사용한다.

```text
id

0       16K       32K       48K
│────────│─────────│─────────│

 Split 1    Split 2    Split 3
```

JobManager가 Snapshot Split을 만든다.

```text
JobManager

Split 1 : id 0 ~ 16192
Split 2 : id 16192 ~ 32384
Split 3 : id 32384 ~ 48576

       │
       ▼

TaskManager들에게 분배
```

각 TaskManager는 받은 범위의 데이터를 동시에 읽는다.

```text
            MySQL
              │
    ┌─────────┼─────────┐
    ▼         ▼         ▼
 Split 1   Split 2   Split 3
    │         │         │
    ▼         ▼         ▼
 Task 0    Task 1    Task 2
```

모든 Split 처리가 완료되면 Snapshot 단계가 끝난다.

## 9. Chunk Key가 중요한 이유

Chunk Key 값이 고르게 분포되어 있다면 범위를 쉽게 나눌 수 있다.

```text
1 2 3 4 5 6 7 8 9 ...

→ 일정한 크기로 Split 생성
```

하지만 값이 심하게 불균형하면 단순하게 범위를 계산할 수 없다.
이 경우 다음 범위를 찾기 위해 DB에 반복해서 Query를 보내야 한다.

```text
Query 1
   │
   ▼
다음 Chunk 경계 계산
   │
   ▼
Query 2
   │
   ▼
다음 Chunk 경계 계산
   │
   ▼
Query 3
   ...
```

앞 Query의 결과를 알아야 다음 Query를 실행할 수 있기 때문에 이 부분은 병렬화하기 어렵다.
따라서 적절한 Chunk Key 선택이 Snapshot 성능에 큰 영향을 준다.

## 10. Snapshot 중 데이터가 변경되면?

여기서 한 가지 문제가 생긴다.
Snapshot에 한 시간이 걸린다고 가정해 보자.

```text
10:00                11:00

Snapshot 시작 ─────────▶ Snapshot 완료

       ↑
       이 시간에도
       INSERT / UPDATE / DELETE 발생
```

Snapshot을 수행하는 동안에도 실제 서비스 DB의 데이터는 계속 변경된다.
그럼 Snapshot 이후에 단순히 현재 시점의 Binlog부터 읽으면 중간 변경 사항을 잃어버릴 수 있다.
이 문제를 해결하기 위해 사용하는 것이 GTID(Global Transaction Identifier) 다.
GTID는 간단하게 생각하면

> MySQL의 변경 내역을 어디까지 처리했는지 나타내는 위치 정보
> 라고 볼 수 있다.
> Flink CDC는 Snapshot Split을 처리하면서 GTID를 함께 기록한다.

```text
Split 1 → GTID 100
Split 2 → GTID 105
Split 3 → GTID 103

          ↓

가장 앞선 기준점 확인

          ↓

GTID 100부터 Binlog Stream
```

따라서 Snapshot 수행 중 발생한 변경 사항까지 다시 읽을 수 있다.

```text
Snapshot
10:00 ────────────────────── 11:00
  │
  └── GTID 100 저장

Binlog Stream
          │
          └── GTID 100부터 다시 읽음
```

이렇게 Snapshot과 Binlog Stream 사이의 데이터 정합성을 유지한다.

## 11. 여기서 실제 운영 문제가 발생했다

Snapshot에서는 병렬 처리가 중요하다.
예를 들어 병렬성을 20으로 설정하면 여러 Task가 동시에 데이터를 가져올 수 있다.

```text
Snapshot

Task 0  █████████
Task 1  █████████
Task 2  █████████
...
Task 19 █████████
```

그런데 Binlog Stream은 상황이 다르다.
DB에서

```text
A → B → C
```

순서로 변경됐다면 Target에도 반드시

```text
A → B → C
```

순서로 적용돼야 한다.
병렬 처리 과정에서 순서가 바뀌면 데이터 정합성이 깨질 수 있다.
그래서 당시 `flink-connector-mysql-cdc`는 0번 Subtask 하나만 Binlog를 읽도록 동작했다.

```text
Binlog Stream

Task 0  █████████  ← 실제 작업

Task 1  .........
Task 2  .........
Task 3  .........
...
Task 19 .........  ← 대기
```

Snapshot 때문에 병렬성을 20으로 설정했지만 Binlog 단계에서는 19개의 Slot이 놀게 된다.
즉,
Snapshot에서는 높은 병렬성이 필요하고, Binlog에서는 하나의 Task만 필요하다.
하지만 당시 사용하던 Flink 1.17에서는 실행 중인 Job의 병렬성을 원하는 방식으로 변경하기 어려웠다.

## 12. 해결 ① Snapshot과 Binlog 단계를 분리

카카오에서는 Snapshot과 Binlog Stream에서 서로 다른 Kafka Topic을 사용하고 있었다.
Snapshot은 대량의 데이터를 빠르게 보내야 하기 때문에 여러 Partition을 사용한다.

```text
Snapshot Topic

Partition 0
Partition 1
Partition 2
Partition 3
...
```

반대로 Binlog는 이벤트 순서가 중요하기 때문에 Partition을 1개로 사용한다.

```text
Binlog Topic

Partition 0
```

문제는 실행 중인 Flink Job에서 Topic을 동적으로 변경하기 어렵다는 것이다.
그래서 라이브러리를 수정해 Snapshot 종료와 Binlog 시작 시점을 알림으로 받을 수 있도록 했다.

```text
Snapshot 실행
      │
      ▼
Snapshot 완료
      │
      ├── 알림 전송
      │   "END SNAPSHOT"
      ▼
기존 Flink Job 종료
      │
      ▼
Binlog용 Job 시작
      │
      └── 저장된 GTID 사용
```

Binlog Stream이 시작될 때 GTID도 함께 전달하도록 했다.
결과적으로

```text
Snapshot Job
병렬성 ↑
     │
     │ Snapshot 완료 + GTID 확보
     ▼
Binlog Job
병렬성 ↓
```

처럼 각 단계에 적절한 리소스를 사용할 수 있게 됐다.

## 13. 해결 ② DDL 이벤트를 바로 반영하지 않는다

운영 중 테이블의 Schema가 바뀔 수도 있다.
서비스 팀에서 다음 컬럼을 추가했다고 가정해 보자.

```sql
ADD COLUMN phone_number VARCHAR(31)
```

문제는 분석 시스템에서 개인정보 컬럼을 Hashing 또는 Masking해서 저장하고 있었다는 점이다.
새로운 컬럼이 자동으로 CDC되면 처리 로직에 등록되지 않은 개인정보가 그대로 넘어올 가능성이 있다.

```text
Service DB

DDL 발생
ADD COLUMN phone_number
       │
       ▼
    CDC 자동 반영
       │
       ▼
분석 DB

phone_number 원본 저장
       │
       ▼
      위험
```

그래서 DDL을 자동으로 반영하지 않는 방식을 선택했다.

```text
Binlog 읽기
    │
    ▼
DDL 발견
    │
    ├── DDL 정보 알림
    ├── GTID 저장
    └── 이후 이벤트 처리 중단
            │
            ▼
      사람이 Schema 확인
            │
            ▼
       Target에 DDL 적용
            │
            ▼
       저장된 GTID부터
         CDC 재시작
```

즉,
Schema 변경을 발견 → 일단 멈춤 → 검증 → 직접 반영 → GTID부터 재개
하는 방식이다.
자동화보다 데이터 안정성과 보안을 우선한 선택이다.

## 14. 해결 ③ DB Primary가 바뀌는 문제

CDC는 서비스의 Primary DB에 부담을 주지 않기 위해 Replica에 연결해서 수행하고 있었다.

```text
Primary
   │
   └── Replication ──▶ Replica
                         ▲
                         │
                      Flink CDC
```

그런데 장애가 발생하면 DB 역할이 바뀔 수 있다.

```text
Before

DB A = Primary
DB B = Replica ← Flink CDC

Failover

DB A = Replica
DB B = Primary ← Flink CDC가 기존 연결 유지
```

그러면 Flink CDC가 의도치 않게 Primary에 연결될 수 있다.
그래서 DB 전환을 감지하는 기능을 추가했다.

### Primary-Replica 두 대 구성

Replica 도메인의 IP를 주기적으로 확인한다.

```text
Replica Domain
     │
     ▼
DNS 조회

10.0.0.2
     │
     │ 일정 시간 후
     ▼
10.0.0.1

IP 변경 감지
     │
     ▼
Exception 발생
     │
     ▼
Flink Job 재시작
     │
     ▼
Replica Domain 재연결
```

### InnoDB Cluster

여러 Replica가 존재하면 DNS IP만으로 판단하기 어렵다.
이 경우 DB의 `read_only` 값을 확인한다.

```text
Flink
  │
  ▼
SELECT read_only
  │
  ├── true  → Replica → 정상
  │
  └── false → Primary → 연결 종료
```

Primary 연결을 감지하면 예외를 발생시키고 Job을 다시 시작한다.

## 15. 해결 ④ Chunk Key 제약 개선

Incremental Snapshot에서는 어떤 컬럼을 기준으로 데이터를 나눌지가 중요하다.
당시 Flink CDC에서는 Primary Key가 있는 테이블이라면 Primary Key에 포함된 컬럼만 Chunk Key로 사용할 수 있었다.

```text
Table

PK = varbinary 컬럼

        ↓

Chunk Key도 PK 사용

        ↓

Chunk 범위 계산 실패 가능

        ↓

전체 테이블이 하나의 Chunk

        ↓

DB 부하 증가
TaskManager OOM 가능
```

특히 `VARBINARY` 같은 컬럼이 Primary Key인 경우 Chunk 범위를 제대로 계산하지 못하는 상황이 발생할 수 있었다.
그래서 Primary Key와 Chunk Key를 분리할 수 있도록 라이브러리 로직을 개선했다.

```text
기존

Primary Key
    │
    └── Chunk Key로 사용

개선

Primary Key ──▶ Row 식별

Chunk Key   ──▶ Snapshot 분할
```

즉, 데이터를 식별하기 좋은 컬럼과 데이터를 잘 나누기 좋은 컬럼은 다를 수 있다는 것이다.
이 변경 사항은 Flink CDC 프로젝트에도 제안됐다.

## 17. 이 사례에서 중요한 점

처음 문제는 단순했다.

> 운영 DB에 부담을 주지 않고 데이터를 실시간으로 복제하고 싶다.
> 그래서 CDC가 필요했고, 대용량 Snapshot을 빠르게 처리하기 위해 Flink CDC를 선택했다.
> 하지만 실제 운영 단계에 들어가자 새로운 문제가 생겼다.

```text
CDC 필요
  │
  ▼
Flink CDC 도입
  │
  ▼
대용량 Snapshot 병렬화
  │
  ▼
운영 시작
  │
  ├── Binlog 단계 리소스 낭비
  ├── DDL 변경 위험
  ├── DB Failover 대응
  └── Chunk Key 제약
          │
          ▼
   라이브러리 내부 분석
          │
          ▼
      직접 기능 개선
```

결국 이 사례에서 눈여겨볼 부분은 단순히 Flink CDC를 사용했다는 것보다,
오픈소스의 내부 동작을 이해하고 실제 운영 환경에서 부족한 부분을 찾아 직접 수정했다는 점이다.
특히 Snapshot의 병렬 처리, GTID를 이용한 Binlog 연결, Checkpoint를 이용한 장애 복구를 이해하면 Flink CDC가 단순한 DB 복제 도구가 아니라 분산 처리 시스템 위에서 동작하는 CDC 파이프라인이라는 점을 이해할 수 있다.
