## 1. 도메인 로직은 성공했는데 이벤트 발행이 실패한다면

이벤트 기반 시스템에서는 하나의 서비스에서 발생한 변경을 다른 서비스에 전달해야 하는 경우가 많다.
예를 들어 상품 서비스에서 재고가 변경되면 검색, 전시, 추천 서비스도 변경 사실을 알아야 한다.

```text
상품 서비스
    |
    | 재고 변경
    v
상품 DB
    |
    | 재고 변경 이벤트
    v
Kafka
    |
    +──────── 검색 서비스
    +──────── 전시 서비스
    +──────── 추천 서비스
```

가장 단순한 구현은 데이터베이스를 변경한 뒤 Kafka에 이벤트를 발행하는 것이다.

```java
@Transactional
public void updateInventory(UpdateInventoryCommand command) {
    inventoryService.update(command);

    kafkaTemplate.send(
        "inventory.updated",
        command.productId(),
        command
    );
}
```

하지만 데이터베이스와 Kafka는 서로 다른 시스템이다.

```text
데이터베이스 트랜잭션
≠
Kafka 메시지 발행
```

따라서 다음과 같은 상황이 발생할 수 있다.

```text
1. 재고 변경 성공
2. DB Commit 성공
3. Kafka 발행 실패
```

결과적으로 서비스마다 서로 다른 데이터를 가지게 된다.

```text
상품 서비스 재고 : 9개
검색 서비스 재고 : 10개
전시 서비스 재고 : 10개
```

반대 상황도 문제가 된다.

```text
1. Kafka 발행 성공
2. DB Commit 실패
```

이 경우 Consumer는 실제로 존재하지 않는 변경을 처리하게 된다.
트랜잭셔널 아웃박스 패턴은 이러한 문제를 해결하기 위해 사용한다.

## 2. 트랜잭셔널 아웃박스 패턴의 핵심

아웃박스 패턴은 Kafka에 바로 메시지를 보내는 대신, **발행해야 할 이벤트를 먼저 데이터베이스에 저장하는 방식**이다.

```text
도메인 데이터 변경
+
Outbox 이벤트 저장
```

두 작업을 하나의 DB 트랜잭션으로 묶는다.

```sql
BEGIN;

UPDATE inventory
SET quantity = quantity - 1
WHERE product_id = 100;

INSERT INTO outbox_event (
    event_id,
    aggregate_id,
    event_type,
    payload,
    status,
    created_at
)
VALUES (
    'evt-001',
    '100',
    'INVENTORY_UPDATED',
    '{"productId":100,"quantity":9}',
    'INIT',
    CURRENT_TIMESTAMP
);

COMMIT;
```

이 구조에서는 두 작업이 함께 성공하거나 함께 실패한다.

```text
재고 변경 성공
+
Outbox 저장 성공
→ Commit

재고 변경 실패
또는
Outbox 저장 실패
→ Rollback
```

중요한 점은 DB Commit과 Kafka 발행을 하나의 물리적 트랜잭션으로 만드는 것이 아니다.

```text
도메인 변경이 Commit되었다면
발행해야 할 이벤트 기록도 DB에 반드시 남게 만든다.
```

Kafka 발행에 실패해도 Outbox에 이벤트가 남아 있으므로 나중에 다시 발행할 수 있다.

## 3. 29CM이 이벤트 기반 구조를 도입한 이유

29CM은 마이크로서비스 전환 이후 서비스 간 통신에 주로 HTTP API를 사용했다.
초기에는 동기식 호출만으로도 충분했지만, 서비스가 늘어나면서 상품 서비스가 여러 서비스에 직접 의존하는 문제가 생겼다.

```text
상품 서비스
    ├── 검색 서비스 API 호출
    ├── 전시 서비스 API 호출
    ├── 추천 서비스 API 호출
    └── 분석 서비스 API 호출
```

이 구조에서는 검색 서비스 장애나 타임아웃이 상품 변경 요청까지 영향을 줄 수 있다.
새로운 Consumer가 추가될 때마다 상품 서비스의 코드가 변경될 가능성도 커진다.
이벤트 기반 구조에서는 상품 서비스가 변경 사실만 Kafka에 발행한다.

```text
상품 서비스
    |
    | PRODUCT_UPDATED
    v
Kafka
    ├── 검색 서비스
    ├── 전시 서비스
    ├── 추천 서비스
    └── 분석 서비스
```

상품 서비스는 누가 이벤트를 소비하는지 알 필요가 없다.
다만 이벤트 기반 구조를 도입하면 새로운 문제가 생긴다.

```text
상품 변경은 완료됐는데
이벤트가 발행되지 않으면 어떻게 복구할 것인가?
```

29CM은 이 문제를 해결하기 위해 상품 도메인에 트랜잭셔널 아웃박스 패턴을 적용했다.

## 4. 29CM이 CDC 대신 Outbox를 선택한 이유

트랜잭셔널 메시징은 CDC로도 구현할 수 있다.
CDC는 데이터베이스 변경 로그를 읽어 이벤트를 생성하는 방식이다.

```text
애플리케이션
    |
    v
MySQL
    |
    | binlog
    v
Debezium
    |
    v
Kafka
```

하지만 29CM은 당시 CDC보다 Outbox를 직접 구현하는 방식을 선택했다.
첫 번째 이유는 운영 경험이었다.
CDC를 안정적으로 운영하려면 다음과 같은 요소를 이해해야 한다.

```text
- MySQL binlog
- Kafka Connect
- Debezium Connector
- Snapshot
- 스키마 변경
- 로그 보존 정책
- 장애 복구
- 중복과 순서 보장
```

기술을 설치할 수 있다는 것과 장애 발생 시 직접 복구할 수 있다는 것은 다른 문제다.
29CM은 당시 팀이 익숙한 Spring과 데이터베이스를 활용하는 Outbox가 운영 측면에서 더 적합하다고 판단했다.
두 번째 이유는 이벤트 모델이었다.
CDC 메시지는 일반적으로 DB Row 변경에 가깝다.

```json
{
  "before": {
    "id": 100,
    "price": 39000
  },
  "after": {
    "id": 100,
    "price": 35000
  }
}
```

하지만 Consumer가 원하는 것은 비즈니스 의미가 담긴 도메인 이벤트일 수 있다.

```json
{
  "eventType": "PRODUCT_PRICE_CHANGED",
  "productId": 100,
  "previousPrice": 39000,
  "changedPrice": 35000
}
```

두 메시지는 의미가 다르다.

```text
CDC
→ 어떤 DB 값이 변경됐는가

도메인 이벤트
→ 비즈니스에서 어떤 일이 발생했는가
```

Outbox를 사용하면 DB 테이블 구조와 외부 이벤트 계약을 분리할 수 있다.

## 5. 29CM의 Outbox 처리 구조

29CM의 최종 구조는 도메인 서비스가 Outbox 저장과 Kafka 발행을 직접 처리하지 않고 내부 이벤트만 발행하도록 역할을 분리했다.

```text
@Transactional 도메인 메서드
        |
        | 도메인 이벤트 발행
        v
ApplicationEventPublisher
        |
        ├── BEFORE_COMMIT Listener
        |       └── Outbox 저장
        |
        └── AFTER_COMMIT Listener
                └── Kafka 발행
```

도메인 서비스는 재고 변경이라는 핵심 책임에 집중한다.

```java
@Transactional
public InventoryQuantityUpdateInfo updateInventoryQuantity(
        InventoryUpdateCommand command
) {
    Inventory inventory = inventoryRepository
            .findByProductId(command.productId())
            .orElseThrow();

    inventory.decrease(command.quantity());

    eventPublisher.publishEvent(
            InventoryQuantityUpdatedEvent.of(
                    inventory.getProductId(),
                    inventory.getQuantity()
            )
    );

    return InventoryQuantityUpdateInfo.from(inventory);
}
```

### BEFORE_COMMIT: Outbox 저장

`BEFORE_COMMIT` Listener는 현재 DB 트랜잭션이 Commit되기 전에 Outbox 이벤트를 저장한다.

```java
@TransactionalEventListener(
    phase = TransactionPhase.BEFORE_COMMIT
)
public void recordMessage(
        InventoryQuantityUpdatedEvent event
) {
    outboxEventRepository.save(
        OutboxEvent.create(
            event.eventId(),
            event.productId().toString(),
            "INVENTORY_QUANTITY_UPDATED",
            event,
            OutboxEventStatus.INIT
        )
    );
}
```

Outbox 저장이 실패하면 예외를 발생시켜 전체 트랜잭션을 Rollback해야 한다.

```text
재고 변경
    |
    v
Outbox 저장 실패
    |
    v
전체 트랜잭션 Rollback
```

이를 통해 다음 불변식을 지킬 수 있다.

```text
도메인 변경이 Commit되었다면
Outbox 이벤트도 반드시 존재한다.
```

### AFTER_COMMIT: Kafka 발행

Kafka 발행은 DB Commit 이후 실행한다.

```java
@Async("eventAsyncTaskExecutor")
@TransactionalEventListener(
    phase = TransactionPhase.AFTER_COMMIT
)
public void sendMessage(
        InventoryQuantityUpdatedEvent event
) {
    kafkaPublisher.publish(event);
}
```

Commit 전에 Kafka를 발행하면 Kafka 발행 후 DB가 Rollback되는 문제가 생길 수 있다.

```text
Kafka 발행 성공
        |
        v
DB Commit 실패
        |
        v
Consumer는 존재하지 않는 변경을 처리
```

따라서 안전한 순서는 다음과 같다.

```text
DB Commit 성공
        |
        v
Kafka 발행 시도
```

Kafka 발행에 실패하더라도 도메인 변경은 이미 Commit된 상태다. 이때 Outbox를 이용해 재발행한다.

### `BEFORE_COMMIT`은 모든 트랜잭션에서 실행되는가

`BEFORE_COMMIT` Listener는 애플리케이션에서 발생하는 모든 트랜잭션마다 실행되는 전역 콜백이 아니다.
현재 Listener의 메서드 파라미터가 `InventoryQuantityUpdatedEvent`이므로, **활성 트랜잭션 안에서 해당 이벤트가 발행된 경우에만** 실행된다.

```java
@TransactionalEventListener(
    phase = TransactionPhase.BEFORE_COMMIT
)
public void recordMessage(
        InventoryQuantityUpdatedEvent event
) {
    outboxEventRepository.save(...);
}
```

예를 들어 주문만 저장하고 재고 변경 이벤트를 발행하지 않는 트랜잭션에서는 이 Listener가 실행되지 않는다.

```text
주문 저장 Transaction
    |
    ├── 주문 데이터 저장
    ├── InventoryQuantityUpdatedEvent 발행 없음
    |
    v
Commit

recordMessage() 실행 안 됨
```

반대로 재고 서비스가 아닌 다른 서비스에서 실행된 트랜잭션이라도 `InventoryQuantityUpdatedEvent`를 발행하면 Listener가 실행된다.

```text
어떤 서비스에서 실행됐는가
→ 중요하지 않음

어떤 이벤트가 트랜잭션 안에서 발행됐는가
→ Listener 실행 여부를 결정
```

### Spring 내부에서는 어떻게 실행되는가

트랜잭션 안에서 `publishEvent()`가 호출되면 Spring은 `recordMessage()`를 즉시 실행하지 않는다.

```java
eventPublisher.publishEvent(event);
```

Spring은 이벤트 타입과 일치하는 `@TransactionalEventListener`를 찾은 뒤, 해당 Listener를 현재 트랜잭션의 동기화 작업으로 등록한다.

```text
publishEvent(event)
        |
        v
이벤트 타입과 일치하는 Listener 탐색
        |
        v
현재 활성 트랜잭션 확인
        |
        v
TransactionSynchronization 등록
        |
        v
트랜잭션 커밋 절차에서 실행
```

`phase = BEFORE_COMMIT`이므로 트랜잭션 관리자가 실제 DB Commit을 수행하기 전에 Listener를 호출한다.

```text
@Transactional 메서드 실행
        |
        ├── 재고 변경
        ├── 이벤트 발행
        |       |
        |       └── BEFORE_COMMIT 작업 등록
        |
        ├── 서비스 메서드 정상 종료
        ├── BEFORE_COMMIT Listener 실행
        ├── Outbox 저장
        ├── 변경 내용 Flush
        |
        v
DB Commit
```

현재 Listener에는 `@Async`가 없으므로 이벤트를 발행한 스레드에서 동기적으로 실행된다. 따라서 기존 트랜잭션과 영속성 컨텍스트를 그대로 사용한다.

```text
하나의 DB Transaction

Inventory 변경
+
OutboxEvent 저장
        |
        v
함께 Commit 또는 Rollback
```

Outbox 저장 중 예외가 발생하면 커밋 절차가 중단되고 재고 변경도 함께 Rollback된다.

### Outbox 저장 코드를 분리한 이유

Outbox 저장 코드를 도메인 메서드 안에 직접 작성해도 원자성은 보장할 수 있다.

```java
@Transactional
public void updateInventory(...) {
    inventory.decrease(...);
    outboxEventRepository.save(...);
}
```

하지만 이 구조에서는 도메인 서비스가 Outbox Entity, 상태값, 이벤트 타입, Payload 저장 방식까지 알아야 한다.

```text
InventoryService
├── 재고 변경
├── Outbox Entity 생성
├── Outbox 상태 관리
├── 이벤트 타입 관리
└── Payload 변환
```

이벤트 Listener로 분리하면 도메인 서비스는 재고가 변경됐다는 사실만 발행한다.

```java
inventory.decrease(command.quantity());

eventPublisher.publishEvent(
    InventoryQuantityUpdatedEvent.of(
        inventory.getProductId(),
        inventory.getQuantity()
    )
);
```

Outbox Listener는 해당 도메인 이벤트를 발행 가능한 메시지 형태로 변환해 저장한다.

```text
InventoryService
└── 재고가 변경됐다는 사실을 발행

OutboxEventListener
└── 이벤트를 Outbox 형식으로 변환하고 저장
```

이를 통해 도메인 로직과 메시징 인프라 로직의 책임을 분리할 수 있다.
다만 이벤트 방식은 실행 흐름이 코드에 직접 드러나지 않아 추적하기 어려울 수 있다. Outbox 저장이 반드시 수행돼야 하는 핵심 절차임을 명확히 보여주고 싶다면 별도 객체를 직접 호출하는 방식도 사용할 수 있다.

```java
@Transactional
public void updateInventory(...) {
    inventory.decrease(...);

    InventoryQuantityUpdatedEvent event =
        InventoryQuantityUpdatedEvent.of(...);

    outboxEventWriter.write(event);
}
```

```text
이벤트 Listener 방식
→ 결합도 감소와 확장에 유리
→ 실행 흐름이 숨겨질 수 있음

OutboxWriter 직접 호출 방식
→ 실행 흐름이 명확함
→ 서비스가 Outbox 저장 절차를 직접 호출
```

현재 구조에서는 도메인 변경과 Outbox 저장의 원자성을 유지하면서 메시징 책임을 분리하기 위해 `BEFORE_COMMIT` Listener를 사용한 것이다.

> Outbox를 저장하는 `BEFORE_COMMIT` Listener에는 `@Async`를 붙이면 안 된다. 비동기 스레드에는 기존 트랜잭션 컨텍스트가 전달되지 않으므로 재고 변경과 Outbox 저장이 하나의 트랜잭션으로 묶이지 않을 수 있다.

## 6. Outbox 상태를 나누는 이유

단순한 구현에서는 발행 여부를 Boolean으로 관리할 수 있다.

```text
published = false
→ 아직 발행되지 않음

published = true
→ 발행 완료
```

하지만 `false`만으로는 왜 발행되지 않았는지 알기 어렵다.

```text
상황 A
Kafka 발행을 시도했지만 실패

상황 B
발행 로직 자체가 실행되지 않음
```

29CM은 이를 구분하기 위해 상태를 나누었다.
| **상태** | **의미** |
| --- | --- |
| `INIT` | Outbox에는 저장됐지만 발행 결과가 아직 기록되지 않음 |
| `SEND_SUCCESS` | Kafka 발행 성공 |
| `SEND_FAIL` | Kafka 발행을 시도했지만 실패 |

상태 전이는 다음과 같다.

```text
INIT
 ├── Kafka 발행 성공 ──▶ SEND_SUCCESS
 └── Kafka 발행 실패 ──▶ SEND_FAIL
                              |
                              | 재발행 성공
                              v
                        SEND_SUCCESS
```

`SEND_SUCCESS`는 Producer가 Kafka에 이벤트를 발행했다는 뜻이다.
다음까지 보장하는 것은 아니다.

```text
- Consumer 처리 성공
- Consumer DB 반영 성공
- 전체 비즈니스 프로세스 완료
```

Producer와 Consumer의 상태는 별도로 관리해야 한다.

## 7. 배포 이후 INIT 이벤트가 남은 이유

정상적인 상황이라면 `INIT`은 오래 유지되지 않는다.

```text
Outbox INIT 저장
        |
        v
DB Commit
        |
        v
AFTER_COMMIT Listener
        |
        v
SEND_SUCCESS 또는 SEND_FAIL
```

하지만 29CM은 배포 직후 일부 이벤트가 계속 `INIT`으로 남는 현상을 발견했다.
원인은 `@Async`로 실행되는 Kafka 발행 작업이었다.

```text
1. 상품 변경 트랜잭션 실행
2. Outbox INIT 저장
3. DB Commit 성공
4. AFTER_COMMIT Listener 호출
5. 비동기 작업을 Executor에 제출
6. Pod 종료
7. Kafka 발행 작업 중단
```

DB에는 이미 상품 변경과 Outbox 이벤트가 저장됐다.
하지만 비동기 작업이 완료되지 않았으므로 Kafka 발행 결과를 기록할 수 없었다.

```text
상품 변경
→ 완료

Outbox
→ INIT 유지

Kafka
→ 발행되지 않았을 가능성
```

`@Async`는 작업을 별도 스레드에서 실행할 뿐, 작업 완료를 보장하지 않는다.

```text
작업 제출
≠
작업 완료
```

## 8. Graceful Shutdown 설정

정상적인 배포 과정에서 비동기 작업이 중단되는 문제를 줄이기 위해 Executor가 작업 완료를 기다리도록 설정할 수 있다.

```java
@Bean(name = "eventAsyncTaskExecutor")
public ThreadPoolTaskExecutor eventAsyncTaskExecutor() {

    // 이벤트 발행 작업을 비동기로 처리할 스레드 풀을 생성한다.
    // @Async("eventAsyncTaskExecutor")에서 이 Executor를 지정해 사용한다.
    ThreadPoolTaskExecutor executor =
            new ThreadPoolTaskExecutor();

    // 기본적으로 유지하면서 동시에 작업을 처리할 스레드 수다.
    // 이벤트가 들어오면 우선 최대 4개의 Core Thread가 작업을 처리한다.
    executor.setCorePoolSize(4);

    // Queue까지 가득 찼을 때 생성할 수 있는 최대 스레드 수다.
    // Core Thread 4개와 추가 Thread를 포함해 최대 8개까지 증가한다.
    executor.setMaxPoolSize(8);

    // Core Thread가 모두 작업 중일 때 대기시킬 작업의 최대 개수다.
    // 최대 1000개의 이벤트 작업이 Queue에서 실행 순서를 기다린다.
    executor.setQueueCapacity(1000);

    // 생성되는 스레드 이름 앞에 붙일 문자열이다.
    // 로그나 Thread Dump에서 이벤트 처리 스레드를 쉽게 구분할 수 있다.
    executor.setThreadNamePrefix("outbox-event-");

    // 애플리케이션이 종료되어도 실행 중이거나 대기 중인 작업의 완료를 기다린다.
    // 이벤트 발행 작업이 종료 과정에서 바로 중단되는 것을 줄여준다.
    executor.setWaitForTasksToCompleteOnShutdown(true);

    // 애플리케이션 종료 시 남은 작업을 최대 10초 동안 기다린다.
    // 10초가 지나도 작업이 끝나지 않으면 종료 절차가 계속 진행된다.
    executor.setAwaitTerminationSeconds(10);

    // 위 설정을 바탕으로 내부 ThreadPoolExecutor를 초기화한다.
    // Spring Bean에서는 자동 초기화되므로 일반적으로 생략해도 된다.
    executor.initialize();

    return executor;
}
```

이 코드는 **Outbox 이벤트 발행 작업을 별도 스레드에서 비동기로 처리하기 위한 스레드 풀 Bean**을 등록한다.

```java
@Async("eventAsyncTaskExecutor")
public void sendMessage(...) {
    kafkaPublisher.publish(...);
}
```

위처럼 사용하면 호출한 요청 스레드가 직접 Kafka 발행을 수행하지 않고, 이 Executor의 작업 Queue에 넘긴다.
동작 순서는 다음과 같다.

```text
이벤트 발행 요청
→ Core Thread 최대 4개가 처리
→ 모두 바쁘면 Queue에 최대 1000개 대기
→ Queue까지 가득 차면 Thread를 최대 8개까지 증가
```

또한 애플리케이션이 종료될 때 남은 이벤트 작업을 바로 끊지 않고 최대 10초 동안 완료되기를 기다린다.
핵심적으로는 **이벤트 발행이 원래 트랜잭션이나 요청 처리를 오래 붙잡지 않도록 분리하고, 동시에 실행되는 작업 수를 제한하는 설정**이다.
두 설정의 역할은 다르다.

```text
setWaitForTasksToCompleteOnShutdown(true)
→ 종료 시 이미 제출된 작업이 끝나기를 기다린다.

setAwaitTerminationSeconds(10)
→ 최대 10초 동안 기다린다.
```

다만 Graceful Shutdown만으로 모든 문제를 막을 수는 없다.

### 정상 종료와 비정상 종료는 다르다

여기서 애플리케이션 종료 시 작업을 기다린다는 것은 서버가 갑자기 죽는 모든 상황을 의미하지 않는다.
Spring이 정상적인 종료 신호를 받아 종료 절차를 수행할 수 있을 때만 동작한다.
예를 들어 배포 과정에서 Pod가 `SIGTERM`을 받으면 다음 순서로 종료된다.

```text
Pod 종료 요청
    |
    v
JVM에 SIGTERM 전달
    |
    v
Spring ApplicationContext 종료 시작
    |
    v
Executor가 새로운 작업 수락 중단
    |
    v
이미 실행 중이거나 Queue에 들어간 작업 완료 대기
    |
    v
최대 10초 후 애플리케이션 종료
```

예를 들어 Kafka 발행 작업이 3개 남아 있고 4초 만에 모두 끝난다면, 애플리케이션은 작업 완료 후 바로 종료된다.

```text
종료 요청
→ 남은 작업 3개 처리
→ 4초 후 모두 완료
→ 애플리케이션 종료
```

반대로 10초 안에 작업이 끝나지 않으면 종료 절차가 계속 진행되므로 남은 작업은 중단될 수 있다.

```text
종료 요청
→ 작업 완료 대기
→ 10초 초과
→ 남은 작업이 있어도 종료
```

다음과 같은 비정상 종료에서는 이 설정이 동작할 수 없다.

```text
- kill -9
- OOM Kill
- JVM Crash
- 서버 전원 장애
- 노드 장애
- 컨테이너 강제 종료
```

이 경우에는 Spring의 종료 절차 자체가 실행되지 않기 때문에 Executor가 작업 완료를 기다릴 기회가 없다.
따라서 Graceful Shutdown은 다음 역할만 한다.

```text
정상 종료
→ 진행 중인 비동기 작업이 끝날 시간을 제공

비정상 종료
→ 작업 완료를 보장할 수 없음
```

이 때문에 Outbox Relay가 반드시 필요하다.

```text
정상 종료
→ Graceful Shutdown으로 즉시 발행 완료 가능성을 높임

비정상 종료
→ Outbox에 남은 INIT 또는 SEND_FAIL 이벤트를 Relay가 재발행
```

즉, Graceful Shutdown은 장애 복구 수단이 아니라 정상적인 배포나 종료 과정에서 미완료 작업을 줄이는 보조 장치다.

## 9. 오래된 INIT과 SEND_FAIL 재발행

Kafka 발행에 실패했거나 오랫동안 처리되지 않은 이벤트는 별도의 Relay가 다시 발행한다.

```sql
SELECT *
FROM outbox_event
WHERE status IN ('INIT', 'SEND_FAIL')
  AND created_at < CURRENT_TIMESTAMP - INTERVAL '10 minutes'
ORDER BY created_at
LIMIT 100;
```

최근에 생성된 `INIT` 이벤트는 비동기 Listener가 아직 처리 중일 수 있으므로 일정 시간이 지난 이벤트만 조회한다.
전체 흐름은 다음과 같다.

```text
Outbox Relay
    |
    | INIT 또는 SEND_FAIL 조회
    v
Kafka 재발행
    |
    ├── 성공 → SEND_SUCCESS
    |
    └── 실패 → SEND_FAIL 유지
```

재시도 횟수가 늘어나면 간격을 점점 늘리는 Exponential Backoff를 적용할 수 있다.

```text
1회 실패 → 1분 후
2회 실패 → 2분 후
3회 실패 → 4분 후
4회 실패 → 8분 후
```

무한 재시도도 피해야 한다.

```text
최대 재시도 횟수 초과
        |
        v
DEAD 상태
        |
        v
운영 알림과 수동 확인
```

재시도해도 해결될 가능성이 낮은 오류는 바로 최종 실패로 분류할 수 있다.

```text
재시도 가능
- Kafka Broker 일시 장애
- 네트워크 타임아웃
- 연결 재설정

재시도 불가능
- 직렬화 오류
- 잘못된 Topic
- 메시지 크기 초과
- 필수 필드 누락
```

## 10. 여러 Relay가 같은 이벤트를 처리한다면

애플리케이션 인스턴스가 여러 개라면 각 서버의 Scheduler가 같은 이벤트를 동시에 조회할 수 있다.

```text
Relay A → evt-001 조회
Relay B → evt-001 조회
```

두 Relay가 모두 Kafka에 이벤트를 발행하면 중복 메시지가 발생한다.
이를 줄이려면 발행 전 이벤트를 Claim할 수 있다.

```text
INIT
  |
  | Claim 성공
  v
PUBLISHING
  |
  ├── 발행 성공 → SEND_SUCCESS
  └── 발행 실패 → SEND_FAIL
```

예를 들어 조건부 UPDATE를 사용할 수 있다.

```sql
UPDATE outbox_event
SET status = 'PUBLISHING',
    processing_owner = :relayId,
    lease_until = CURRENT_TIMESTAMP + INTERVAL '30 seconds'
WHERE event_id = :eventId
  AND status IN ('INIT', 'SEND_FAIL')
RETURNING *;
```

영향받은 행이 1개인 Relay만 발행 권한을 얻는다.
외부 Kafka 호출 동안 DB Row Lock을 오래 유지하는 것은 피하는 것이 좋다.

```text
Transaction A
INIT → PUBLISHING
Commit

Kafka 발행

Transaction B
PUBLISHING → SEND_SUCCESS 또는 SEND_FAIL
Commit
```

Relay가 `PUBLISHING` 상태에서 종료될 수 있으므로 Lease 만료 후 다른 Relay가 다시 Claim할 수 있어야 한다.

## 11. Outbox도 중복 발행을 완전히 막을 수 없다

Kafka 발행과 Outbox 상태 변경은 서로 다른 시스템에서 수행된다.

```text
1. Kafka 발행
2. Outbox SEND_SUCCESS 저장
```

이 두 작업은 하나의 원자적 트랜잭션이 아니다.
다음 장애가 발생할 수 있다.

```text
Kafka 발행 성공
        |
        X 프로세스 종료
        |
        v
SEND_SUCCESS 저장 실패
```

DB에는 `INIT`이나 `SEND_FAIL`로 남아 있으므로 Relay가 같은 이벤트를 다시 발행한다.
따라서 Outbox는 일반적으로 다음 전달 특성을 가진다.

```text
At-Least-Once

최소 한 번은 발행한다.
대신 여러 번 발행될 수 있다.
```

Outbox 상태를 먼저 성공으로 변경한 뒤 Kafka를 발행하면 메시지 유실 위험이 생긴다.

```text
SEND_SUCCESS 저장
        |
        v
Kafka 발행 실패
        |
        v
DB에서는 성공으로 보이므로 재발행되지 않음
```

그래서 일반적으로 유실보다 중복을 선택한다.

```text
유실
→ Consumer가 이벤트 존재 자체를 알 수 없음

중복
→ Consumer 멱등성으로 방어 가능
```

Kafka의 `send()` 호출이 끝났다는 이유만으로 발행 성공 처리해서도 안 된다.
비동기 전송 결과를 확인한 뒤 `SEND_SUCCESS`로 변경해야 한다.

```java
CompletableFuture<SendResult<String, String>> future =
        kafkaTemplate.send(
            event.getTopic(),
            event.getAggregateId(),
            event.getPayload()
        );

SendResult<String, String> result =
        future.get(5, TimeUnit.SECONDS);

statusService.markSendSuccess(event.getEventId());
```

타임아웃이 발생하면 Broker에 저장되지 않았을 수도 있고, 저장은 됐지만 ACK만 늦었을 수도 있다.
따라서 재발행을 허용하고 Consumer에서 중복을 막는 편이 안전하다.

## 12. Consumer 멱등성이 필요한 이유

Outbox를 적용해도 동일한 `eventId`가 여러 번 전달될 수 있다.

```text
Offset 100 → eventId = evt-001
Offset 101 → eventId = evt-001
```

Consumer는 같은 이벤트가 다시 들어와도 최종 결과를 한 번만 반영해야 한다.
처리한 이벤트를 기록하는 테이블을 둘 수 있다.

```sql
CREATE TABLE processed_event (
    consumer_name VARCHAR(100) NOT NULL,
    event_id UUID NOT NULL,
    processed_at TIMESTAMPTZ NOT NULL,
    PRIMARY KEY (
        consumer_name,
        event_id
    )
);
```

`consumer_name`을 함께 사용하는 이유는 하나의 이벤트를 여러 Consumer가 각각 처리해야 하기 때문이다.

```text
evt-001
├── 검색 서비스에서 한 번 처리
├── 전시 서비스에서 한 번 처리
└── 추천 서비스에서 한 번 처리
```

다만 다음과 같이 먼저 조회한 뒤 처리하는 방식은 동시성 문제가 있다.

```text
1. 처리 여부 SELECT
2. 비즈니스 로직 실행
3. 처리 기록 INSERT
```

두 스레드가 동시에 조회하면 둘 다 처리되지 않았다고 판단할 수 있다.

```text
Consumer A             Consumer B
-----------------------------------------
처리 기록 없음 조회
                       처리 기록 없음 조회
비즈니스 처리
                       비즈니스 처리
처리 기록 INSERT
                       INSERT 충돌
```

DB 제약이 중복 기록은 막더라도 비즈니스 로직은 이미 두 번 실행됐을 수 있다.
따라서 처리 권한을 먼저 Claim하는 것이 안전하다.

```sql
INSERT INTO processed_event (
    consumer_name,
    event_id,
    processed_at
)
VALUES (
    :consumerName,
    :eventId,
    CURRENT_TIMESTAMP
)
ON CONFLICT (
    consumer_name,
    event_id
)
DO NOTHING;
```

```text
영향받은 행 = 1
→ 처리 권한 획득

영향받은 행 = 0
→ 이미 처리됐거나 다른 스레드가 처리 중
```

비즈니스 DB 변경과 `processed_event` 저장이 같은 데이터베이스라면 하나의 트랜잭션으로 묶을 수 있다.
외부 검색 엔진이나 외부 API를 변경하는 경우에는 작업 자체를 멱등하게 만들어야 한다.
예를 들어 상품 ID를 검색 문서 ID로 사용해 덮어쓰면 같은 이벤트를 여러 번 적용해도 최종 결과는 같다.
이벤트 순서가 중요하다면 버전도 함께 비교해야 한다.

```text
현재 저장된 version = 15

도착한 version = 14
→ 오래된 이벤트이므로 무시

도착한 version = 16
→ 최신 이벤트이므로 반영
```

## 13. Outbox 운영에서 확인해야 할 것

Outbox는 구현만 해두고 끝나는 기능이 아니다.
이벤트가 밀리거나 고착된 상태를 운영자가 확인할 수 있어야 한다.
중요한 메트릭은 다음과 같다.

```text
outbox_init_count
→ INIT 이벤트 수

outbox_send_fail_count
→ SEND_FAIL 이벤트 수

outbox_oldest_pending_age
→ 가장 오래된 미발행 이벤트 대기 시간

outbox_publish_success_total
→ 발행 성공 누적 수

outbox_publish_fail_total
→ 발행 실패 누적 수

outbox_retry_total
→ 재발행 시도 수

outbox_dead_count
→ 자동 복구가 어려운 이벤트 수
```

단순한 건수보다 가장 오래된 미발행 이벤트의 시간이 더 중요한 경우도 있다.

```text
미발행 이벤트 100개
가장 오래된 이벤트 10초
→ 일시적인 지연일 수 있음

미발행 이벤트 3개
가장 오래된 이벤트 2시간
→ 이벤트 고착 가능성
```

로그에는 최소한 다음 값을 포함하는 것이 좋다.

```text
eventId
aggregateType
aggregateId
eventType
retryCount
topic
partition
offset
errorType
```

발행에 성공한 이벤트를 계속 보관하면 Outbox 테이블이 빠르게 커진다.
일정 기간이 지난 성공 이벤트는 삭제하거나 별도 저장소로 옮겨야 한다.

```text
- 일정 기간 후 삭제
- 이력 테이블로 이동
- 날짜 파티션 제거
- Object Storage에 아카이빙
```

### 미발행 이벤트 조회를 위한 Partial Index

Outbox 테이블은 시간이 지날수록 대부분의 이벤트가 `SEND_SUCCESS` 상태가 된다.
예를 들어 전체 이벤트가 100만 개여도 실제 재발행 대상은 일부일 수 있다.

```text
SEND_SUCCESS : 990,000개
INIT         :   5,000개
SEND_FAIL    :   5,000개
```

하지만 Outbox Relay가 조회하는 대상은 아직 발행되지 않았거나 발행에 실패한 이벤트뿐이다.

```sql
SELECT *
FROM outbox_event
WHERE status IN ('INIT', 'SEND_FAIL')
  AND next_attempt_at <= CURRENT_TIMESTAMP
ORDER BY next_attempt_at, created_at
LIMIT 100;
```

이처럼 특정 상태만 반복해서 조회한다면 Partial Index를 사용할 수 있다.

```sql
CREATE INDEX idx_outbox_relay_target
ON outbox_event (
    next_attempt_at,
    created_at
)
WHERE status IN ('INIT', 'SEND_FAIL');
```

Partial Index는 테이블의 모든 행이 아니라 조건을 만족하는 행만 인덱스에 포함한다.

```text
일반 인덱스
→ INIT, SEND_FAIL, SEND_SUCCESS를 모두 포함

Partial Index
→ INIT과 SEND_FAIL만 포함
```

따라서 대부분을 차지하는 `SEND_SUCCESS` 이벤트를 제외하고, 실제 재발행 후보가 들어 있는 작은 인덱스에서 대상을 빠르게 찾을 수 있다.
`next_attempt_at`은 현재 재시도할 수 있는 이벤트를 찾는 데 사용하고, `created_at`은 재시도 시각이 같은 이벤트를 오래된 순서로 처리하는 데 사용한다.
이벤트 발행이 성공해 상태가 `SEND_SUCCESS`로 변경되면 해당 행은 Partial Index의 조건을 만족하지 않으므로 인덱스에서 제외된다.

```text
INIT 또는 SEND_FAIL
→ Partial Index에 포함

SEND_SUCCESS로 변경
→ Partial Index에서 제외
```

결과적으로 전체 Outbox 테이블이 계속 커지더라도 재발행 대상 조회에 사용하는 인덱스는 비교적 작게 유지할 수 있다.

## 14. Outbox가 보장하는 것과 보장하지 않는 것

트랜잭셔널 아웃박스 패턴이 보장하려는 핵심은 명확하다.

```text
도메인 변경이 Commit되었다면
발행해야 할 이벤트 기록도 DB에 남는다.
```

Kafka 장애나 프로세스 종료가 발생해도 Outbox 기록을 이용해 다시 발행할 수 있다.
하지만 Outbox가 다음 문제까지 자동으로 해결하는 것은 아니다.

```text
- 정확히 한 번 발행
- 정확히 한 번 소비
- Consumer 비즈니스 로직의 원자성
- 여러 서비스의 즉시 일관성
- 전역 이벤트 순서
- DB와 외부 시스템 사이의 원자성
```

Outbox가 해결하는 범위는 다음 구간이다.

```text
도메인 DB 변경
↕
이벤트 발행 요청 기록
```

그 이후에는 별도의 설계가 필요하다.

```text
Producer 중복 발행
→ Consumer 멱등성

오래된 이벤트 도착
→ Version 또는 순서 검증

Consumer DB와 외부 시스템 불일치
→ 외부 작업 멱등성 또는 보상 처리
```

## 16. 정리

트랜잭셔널 아웃박스 패턴은 도메인 데이터 변경과 이벤트 발행 요청 기록을 하나의 DB 트랜잭션으로 묶는 방식이다.

```text
도메인 변경
+
Outbox 저장
→ 함께 Commit 또는 Rollback
```

29CM은 Spring의 내부 이벤트와 트랜잭션 Listener를 사용해 역할을 분리했다.

```text
BEFORE_COMMIT
→ Outbox 저장

AFTER_COMMIT
→ Kafka 발행
```

Kafka 발행이 실패하거나 배포 과정에서 비동기 작업이 중단되면 Outbox 이벤트는 `INIT` 또는 `SEND_FAIL`로 남는다.
Relay는 이러한 이벤트를 조회해 다시 발행한다.

```text
정상 경로
→ AFTER_COMMIT Listener를 통한 즉시 발행

복구 경로
→ Outbox Relay를 통한 재발행
```

Graceful Shutdown은 정상적인 배포 과정에서 작업 누락 가능성을 줄여주지만, 강제 종료나 노드 장애까지 막을 수는 없다.
따라서 안정적인 이벤트 시스템은 다음 요소가 함께 필요하다.

```text
DB Transaction
→ 도메인 변경과 Outbox 저장의 원자성

Graceful Shutdown
→ 정상 종료 과정의 작업 누락 감소

Outbox Relay
→ 실패 이벤트 재발행

상태와 메트릭
→ 장애 탐지와 운영

Consumer 멱등성
→ 중복 메시지의 중복 반영 방지
```

Outbox의 핵심은 장애를 완전히 없애는 것이 아니다.

```text
장애가 발생하더라도
발행해야 했던 이벤트를 잃지 않고
나중에 복구할 수 있게 만드는 것
```

이것이 트랜잭셔널 아웃박스 패턴이 해결하려는 가장 중요한 문제다.
