# Redis와 Kafka를 활용한 선착순 쿠폰 이벤트 설계 정리

여기어때 기술블로그의 **「Redis&Kafka를 활용한 선착순 쿠폰 이벤트 개발기」**를 읽고, 선착순 쿠폰 시스템에서 어떤 문제가 있었고 이를 어떻게 해결했는지 정리해보았다.

이 글의 핵심은 단순히 Redis와 Kafka를 사용했다는 것이 아니라,

**선착순 판정**, **중복 발급 방지**, **DB 부하 완화**, **장애 전파 방지**라는 문제를 각각 어떤 기술로 나누어 해결했는지에 있다.

---

## 1. 선착순 쿠폰 이벤트의 요구사항

선착순 쿠폰 이벤트는 겉으로 보면 단순해 보인다.

사용자가 쿠폰 발급 버튼을 누르면, 남은 쿠폰이 있을 때 쿠폰을 지급하면 된다.

하지만 실제 서비스에서는 이벤트 시작 시간에 수많은 요청이 동시에 들어오기 때문에 생각보다 까다로운 문제가 발생한다.

요구사항은 크게 세 가지였다.

```
1. 이벤트 기간 동안 매일 특정 시간에 쿠폰을 오픈한다.
2. 쿠폰은 정해진 수량을 초과해서 지급되면 안 된다.
3. 한 사용자는 쿠폰을 한 장만 받을 수 있어야 한다.
```

예를 들어 쿠폰이 7,000장만 준비되어 있다면, 아무리 많은 사용자가 동시에 요청하더라도 7,001장이 발급되면 안 된다.

또한 같은 사용자가 여러 번 요청하더라도 한 번만 성공해야 한다.

---

## 2. 기존 RDB 중심 방식의 문제

기존 방식에서는 RDB를 기준으로 쿠폰 발급 수량을 확인하고, 조건을 만족하면 쿠폰을 발급하는 식으로 처리할 수 있다.

```
사용자 요청
   ↓
API 서버
   ↓
RDB에서 현재 발급 수량 조회
   ↓
남은 수량이 있으면 쿠폰 INSERT
```

하지만 이 방식은 트래픽이 몰릴 때 동시성 문제가 발생할 수 있다.

예를 들어 현재 발급 수량이 6,999장이고, 최대 수량이 7,000장이라고 해보자.

이때 여러 요청이 거의 동시에 들어오면 여러 요청이 모두 “아직 1장 남았다”고 판단할 수 있다.

```
현재 발급 수량 = 6,999
최대 발급 수량 = 7,000

Thread A → 6,999 확인 → 발급 가능
Thread B → 6,999 확인 → 발급 가능
Thread C → 6,999 확인 → 발급 가능
```

그 결과 실제로는 한 장만 더 발급되어야 하는데, 여러 장이 추가로 발급될 수 있다.

```
Thread A INSERT → 7,000
Thread B INSERT → 7,001
Thread C INSERT → 7,002
```

결국 문제는 **조회 → 판단 → 저장** 과정이 하나의 안전한 작업으로 묶여 있지 않다는 점이다.

---

## 3. Redis INCR 방식의 한계

이 문제를 해결하기 위해 먼저 생각할 수 있는 방법은 Redis의 `INCR` 명령어를 사용하는 것이다.

`INCR`는 특정 key의 숫자 값을 1씩 증가시키는 명령어다.

```
coupon:issued:count = 0

INCR 실행 → 1
INCR 실행 → 2
INCR 실행 → 3
```

Redis는 명령어를 순차적으로 처리하기 때문에, 단순히 발급 수량만 증가시키는 작업에는 적합하다.

```
여러 요청이 동시에 들어와도 Redis 내부에서는 순서대로 처리된다.

Request A → INCR → count = 1
Request B → INCR → count = 2
Request C → INCR → count = 3
```

하지만 `INCR`만으로는 한 가지 문제가 남는다.

바로 **사용자 중복 발급 여부를 알 수 없다는 점**이다.

`INCR`는 숫자만 증가시키기 때문에 현재 몇 장이 발급되었는지는 알 수 있지만, 어떤 사용자가 이미 쿠폰을 받았는지는 알 수 없다.

```
User 1 요청 → count + 1
User 1 재요청 → count + 1
User 1 또 요청 → count + 1
```

따라서 “1인당 1장만 지급”이라는 요구사항을 만족시키기에는 부족하다.

---

## 4. Redis SET을 활용한 중복 발급 방지

다음으로 사용한 방식은 Redis의 `SET` 자료형이다.

SET은 중복 값을 허용하지 않는 자료구조다.

즉, 이미 들어있는 값을 다시 추가해도 중복 저장되지 않는다.

쿠폰을 발급받은 사용자의 `userId`를 Redis SET에 저장하면, 자연스럽게 중복 발급을 막을 수 있다.

```
key   = coupon:time-attack:{policyId}:date-time:{dateTimeId}:issued:users
value = userId
```

예를 들어 쿠폰을 받은 사용자가 다음과 같이 저장된다고 해보자.

```
issued_users = {101, 102, 103}
```

이때 Redis의 `SCARD` 명령어를 사용하면 현재 몇 명이 쿠폰을 받았는지 알 수 있다.

```
SCARD issued_users
→ 현재 발급된 쿠폰 수량
```

그리고 `SADD` 명령어를 사용하면 사용자를 SET에 추가할 수 있다.

```
SADD issued_users 104
→ 1 반환: 새로 추가됨

SADD issued_users 101
→ 0 반환: 이미 존재하는 사용자
```

이 방식의 장점은 수량과 중복 여부를 함께 관리할 수 있다는 것이다.

```
SCARD → 현재 발급 수량 확인
SADD  → 사용자 중복 발급 방지
```

하지만 여기에도 문제가 있었다.

## 5. SCARD와 SADD를 분리했을 때의 동시성 문제

<img width="761" height="489" alt="image" src="https://github.com/user-attachments/assets/3a646866-b874-4943-a6ea-48b8771104c2" />

처음에는 다음과 같은 흐름으로 처리할 수 있다.

```
1. SCARD로 현재 발급 수량을 확인한다.
2. 아직 수량이 남아 있으면 SADD로 userId를 추가한다.
3. 쿠폰 발급 처리를 진행한다.
```

코드 흐름으로 보면 대략 이런 식이다.

```
count = SCARD issued_users

if count < maxCount:
    result = SADD issued_users userId

    if result == 1:
        쿠폰 발급 처리
```

문제는 `SCARD`와 `SADD`가 각각 별도의 명령어라는 점이다.

Redis의 명령어 하나하나는 원자적으로 실행되지만,

`SCARD → 조건 판단 → SADD` 전체 흐름이 자동으로 하나의 원자적 작업이 되는 것은 아니다.

예를 들어 쿠폰이 1장 남은 상황에서 여러 요청이 동시에 들어오면 다음과 같은 일이 발생할 수 있다.

```
현재 SET 크기 = 6,999
최대 쿠폰 수량 = 7,000

Thread A → SCARD → 6,999 확인
Thread B → SCARD → 6,999 확인
Thread C → SCARD → 6,999 확인

Thread A → SADD userA → size 7,000
Thread B → SADD userB → size 7,001
Thread C → SADD userC → size 7,002
```

결국 SET을 사용했더라도 명령어 조합을 안전하게 처리하지 않으면 초과 발급 문제가 다시 발생할 수 있다.

이 부분이 중요한 포인트다.

```
SCARD는 원자적이다.
SADD도 원자적이다.

하지만

SCARD → 조건 판단 → SADD

이 전체 흐름은 원자적이지 않다.
```

## 6. Redis Transaction으로 동시성 문제 해결

이를 해결하기 위해 Redis Transaction을 사용했다.

Redis Transaction은 여러 명령어를 하나의 묶음으로 실행할 수 있게 해준다.

```
MULTI
  SCARD issued_users
  SADD issued_users userId
EXEC
```

이렇게 하면 여러 명령어가 Redis에서 순차적으로 처리되기 때문에, 중간에 다른 요청이 끼어드는 문제를 줄일 수 있다.

```
Transaction A
  - SCARD
  - SADD userA

Transaction B
  - SCARD
  - SADD userB

Transaction C
  - SCARD
  - SADD userC
```

이를 통해 선착순 쿠폰 시스템에서 중요한 두 가지 문제를 해결할 수 있었다.

```
1. 정해진 수량을 초과하지 않도록 제어
2. 한 사용자가 여러 번 발급받지 못하도록 제어
```

다만 Redis Transaction은 RDB의 Transaction과 완전히 같지는 않다.

RDB에서는 문제가 생기면 `ROLLBACK`을 통해 이전 상태로 되돌릴 수 있다.

```
BEGIN
INSERT
UPDATE
문제 발생
ROLLBACK
```

하지만 Redis Transaction은 RDB처럼 모든 상황에서 자동 Rollback을 제공하지 않는다.

따라서 Redis에 사용자를 추가한 뒤 Kafka 발행에 실패하는 경우처럼, 일부 작업만 성공한 상황에 대비한 보상 로직이 필요하다.

예를 들어 다음과 같은 상황이 생길 수 있다.

```
1. Redis SET에 userId 추가 성공
2. Kafka 메시지 발행 실패
3. 실제 쿠폰 발급은 진행되지 않음
4. Redis에는 이미 발급받은 사용자처럼 남아 있음
```

이런 경우에는 Redis에서 해당 userId를 제거하는 보상 처리가 필요하다.

```
SREM issued_users userId
```

## 7. Redis로 해결한 것과 아직 남은 문제

Redis를 사용하면서 선착순 판정 문제는 어느 정도 해결되었다.

```
Redis가 해결한 문제

1. 쿠폰 수량 초과 발급 방지
2. 사용자 중복 발급 방지
3. 빠른 선착순 판정
```

하지만 성능 테스트를 진행하면서 새로운 문제가 드러났다.

바로 **Write DB 부하**다.

Redis로 선착순 여부를 빠르게 판단하더라도, 실제 쿠폰 발급을 API 서버에서 바로 RDB에 INSERT하면 결국 Write DB에 부하가 몰린다.

```
사용자 요청 폭증
   ↓
API 서버
   ↓
Redis로 선착순 판정
   ↓
RDB에 쿠폰 INSERT
   ↓
Write DB 부하 증가
```

특히 Write DB는 Read DB처럼 쉽게 scale-out하기 어렵다.

<img width="650" height="493" alt="image" src="https://github.com/user-attachments/assets/8c201529-944c-4605-87de-8fd5c131c984" />

읽기 요청은 여러 Reader DB로 분산할 수 있지만, 쓰기 요청은 정합성을 유지해야 하므로 병목이 되기 쉽다.

또한 쿠폰 DB는 이벤트에만 사용되는 것이 아니라 기존 쿠폰 서비스에서도 사용된다.

이벤트 트래픽 때문에 Write DB가 불안정해지면, 쿠폰 서비스 전체에 장애가 전파될 수 있다.

## 8. Kafka를 도입한 이유

이 문제를 해결하기 위해 Kafka를 도입했다.

Kafka를 도입한 핵심 이유는 API 서버가 직접 DB INSERT를 하지 않도록 만들기 위해서다.

기존 흐름은 다음과 같았다.

```
Client
  ↓
API Server
  ↓
Redis 선착순 판정
  ↓
RDB INSERT
  ↓
응답
```

Kafka를 도입한 후에는 흐름이 바뀐다.

```
Client
  ↓
API Server
  ↓
Redis 선착순 판정
  ↓
Kafka에 발급 요청 메시지 발행
  ↓
사용자에게 응답
```

그리고 실제 쿠폰 발급은 Kafka Consumer가 비동기로 처리한다.

```
Kafka Topic
  ↓
Coupon Consumer
  ↓
RDB INSERT
```

전체 구조를 보면 다음과 같다.

<img width="722" height="507" alt="image" src="https://github.com/user-attachments/assets/fb42c72e-7b5f-42fd-a147-b6fd8570e8ab" />

```
┌────────────┐
│  Client    │
└─────┬──────┘
      ↓
┌────────────┐
│ API Server │
└─────┬──────┘
      ↓
┌────────────┐
│   Redis    │
│ 선착순 판정 │
└─────┬──────┘
      ↓
┌────────────┐
│   Kafka    │
│ 발급 요청 저장 │
└─────┬──────┘
      ↓
┌────────────────┐
│ Kafka Consumer │
│ 실제 쿠폰 발급  │
└─────┬──────────┘
      ↓
┌────────────┐
│  Write DB  │
│ 쿠폰 INSERT │
└────────────┘
```

이 구조의 장점은 API 요청 처리와 DB 쓰기 작업을 분리할 수 있다는 점이다.

API 서버는 Redis에서 선착순 판정을 하고 Kafka에 메시지만 발행하면 된다.

실제 DB INSERT는 Consumer가 처리하므로, API 서버가 DB 쓰기 작업에 직접 묶이지 않는다.

## 9. Kafka가 하는 역할

Kafka는 여기서 단순한 메시지 전달 도구가 아니라, 순간적으로 몰리는 트래픽을 완충하는 역할을 한다.

```
Kafka의 역할

1. API 서버와 DB 쓰기 작업 분리
2. 순간 트래픽을 메시지로 저장
3. Consumer가 처리 가능한 속도로 DB INSERT 수행
4. 장애 발생 시 메시지 재처리 가능
```

비유하면 음식점의 주문 대기열과 비슷하다.

```
손님이 몰림
  ↓
직원이 주문을 받음
  ↓
주문표를 주방 대기열에 넣음
  ↓
손님에게 주문 접수 응답
  ↓
주방은 주문표를 순서대로 처리
```

여기서 각 구성 요소를 시스템에 대입하면 다음과 같다.

```
Client       = 손님
API Server   = 주문 받는 직원
Redis        = 선착순 번호표 확인
Kafka        = 주문 대기열
Consumer     = 주방
RDB          = 최종 주문 기록
```

## 10. Kafka Topic과 Consumer 구조

블로그에서는 쿠폰 발급 요청을 다음과 같은 Kafka Topic으로 전달했다.

```
Topic: TimeAttackCouponIssue

Message:
{
  policyId: 1,
  userId: 1,
  issuedAt: "2022-02-26T11:31:42"
}
```

메시지에는 실제 쿠폰 발급에 필요한 최소한의 정보만 들어간다.

```
policyId → 어떤 쿠폰 정책인지
userId   → 어떤 사용자에게 발급할 것인지
issuedAt → 언제 발급 요청이 되었는지
```

Topic은 Partition 3개, Replica 3개로 구성되어 있었고, Consumer 애플리케이션도 Partition 수에 맞춰 3대로 운영되었다.

```
Kafka Topic: TimeAttackCouponIssue

Partition 0 → Consumer 1
Partition 1 → Consumer 2
Partition 2 → Consumer 3
```

Partition은 병렬 처리를 가능하게 해준다.

```
Partition 1개 → Consumer 1대가 처리
Partition 3개 → Consumer 최대 3대가 병렬 처리
Partition 10개 → Consumer 최대 10대가 병렬 처리
```

Replica는 장애 대응을 위한 복제본이다.

```
Partition = 처리량 확장
Replica   = 장애 대응
```

즉, Partition을 통해 처리량을 늘리고, Replica를 통해 Kafka Broker 장애에도 데이터를 안전하게 유지할 수 있다.

## 11. 최종 요청 처리 흐름

최종적으로 사용자가 쿠폰 발급 요청을 보냈을 때의 흐름은 다음과 같다.

```
1. 사용자가 쿠폰 발급 요청을 보낸다.
2. API 서버가 요청을 받는다.
3. Redis에서 이벤트 시간, 남은 수량, 중복 발급 여부를 확인한다.
4. 발급 불가능하면 바로 실패 응답을 반환한다.
5. 발급 가능하면 Redis SET에 userId를 저장한다.
6. Kafka Topic에 쿠폰 발급 요청 메시지를 발행한다.
7. 사용자에게 발급 요청 접수 응답을 반환한다.
8. Kafka Consumer가 메시지를 소비한다.
9. Consumer가 RDB에 실제 쿠폰 발급 데이터를 INSERT한다.
10. 사용자는 마이페이지나 알림을 통해 최종 발급 결과를 확인한다.
```

그림으로 정리하면 다음과 같다.

```
┌──────────────────────────────┐
│ 1. 사용자 쿠폰 발급 요청       │
└───────────────┬──────────────┘
                ↓
┌──────────────────────────────┐
│ 2. API Server 요청 수신        │
└───────────────┬──────────────┘
                ↓
┌──────────────────────────────┐
│ 3. Redis 선착순 판정           │
│ - 수량 남았는가?               │
│ - 이미 받은 사용자인가?         │
└───────────────┬──────────────┘
                ↓
        ┌───────────────────┐
        │ 발급 가능한가?      │
        └───────┬───────────┘
                │
       ┌────────┴────────┐
       │                 │
      No                Yes
       │                 │
       ↓                 ↓
┌──────────────┐   ┌──────────────────────────────┐
│ 실패 응답     │   │ Redis SET에 userId 저장        │
└──────────────┘   └───────────────┬──────────────┘
                                    ↓
                      ┌──────────────────────────────┐
                      │ Kafka 메시지 발행              │
                      └───────────────┬──────────────┘
                                      ↓
                      ┌──────────────────────────────┐
                      │ 사용자에게 접수 성공 응답       │
                      └───────────────┬──────────────┘
                                      ↓
                      ┌──────────────────────────────┐
                      │ Kafka Consumer가 메시지 소비   │
                      └───────────────┬──────────────┘
                                      ↓
                      ┌──────────────────────────────┐
                      │ RDB에 실제 쿠폰 발급 INSERT    │
                      └──────────────────────────────┘
```

## 12. 비동기 처리로 인해 생기는 변화

Kafka를 도입하면 API 서버는 실제 DB INSERT가 끝나기 전에 사용자에게 응답할 수 있다.

기존 방식은 다음과 같았다.

```
Redis 판정
  ↓
DB INSERT 완료
  ↓
성공 응답
```

개선 후에는 다음과 같다.

```
Redis 판정
  ↓
Kafka 메시지 발행
  ↓
접수 성공 응답
  ↓
Consumer가 나중에 DB INSERT
```

이렇게 하면 사용자 입장에서는 응답 속도가 빨라진다.

하지만 실제 쿠폰이 마이페이지에 보이기까지 약간의 지연이 생길 수 있다.

따라서 사용자에게는 “쿠폰 발급 완료”보다는 다음과 같은 문구가 더 적절하다.

```
쿠폰 발급 요청이 접수되었습니다.
잠시 후 쿠폰함에서 확인해주세요.
```

비동기 구조에서는 이런 사용자 안내도 중요한 설계 요소가 된다.

---

## 13. 이 설계가 해결한 문제

이 구조는 여러 문제를 단계적으로 해결했다.

첫 번째는 **쿠폰 초과 발급 문제**다.

Redis SET과 Transaction을 사용해 수량 제한과 중복 발급 여부를 빠르게 판단했다.

두 번째는 **사용자 중복 발급 문제**다.

발급받은 userId를 Redis SET에 저장하여 같은 사용자가 여러 번 쿠폰을 받을 수 없게 했다.

세 번째는 **Write DB 부하 문제**다.

API 서버가 직접 DB에 INSERT하지 않고 Kafka에 메시지만 발행하게 하여 DB 쓰기 부하를 Consumer 쪽으로 분리했다.

네 번째는 **장애 전파 문제**다.

이벤트 트래픽이 바로 쿠폰 DB에 몰리지 않도록 Kafka를 중간에 두어, 쿠폰 발급 처리가 지연되더라도 전체 서비스로 장애가 번지는 위험을 줄였다.

다섯 번째는 **순간 트래픽 흡수 문제**다.

Redis는 빠르게 선착순 성공 여부를 판단하고, Kafka는 성공한 요청을 메시지로 쌓아두었다가 Consumer가 처리 가능한 속도로 DB에 반영한다.

## 14. 정리

이 시스템에서 Redis, Kafka, RDB는 각각 역할이 다르다.

```
Redis
- 선착순 판정
- 발급 수량 제한
- 사용자 중복 발급 방지

Kafka
- 쿠폰 발급 요청 저장
- API 서버와 DB 쓰기 작업 분리
- 순간 트래픽 완충
- Consumer를 통한 비동기 처리

RDB
- 최종 쿠폰 발급 이력 저장
- 마이페이지 조회
- 운영, 정산, CS 기준 데이터
```

결국 이 설계의 핵심은 모든 문제를 하나의 DB에서 해결하려 하지 않았다는 점이다.

선착순 판정처럼 빠르고 원자적인 처리가 필요한 부분은 Redis가 담당하고,

실제 쿠폰 발급처럼 안정적으로 처리되어야 하는 작업은 Kafka를 통해 비동기로 넘기고,

최종 데이터는 RDB에 저장한다.

즉, 각 기술을 다음과 같이 역할 분리한 것이다.

```
Redis = 선착순 판정소
Kafka = 발급 요청 대기열
Consumer = 실제 발급 처리자
RDB = 최종 발급 결과 저장소
```

이 구조를 통해 여기어때는 네고왕과 같은 대규모 선착순 이벤트에서도 쿠폰 초과 지급 없이 안정적으로 트래픽을 처리할 수 있었다.

개인적으로 이 글에서 가장 인상 깊었던 점은 Redis나 Kafka를 단순히 “성능 좋은 기술”로 사용한 것이 아니라, 각각의 장단점을 고려해서 시스템의 병목 지점을 분리했다는 점이다.

선착순 이벤트 시스템에서 중요한 것은 단순히 요청을 빠르게 받는 것이 아니라,

**정해진 수량을 넘기지 않는 것**, **중복 발급을 막는 것**, **DB를 보호하는 것**, **장애가 전체 서비스로 번지지 않게 하는 것**이다.

이 글은 Redis와 Kafka를 왜 사용하는지, 그리고 어떤 문제를 해결하기 위해 사용하는지를 시스템 설계 관점에서 잘 보여주는 사례라고 생각한다.

# 느낀점

이 글을 읽으면서 선착순 이벤트는 단순한 성능 문제가 아니라 동시성, 중복 처리, DB 부하, 장애 전파까지 함께 고려해야 하는 문제라는 것을 알 수 있었다. Redis와 Kafka를 각각 선착순 판정과 비동기 발급 처리에 나누어 사용한 점이 인상 깊었고, 좋은 시스템 설계는 기술을 많이 쓰는 것이 아니라 각 기술의 역할을 명확히 나누는 것이라는 생각이 들었다.
