## 밑바닥부터 이해하는 실시간 데이터 파이프라인 - Debezium 동작 원리

기존 데이터 파이프라인에서는 데이터 웨어하우스에 데이터를 일 단위나 시간 단위 Batch로 적재할 수 있다.

```txt
Source DB
    │
    │ 1시간마다 Batch
    ▼
Data Warehouse
```

하지만 서비스 규모가 커지면 데이터 변경을 더 빠르게 반영해야 하는 경우가 생긴다.

```txt
DB 변경

10:00:01

      ↓

10:00:02

분석 시스템에도 반영
```

여기어때에서는 이런 실시간 데이터 반영을 위해 **CDC(Change Data Capture)** 를 도입했고, 로그 기반 CDC 플랫폼으로 Debezium을 사용했다.

---

## 1. CDC란?

CDC는 **데이터베이스에서 발생한 변경 사항을 감지****해서 다른 시스템으로 전달하는 방식**이다.

예를 들어 다음 데이터가 있다고 하자.

```txt
User Table

id | name
1  | Kim
```

사용자가 이름을 수정했다.

```sql
UPDATE user
SET name = 'Lee'
WHERE id = 1;
```

CDC는 이 변경을 감지한다.

```txt
Before

id = 1
name = Kim


After

id = 1
name = Lee
```

그리고 다른 시스템으로 전달한다.

```txt
MySQL
  │
  │ UPDATE
  ▼
CDC
  │
  ▼
Kafka
  │
  ▼
Data Warehouse
```

---

## 2. 변경 사항을 감지하는 방법

DB 변경을 감지하는 방법은 여러 가지가 있다.

```txt
Trigger 기반

Query 기반

Timestamp 기반

Transaction Log 기반
```

### Trigger 기반

DB Trigger를 만들어 변경 데이터를 별도 Table에 저장한다.

---

**DB Trigger란?**

DB Trigger는 테이블에서 특정 이벤트가 발생했을 때 **DB가 자동으로 실행하는 코드**입니다.

예를 들어 주문 금액이 변경될 때 변경 이력을 자동으로 저장할 수 있습니다.

```sql
CREATE TRIGGER save_order_history
AFTER UPDATE ON orders
FOR EACH ROW
INSERT INTO order_history (
    order_id,
    old_price,
    new_price
)
VALUES (
    OLD.id,
    OLD.price,
    NEW.price
);
```

그러면 애플리케이션이 다음 쿼리만 실행해도:

```txt
UPDATE orders
SET price = 20000
WHERE id = 1;
```

DB가 Trigger를 자동 실행하여 `order_history`에도 기록합니다.

현재 글의 CDC 맥락에서는 다음 구조입니다.

```txt
원본 테이블 변경
      ↓
Trigger 자동 실행
      ↓
별도의 Change Table에 변경 내용 저장
```

장점은 애플리케이션 코드를 수정하지 않아도 변경을 빠짐없이 기록할 수 있다는 것입니다. 반면 단점도 있습니다.

- 원본 데이터 변경마다 추가 작업이 발생함
- DB 내부에 숨은 로직이 생겨 추적과 디버깅이 어려움
- 트래픽이 많으면 DB 부하가 증가함
- 테이블 구조 변경 시 Trigger도 관리해야 함

Debezium은 이런 Trigger 대신 MySQL의 binlog 같은 **트랜잭션 로그를 읽어 변경을 감지**합니다. 그래서 원본 테이블의 쓰기 과정에 Trigger와 Change Table을 직접 추가하지 않아도 됩니다.

---

```txt
UPDATE
   │
   ▼
Trigger
   │
   ▼
Change Table
```

### Query 기반

주기적으로 Query를 실행한다.

```txt
SELECT ...

5초 후

SELECT ...

→ 이전 결과와 비교
```

### Timestamp 기반

`updated_at` 같은 값을 기준으로 변경 데이터를 찾는다.

```sql
SELECT *
FROM user
WHERE updated_at > last_time;
```

여기어때에서 선택한 방식은 **Transaction Log 기반 CDC**였다.

---

## 3. 왜 Transaction Log를 읽을까?

DB는 데이터 변경 내용을 내부 Log에 기록한다.

대표적으로

```txt
MySQL
→ binlog


PostgreSQL
→ WAL
```

이 있다.

MySQL에서

```sql
UPDATE user
SET name = 'Lee'
WHERE id = 1;
```

이 실행되면 변경 내역이 binlog에 기록된다.

```txt
Application
    │
    ▼
 MySQL
    │
    ├── Data Page 변경
    │
    └── binlog 기록
```

Debezium은 이 Transaction Log를 읽는다.

```txt
MySQL

Table
  │
  │ 직접 반복 조회 X
  │
binlog
  │
  ▼
Debezium
```

원문에서는 로그 기반 CDC가 원본 DB를 반복 Query하는 방식보다 DB 부하를 줄일 수 있고, 변경 전후 값을 활용해 데이터 상태를 유지할 수 있다는 점을 선택 이유로 설명한다.

---

## 4. Debezium은 어디에 위치할까?

Debezium은 독립적으로 Kafka에 데이터를 보내는 단순 프로그램이라기보다 **Kafka Connect의 Source Connector로 동작하는 플러그인**이다.

전체 구조는 다음과 같다.

```txt
MySQL
 │
 │ binlog
 ▼
Debezium
 │
 ▼
Kafka Connect
 │
 ▼
Kafka
 │
 ▼
Sink Connector
 │
 ▼
Target
```

Source는 MySQL뿐만 아니라 PostgreSQL, MongoDB 등 여러 DB가 될 수 있다.

```txt
MySQL ───────┐
PostgreSQL ──┼─▶ Debezium ─▶ Kafka
MongoDB ─────┘
```

Kafka에 들어온 Change Event는 다시 Sink Connector를 통해 Data Warehouse 등 다른 시스템으로 전달할 수 있다.

## 5. Kafka Connect부터 이해해야 한다

Debezium의 내부 동작을 이해하려면 Kafka Connect 구조를 먼저 봐야 한다.

Kafka Connect의 주요 단위는 다음과 같다.

```txt
Kafka Connect Cluster

Worker
  │
  ├─ Connector
  │     │
  │     └─ Task
  │
Worker
  │
  └─ Task
```

**Connector와 Worker가 각각 Task와 연결되는 이유**

### 둘 다 맞지만 관계의 종류가 달라요

헷갈린 이유는 그림이 **논리적 소속**과 **실행 위치**를 섞어서 표현했기 때문입니다.

- `Connector → Task`: Task가 **어느 Connector의 작업인지**
- `Worker → Task`: Task가 **어느 프로세스에서 실행되는지**

예를 들어 하나의 Connector가 Task 두 개를 만든다면:

```txt
논리적 관계

Connector A
├─ Task A-1
└─ Task A-2
```

실제 실행 위치는 다음처럼 나뉠 수 있습니다.

```txt
Kafka Connect Cluster

Worker 1
├─ Connector A 관리
└─ Task A-1 실행

Worker 2
└─ Task A-2 실행
```

즉 `Task A-2`는 논리적으로 `Connector A` 소속이지만, 물리적으로는 `Worker 2`에서 실행됩니다.

비유하면:

```txt
Connector = 작업 지시서
Task      = 지시서를 나눈 실제 작업
Worker    = 작업을 수행하는 직원
```

한 작업 지시서에서 여러 작업이 나오고, 각각을 서로 다른 직원에게 배정할 수 있는 것입니다.

따라서 페이지의 그림은 다음처럼 이해하면 됩니다.

> Connector가 Task를 정의하고 만들며, Worker가 그 Task를 받아 실행한다.

Debezium MySQL Connector는 Task를 하나만 만들기 때문에, 그 Task가 여러 Worker 중 한 곳에서 실행됩니다. 해당 Worker가 죽으면 다른 Worker가 그 Task를 넘겨받을 수 있습니다.

개념적으로 보면

```txt
Worker
→ 실제 프로세스


Connector
→ 무엇을 할지 정의


Task
→ 실제 작업 수행 단위
```

다.

Connector를 등록하면 Task가 만들어지고 Worker 위에서 실행된다.

## 6. Debezium MySQL Connector는 왜 Task가 하나일까?

**일반적인 Kafka Connect Connector는 여러 Task로 일을 나눌 수 있다.**

### Connector와 Task의 관계

선택한 문장은 **하나의 Connector 작업을 여러 실행 단위로 쪼개 병렬 처리할 수 있다**는 뜻입니다.

```txt
Connector: “이 데이터를 Kafka로 옮겨라”
   ├─ Task 1: 데이터 일부 처리
   ├─ Task 2: 데이터 일부 처리
   └─ Task 3: 데이터 일부 처리
```

예를 들어 Sink Connector가 Kafka 파티션 6개를 처리한다면:

```txt
Task 1 → Partition 0, 1
Task 2 → Partition 2, 3
Task 3 → Partition 4, 5
```

각 Task가 동시에 실행되므로 처리량이 올라갑니다.

개념을 구분하면:

- **Connector**: 연결 설정과 작업 분배를 관리
- **Task**: 데이터를 실제로 읽거나 쓰는 실행 단위
- **Worker**: Task가 실행되는 Kafka Connect 프로세스

하지만 Debezium MySQL Connector는 하나의 binlog를 순서대로 읽어야 합니다.

```txt
binlog
1. INSERT
2. UPDATE
3. DELETE
```

여러 Task가 나눠 읽으면 이벤트 순서가 뒤섞일 수 있으므로 일반적으로 Task를 하나만 사용합니다. 여러 Worker가 있더라도 처리 병렬화보다는, 현재 Worker 장애 시 다른 Worker가 Task를 이어받는 데 의미가 있습니다.

```txt
Connector

├─ Task 1
├─ Task 2
└─ Task 3
```

하지만 원문에서 설명하는 Debezium MySQL Connector는 **이벤트 발생 순서 보장을 위해 Task 수를 1개로 제한**한다.

예를 들어 DB에서

```txt
1. INSERT

2. UPDATE

3. DELETE
```

가 발생했다.

여러 Task에서 병렬 처리하면서 순서가 달라진다면

```txt
Task 1 → UPDATE

Task 2 → INSERT
```

같은 상황이 생길 수 있다.

따라서 MySQL Transaction Log를 따라가는 작업은 하나의 Task에서 순서대로 처리한다.

## 7. Kafka Connect Task 내부에서는 무엇을 반복할까?

Kafka Connect의 `AbstractWorkerSourceTask`에는 핵심적으로 다음과 같은 Loop가 있다.

```txt
while 실행 중

   │
   ▼
poll()
   │
   ▼
sendRecords()
   │
   ▼
반복

종료

   │
   ▼
finalOffsetCommit()
```

원문의 코드를 단순화하면

```java
while (!isStopping()) {

    toSend = poll();

    sendRecords();
}

finalOffsetCommit();
```

형태다.

결국 Source Connector가 하는 핵심 일은 간단하다.

```txt
가져온다.

   ↓

Kafka에 보낸다.

   ↓

어디까지 처리했는지 기록한다.
```

---

## 8. 1단계: 가져온다

Kafka Connect가 `poll()`을 실행하면 결국 Debezium의 SourceTask로 이어진다.

MySQL Connector에서는 다음과 비슷한 코드가 실행된다.

```java
List<DataChangeEvent> records = queue.poll();

return records.stream()
        .map(DataChangeEvent::getRecord)
        .collect(Collectors.toList());
```

**Debezium 쪽 Java 코드입니다**

MySQL 내부에서 실행되는 코드가 아닙니다. 다만 **MySQL에서 직접 binlog를 읽는 부분도 아니고**, 이미 읽어둔 변경 이벤트를 Debezium 내부 Queue에서 꺼내는 부분입니다.

전체 흐름은 다음과 같습니다.

```txt
MySQL binlog
    ↓
Debezium의 binlog Reader가 읽음
    ↓
Change Event Queue에 저장
    ↓
선택한 코드가 Queue에서 꺼냄
    ↓
Kafka Connect에 SourceRecord로 전달
    ↓
Kafka로 전송
```

선택한 코드를 풀어보면:

```java
// Queue에 쌓인 변경 이벤트를 여러 개 꺼냄
List<DataChangeEvent> records = queue.poll();

// DataChangeEvent 내부의 SourceRecord만 꺼내 List로 반환
return records.stream()
        .map(DataChangeEvent::getRecord)
        .collect(Collectors.toList());
```

따라서 정확히 표현하면:

> Debezium MySQL Connector가 이미 수집해 놓은 MySQL 변경 이벤트를 내부 Queue에서 꺼내 Kafka Connect에 전달하는 코드입니다.

MySQL binlog를 실제로 읽는 코드는 이보다 앞단의 Debezium binlog Reader에 있습니다.

즉 어떤 **Queue에서 변경 이벤트를 꺼낸다.**

```txt
MySQL binlog
    ↓
Debezium의 binlog Reader가 읽음
    ↓
Change Event Queue에 저장
    ↓
선택한 코드가 Queue에서 꺼냄
    ↓
Kafka Connect에 SourceRecord로 전달
    ↓
Kafka로 전송
```

```txt
Change Event Queue

┌──────────────┐
│ Event A      │
│ Event B      │
│ Event C      │
│ Event D      │
└──────────────┘

       │
       │ poll()
       ▼

DataChangeEvent
```

그리고 각각을 Kafka Connect가 이해하는 `SourceRecord`로 반환한다.

## 9. SourceRecord란?

Kafka Connect Source Connector가 Kafka에 전달할 데이터의 기본 표현이라고 보면 된다.

```txt
DB Change Event

      ↓

DataChangeEvent

      ↓

SourceRecord
```

이후 Kafka Connect가 이를 실제 Kafka Producer가 사용할 형태로 변환한다.

## 10. 2단계: Kafka에 보낸다

Kafka Connect는 `sendRecords()`를 실행한다.

---

#### 추가 학습

**정확히는 Kafka Connect Worker에서 실행됩니다**

“Kafka에서 실행된다”를 **Kafka 생태계 안에서 실행된다**는 의미로 말하면 맞지만, **Kafka Broker 내부에서 실행되는 것은 아닙니다.**

```txt
MySQL
  │ binlog
  ▼
Kafka Connect Worker
  ├─ Debezium Connector 실행
  ├─ sendRecords() 실행
  └─ Kafka Producer 사용
          │
          ▼
Kafka Broker
  └─ 메시지 저장
```

역할을 구분하면:

- **Kafka Connect Worker**: `sendRecords()`를 실행하고 메시지를 보냄
- **Kafka Producer**: Kafka Broker로 전송하는 클라이언트
- **Kafka Broker**: 받은 메시지를 Topic에 저장

즉, 선택한 `sendRecords()`는 **Kafka Connect 프로세스에서 실행되고, Kafka Broker는 그 결과를 받아 저장합니다.**

**debezium은 Kafka Connect Worker 안에서 플러그인으로 실행됩니다**

현재 글의 구성에서는 Debezium이 별도 서버 프로세스로 실행되는 것이 아니라, **Kafka Connect Worker에 설치된 Connector 플러그인(JAR)**입니다.

```txt
Kafka Connect Worker 프로세스(JVM)
├─ Kafka Connect 실행 코드
├─ Debezium MySQL Connector 플러그인
├─ Debezium Task
└─ Kafka Producer
```

동작 과정은 다음과 같습니다.

1. Worker의 플러그인 경로에 Debezium을 설치합니다.
1. Kafka Connect REST API로 MySQL 접속 정보 등을 등록합니다.
1. Worker가 Debezium 플러그인을 로딩합니다.
1. Debezium Task가 Worker 프로세스 안에서 실행됩니다.
1. MySQL binlog를 읽어 Kafka Broker로 전송합니다.

따라서 관계는 다음과 같습니다.

```txt
Kafka Connect Worker = 플러그인을 실행하는 플랫폼
Debezium              = Worker에 설치되는 플러그인
Kafka Broker          = 변경 이벤트를 저장하는 서버
```

분산 모드에서는 Task가 다른 Worker로 이동할 수 있으므로, 보통 **모든 Kafka Connect Worker에 동일한 Debezium 플러그인을 설치**합니다.

참고로 Debezium Server나 Embedded Engine을 사용하면 Kafka Connect 없이 별도 애플리케이션으로 실행할 수도 있지만, 현재 글은 Kafka Connect 플러그인 방식입니다.

**보통 별도의 Kafka Connect 서버에 둡니다**

Kafka Connect Worker는 **애플리케이션·DB·Kafka Broker와 분리된 별도 프로세스/서버**로 운영하는 것이 일반적입니다.

```txt
Application Server
        │
        ▼
     MySQL DB
        │ binlog
        ▼
Kafka Connect Worker 서버
  └─ Debezium 플러그인
        │
        ▼
Kafka Broker 서버
```

즉 Kafka Connect Worker는 네트워크를 통해:

- MySQL에 접속해 binlog를 읽고
- Kafka Broker에 접속해 이벤트를 전송합니다.

실제 배포 형태는 보통 다음 중 하나입니다.

```txt
별도 VM 또는 EC2
별도 Docker 컨테이너
Kubernetes의 별도 Deployment/Pod
```

기술적으로 DB나 Kafka Broker와 같은 서버에서 실행할 수도 있지만, 운영 환경에서는 권장하지 않습니다. CPU·메모리 경쟁이나 장애 전파를 피하기 위해서입니다.

따라서 가장 정확한 표현은:

> Kafka Connect Worker는 Kafka Broker 안에 포함된 기능이 아니라, Debezium을 실행하면서 DB와 Kafka 사이를 연결하는 별도의 서버 프로세스다.

다만 현재 글만으로는 여기어때에서 어느 서버에 배치했는지까지는 확인되지 않습니다. 일반적인 운영 구조는 위와 같습니다.

---

내부적으로는

```java
producer.send(producerRecord);
```

형태로 Kafka Producer를 사용한다.

`ProducerRecord`에는 Kafka 메시지에 필요한 정보가 들어 있다.

├─ Partition
├─ Header

```

즉 전체 변환은

      ▼

      ▼

      │
      ▼

      │

```

로 볼 수 있다.

## 11. 3단계: 어디까지 처리했는지 기록한다

Kafka로 Event를 보내는 것만으로는 부족하다.

Debezium이 중단됐다가 다시 실행될 때

```txt
어디까지 binlog를 읽었는가?
```

를 알아야 한다.

그래서 Kafka로 전송이 성공하면 처리 위치를 업데이트한다.

```txt
Kafka ACK
   │
   ▼
recordSent()
   │
   ▼
commitRecord()
   │
   ▼
Last Offset Update
```

원문의 `commitRecord()`에서는 `record.sourceOffset()` 값을 가져와 마지막 Offset을 갱신한다.

**offset은 MySQL binlog를 어디까지 읽었는지 나타내는 Offset입니다**

정확히는 **Debezium이 값의 의미를 정의하고, Kafka Connect가 저장·관리하는 Source Offset**입니다.

예를 들면:

```txt
binlog 파일: mysql-bin.000120
읽은 위치:   483920
```

이 정보는 “이 MySQL binlog의 483920 위치까지 처리했다”라는 체크포인트입니다.

역할을 구분하면:

- **Debezium**: 현재 읽은 binlog 위치를 Offset으로 제공
- **Kafka Connect**: 해당 Offset을 영구 저장하고 복구 시 Debezium에 전달
- **MySQL**: binlog를 제공

분산 모드에서는 일반적으로 Kafka 내부의 `offset.storage.topic`에 저장합니다.

```txt
MySQL binlog
    ↓
Debezium이 변경 이벤트를 읽음
    ↓
Kafka 전송 성공
    ↓
Kafka Connect가 Source Offset 저장
    ↓
장애 후 저장된 위치부터 재개
```

이것은 Kafka Topic 메시지의 Offset과는 다른 개념입니다.

```txt
Source Offset
→ Debezium이 MySQL binlog를 어디까지 읽었는가

Kafka Offset
→ Kafka Consumer가 Topic Partition을 어디까지 읽었는가
```

실제로는 binlog 파일과 위치 외에도 GTID, 행 위치, Snapshot 진행 상태 같은 정보가 함께 저장될 수 있습니다.

## 13. 이제 Debezium이 CDC를 어떻게 구현하는지 보자

Debezium의 MySQL CDC는 크게 두 단계로 나눌 수 있다.

```txt
1. Snapshot

      ↓

2. Binlog Streaming
```

왜 Snapshot이 먼저 필요할까?

---

## 14. CDC만 시작하면 기존 데이터는 어떻게 될까?

현재 MySQL에 데이터가 100만 건 있다고 하자.

```txt
MySQL

기존 Row 1
기존 Row 2
...
기존 Row 1,000,000
```

이 상태에서 binlog 변경 이벤트만 읽으면 CDC 시작 이후에 변경된 데이터만 Kafka에 들어간다.

```txt
CDC 시작 이후

INSERT A
UPDATE B
DELETE C

      ↓

Kafka
```

하지만 Target에는 기존 100만 건이 없다.

```txt
Source

기존 100만 건


Target

0건
```

따라서 먼저 Source와 Target의 초기 상태를 맞춰야 한다.

---

## 15. Snapshot

Debezium에서는 초기 데이터를 복사하는 과정을 **Snapshot**이라고 한다.

```txt
MySQL
  │
  │ 전체 데이터 SELECT
  ▼
Debezium
  │
  ▼
READ Event
  │
  ▼
Kafka
  │
  ▼
Target
```

원문 소스 분석에서는 Snapshot 대상 Table과 Column을 기반으로 실제 `SELECT` Query를 생성하는 부분을 확인했다.

개념적으로는

```sql
SELECT
    column1,
    column2,
    column3
FROM table;
```

형태다.

---

## 16. Snapshot 이후 정상 CDC 시작

Snapshot이 끝나면 Source와 Target의 초기 상태가 맞춰진다.

```txt
Source

A
B
C

     =

Target

A
B
C
```

이제 이후 변경 사항만 전달하면 된다.

```txt
MySQL UPDATE
      │
      ▼
binlog
      │
      ▼
Debezium
      │
      ▼
Kafka
      │
      ▼
Target UPDATE
```

즉 전체 흐름은

```txt
초기 전체 동기화

Snapshot

      ↓

현재 상태 맞춤

      ↓

이후 변경만

Binlog Streaming
```

이다.

---

## 17. Binlog Streaming은 어떻게 시작될까?

MySQL Connector는 MySQL binlog를 읽기 위한 라이브러리를 사용해 이벤트를 수신한다.

binlog에는 여러 이벤트 유형이 있다.

대표적으로

```txt
WRITE_ROWS

UPDATE_ROWS

DELETE_ROWS
```

가 있다.

Debezium에서는 Event Type별 Deserializer를 등록해서 각각의 이벤트를 해석한다.

```txt
MySQL binlog
     │
     ▼
Event Type
     │
 ┌───┼────────┐
 ▼   ▼        ▼
WRITE UPDATE DELETE
 │    │        │
 ▼    ▼        ▼
Deserialize
```

---

## 18. DML 이벤트

DB에서

```sql
INSERT

UPDATE

DELETE
```

가 발생하면 Debezium Change Event로 변환된다.

```txt
MySQL

UPDATE user

     │
     ▼
binlog UPDATE_ROWS

     │
     ▼
Debezium

     │
     ▼
Change Event

     │
     ▼
Kafka Topic
```

일반적으로 Table에 매핑되는 Change Event Topic으로 전달된다.

---

## 19. DDL 이벤트도 처리해야 한다

데이터만 바뀌는 것이 아니다.

DB Schema도 바뀔 수 있다.

```sql
ALTER TABLE user
ADD COLUMN age INT;
```

Debezium이 이 변경을 모르면 이후 binlog를 잘못 해석할 수 있다.

그래서 Schema 변경도 추적한다.

```txt
DDL

CREATE TABLE
ALTER TABLE
...

     │
     ▼
Debezium
     │
     ├─ Schema Model 갱신
     │
     ├─ Schema Change Topic
     │
     └─ Schema History Topic
```

---

## 20. Schema Change Topic과 Schema History Topic

둘의 목적은 다르다.

#### Schema Change Topic

외부 시스템이 Schema 변경을 알 수 있도록 DDL Event를 제공한다.

```txt
ALTER TABLE
     │
     ▼
Schema Change Topic
     │
     ▼
External Consumer
```

#### Schema History Topic

Debezium Connector 내부에서 과거 Schema 이력을 관리하는 용도다.

```txt
Schema v1

   ↓

ALTER TABLE

   ↓

Schema v2

   ↓

ALTER TABLE

   ↓

Schema v3
```

binlog의 특정 위치를 읽을 때 당시 Schema가 무엇이었는지 알아야 이벤트를 정확히 해석할 수 있기 때문이다. 원문은 이 두 Topic을 외부 감지용과 Connector 내부 이력 관리용으로 구분한다.

---

## 21. Debezium에서 Offset은 무엇일까?

MySQL Debezium에서 중요한 위치 정보 중 하나가 **binlog file + position**이다.

예를 들어

```txt
mysql-bin.000120

position = 483920
```

이라고 하자.

이는

```txt
여기까지 처리했다.
```

는 체크포인트 역할을 한다.

```txt
binlog

───────────────●─────────────▶

                ↑
          last position
```

이 정보가 Kafka Connect의 Offset Storage에 기록된다.

---

## 22. Debezium이 재시작되면?

Connector가 장애로 종료됐다고 해보자.

```txt
Debezium
   X
```

다시 실행되면 Offset 정보를 확인한다.

```txt
Offset Storage

mysql-bin.000120
position 483920
```

그리고 해당 위치를 기준으로 CDC를 다시 이어간다.

```txt
binlog

─────────────●──────────────▶
             │
             ▼
         Resume
```

이를 통해 처음부터 binlog를 다시 읽는 것을 피하고 마지막 처리 지점을 기반으로 CDC를 재개한다.

## 25. 실제 운영에서는 어디가 느린지 알아야 한다

CDC Pipeline이 느리다고 해보자.

```txt
Source
  │
  ▼
Debezium
  │
  ▼
Kafka
  │
  ▼
Sink
  │
  ▼
Target

총 10초
```

10초라는 결과만 보면 어느 구간이 느린지 알 수 없다.

```txt
Source → Debezium ?

Debezium Queue ?

Kafka Send ?

Sink ?

Target Write ?
```

그래서 각 Timestamp가 어떤 시점을 의미하는지 분석했다.

---

## 26. source.ts\_ms

`source.ts_ms`는 원문의 설명 기준으로 **Source DB에서 Event가 발생한 시각**을 나타낸다.

```txt
DB Event 발생
     │
     │ source.ts_ms
     ▼
Debezium
```

따라서 Source Query/Transaction 자체가 오래 걸렸다면 전체 Pipeline 시간에도 영향을 준다.

---

## 27. ts\_ms

원문에서는 `ts_ms`를 **Change Event가 Queue에 들어가기 전 기록되는 시각**으로 분석한다.

```txt
binlog Event
    │
    ▼
Debezium 처리
    │
    │ ts_ms
    ▼
Change Event Queue
```

그러면

```txt
ts_ms - source.ts_ms
```

를 통해 Source Event 이후 Debezium에서 Queue에 들어오기 전까지 어느 정도 시간이 걸렸는지 관찰할 수 있다.

---

## 28. Kafka Message Timestamp

Kafka Producer가 실제 메시지를 보낼 때 Kafka Message Timestamp가 기록된다.

```txt
Queue
 │
 ▼
poll
 │
 ▼
Producer
 │
 │ Kafka Timestamp
 ▼
Kafka
```

따라서

```txt
source.ts_ms

ts_ms

Kafka Message Timestamp
```

를 비교하면 병목 위치를 더 구체적으로 확인할 수 있다.

---

## 29. Queue가 왜 필요할까?

Debezium 내부에서

```txt
binlog를 읽는 속도
```

와

```txt
Kafka에 보내는 속도
```

가 항상 같지는 않다.

```txt
Binlog Reader
      │
      ▼
     Queue
      │
      ▼
Kafka Producer
```

Queue가 완충 장치 역할을 한다.

```txt
Source 처리

빠름

   ↓

Queue

   ↓

Kafka Send

조금 느림
```

하지만 Queue가 너무 작으면 Source 쪽 처리가 자주 막힐 수 있고, 너무 크게 잡으면 메모리 사용과 대기 데이터가 늘어날 수 있다.

원문에서는 이 Queue 크기와 Batch 설정을 실제 성능 튜닝 대상으로 사용했다.

---

## 30. max.batch.size

`max.batch.size`는 Connector가 Poll 과정에서 가져올 수 있는 Record 수의 최대값이다.

```txt
Queue

Event 1
Event 2
Event 3
...
Event 1000

      │

max.batch.size = 100

      ▼

100건씩 Poll
```

값을 키우면 한 번에 더 많은 데이터를 처리할 수 있지만 Memory나 처리 지연과 함께 봐야 한다.

---

## 31. max.queue.size

Kafka에 Write하기 전에 Change Event를 저장하는 Queue의 크기다.

```txt
Binlog Reader
      │
      ▼

┌─────────────────┐
│ Change Queue    │
│ max.queue.size  │
└─────────────────┘

      │
      ▼
Kafka
```

Source와 Kafka Producer 사이의 완충 영역 크기를 결정한다.

---

## 32. linger.ms

Kafka Producer가 Record를 바로 하나씩 보내지 않고 조금 기다렸다가 묶어서 전송하도록 할 수 있다.

```txt
Record A ─┐
Record B ─┤
Record C ─┤
Record D ─┘

     │
 linger.ms
     ▼

Batch

     │
     ▼
Kafka
```

Latency와 처리량 사이의 Trade-off가 생긴다.

---

## 33. producer.override.batch.size

Kafka Producer가 Broker로 전송할 때 사용할 Batch 크기를 조절하는 설정이다.

```txt
Connector Queue
      │
      ▼
Producer
      │
      │ Batch
      ▼
Kafka Broker
```

여기어때에서는 이러한 설정이 내부 흐름에 어떤 영향을 미치는지 확인한 뒤 실제 값을 조정해 성능을 개선했다.

---

## 34. 성능 튜닝 구조

정리하면 이런 관계다.

```txt
MySQL binlog
     │
     ▼
Debezium Reader
     │
     ▼
Change Event Queue
     │
     │ max.queue.size
     ▼
poll()
     │
     │ max.batch.size
     ▼

     │
     ├─ linger.ms
     │

     ▼

```

즉 단순히

```txt

```

가 아니라 각 설정이 **어느 단계에 영향을 주는지 알고 조절하는 것**이 중요하다.

## 36. Kafka Connect의 Converter와 Transform

Kafka Connect에는 중간 처리 단계가 있다.

```txt
Connector
   │
   ▼
Transform
   │
   ▼
Converter
   │
   ▼
Kafka
```

#### Converter

데이터를 Kafka가 저장할 Byte 형태로 직렬화하거나 반대로 역직렬화한다.

```txt
Object
  │
  ▼
Serialize
  │
  ▼
Bytes
```

#### Transform

Record에 간단한 변환을 적용한다.

```txt
SourceRecord

     │
     ▼
Transform

     │
     ▼
Modified SourceRecord
```

---

## 37. SMT란?

Kafka Connect에서는 이런 Transform을 **SMT(Single Message Transform)** 로 적용할 수 있다.

기본적으로

```txt
Cast

TimestampConverter
```

같은 Transform이 제공된다.

하지만 원문에서는 기존 Transform만으로 요구사항을 만족시키기 어려웠다.

특정 필드 이름이 아니라

> 특정 데이터 타입을 가진 모든 필드

를 자동으로 변환하고 싶었기 때문이다.

---

## 38. Custom SMT

그래서 직접 SMT를 구현했다.

개념적으로는 다음과 같다.

```txt
SourceRecord
     │
     ▼
Schema Field 순회
     │
     ├─ DATE ?
     │      ↓
     │   변환
     │
     ├─ TIMESTAMP ?
     │      ↓
     │   변환
     │
     └─ DECIMAL ?
            ↓
          변환
     │
     ▼
New Record
```

원문 코드에서도 Schema Field를 하나씩 확인하고 타입에 따라 변환 값을 만드는 구조를 사용한다.

## 40. 장애 후 복구 흐름

운영 중 Debezium이 죽었다고 해보자.

```txt
MySQL
 │
 ▼
binlog

   X
```

Kafka Connect에는 마지막으로 처리한 Source Offset이 남아 있다.

```txt
Offset Storage

binlog file
+
position
```

재시작 후

```txt

      │
      ▼

      │

      │

```

## 41. 이 글에서 가장 중요한 구조

Debezium을 단순히

```txt
DB 변경을 Kafka로 보내주는 프로그램
```

정도로 이해하면 실제 장애나 성능 문제를 분석하기 어렵다.

내부적으로는

```txt
DB Transaction
      │
      ▼
Transaction Log
      │
      ▼
Debezium Reader
      │
      ▼
Deserializer
      │
      ▼
Change Event
      │
      ▼
Internal Queue
      │
      ▼
SourceRecord
      │
      ▼
Kafka Connect
      │
      ▼
ProducerRecord
      │
      ▼
Kafka
      │
      ▼
ACK
      │
      ▼
Source Offset Update
```

라는 여러 단계가 존재한다.

따라서 CDC가 느리면

```txt
DB에서 이벤트 자체가 늦게 발생했나?

Binlog Reader가 느린가?

Internal Queue가 밀렸나?

poll Batch가 작은가?

Kafka Producer가 느린가?

Kafka Broker가 느린가?

Sink가 느린가?
```

를 단계별로 분리해서 봐야 한다.

---

## 42. Snapshot과 Streaming도 구분해야 한다

Debezium의 전체 생명주기는 다음처럼 이해하면 쉽다.

```txt
Connector Start
      │
      ▼
기존 데이터 존재?
      │
      ▼
Snapshot
      │
      │ SELECT
      ▼
READ Events
      │
      ▼
Kafka
      │
      ▼
초기 동기화 완료
      │
      ▼
Binlog Streaming
      │
      ▼
INSERT / UPDATE / DELETE
      │
      ▼
실시간 반영
```

Snapshot은 **초기 상태 동기화**이고,

Streaming은 **이후 변경 사항 동기화**다.

둘의 목적이 다르다.

---

## 43. Kafka Connect와 Debezium의 역할도 구분하자

이 둘도 자주 섞인다.

```txt
Debezium

"DB의 변경을 어떻게 읽을 것인가?"


Kafka Connect

"Source Connector가 가져온 데이터를
어떻게 Kafka로 전달하고
Offset을 관리할 것인가?"
```

즉

```txt
MySQL binlog 해석

→ Debezium


poll / send / offset 관리

→ Kafka Connect
```

라고 보면 이해하기 쉽다.

실제로 Debezium은 Kafka Connect Source Connector 구조 위에서 동작한다.

---

## 정리

Debezium 기반 CDC Pipeline은 다음 순서로 이해하면 된다.

```txt
                 최초 실행

                    │
                    ▼
                 Snapshot
                    │
                    ▼
             초기 데이터 동기화
                    │
                    ▼
              Binlog Streaming
                    │
                    ▼
              Change Event 생성
                    │
                    ▼
             Change Event Queue
                    │
                    ▼
                SourceRecord
                    │
                    ▼
              Kafka Connect
                    │
                    ▼
              Kafka Producer
                    │
                    ▼
                   Kafka
                    │
                    ▼
              Sink Connector
                    │
                    ▼
                  Target


                동시에

Kafka ACK
    │
    ▼
Source Offset Update
    │
    ▼
CDC 재시작 위치 저장
```

이 사례의 핵심은 단순히 Debezium을 설치해 CDC를 구축했다는 것이 아니다.

실제 Source Code까지 따라가며

```txt
어디에서 데이터를 가져오는가?

어디에서 Queue에 쌓이는가?

어떻게 Kafka Record로 변환되는가?

언제 Offset이 기록되는가?

Snapshot은 어떻게 동작하는가?

Binlog Event는 어떻게 해석되는가?

Latency는 어느 Timestamp로 측정할 수 있는가?

각 성능 설정은 어느 구간에 영향을 주는가?
```

를 이해한 뒤 실제 Pipeline 성능 개선과 Custom SMT 구현에 활용했다는 점이 중요하다.

결국 Debezium을 이해할 때 가장 중요한 흐름은 이것이다.

```txt
binlog
  ↓
Debezium
  ↓
Queue
  ↓
SourceRecord
  ↓
Kafka Connect
  ↓
Kafka
  ↓
Offset
```

**CDC 장애나 지연 문제를 해결하려면 "Debezium이 안 된다"에서 멈추지 않고 이 Pipeline의 어느 단계가 막혔는지를 찾을 수 있어야 한다.**
